### 5、读出来的 6 个代码疑点

`compile/src/v-lxde/build.sh:51-78`

1. **`$branch` 未定义** —— 脚本头部不像 v-tint2 那样声明 `branch="--branch=0.6.13"`，`lxtask():56` 的 `git clone --depth=1 $branch $GITHUB/lxde/lxtask` 里 `$branch` 是空串 → 隐式克隆默认分支。`vers.txt` 声明的是 `master`，行为一致但隐式，镜像切换后可能落到错的分支。

2. **`--prefix=$TARGETPATH` 把产物装到 GTK 查找路径之外** —— `lxtask():60` 传 `--prefix=$TARGETPATH`，产物落 `/usr/local/static/lxde/bin/lxtask`。这与 openbox 一致（openbox 也是 `INS_PREFIX=$TARGETPATH`，见 `openbox/build.sh:28`，同样没有 `/usr/local` 那层），两者取件路径模型统一。**但问题在另一头**：GTK 的主题/图标是走全局系统路径查的（`/usr/share/themes`、`/usr/share/icons`、`/usr/etc/gtk-2.0/settings.ini`），构建产物隔离在 `/usr/local/static/<comp>/` 下，**装了也查不到**。见第七章第 2、3 点。

3. **`make LDFLAGS="-static "` 整体覆盖** —— `lxtask():69` 把 LDFLAGS 整个替换，不像 openbox 用 `LDFLAGS="$LDFLAGS -Wl,--start-group $OB_LIBS -Wl,--end-group"` 追加并包裹。`-lgpg-error` / `-lgdk_pixbuf-2.0` / `-lmount` / `-lblkid` 这些传递库**没有 `--start-group` 保护**，能链过靠的是 `LIBS0` 里 OB_LIBS 排在 ex0 / ex1 之后，链接顺序恰好够。这是脆的——增删一个库就可能翻车。

4. **`xx-verify` 验的是构建树，不是安装产物** —— `lxtask():77` 验 `/tmp/lxtask/src/lxtask`；安装到 TARGETPATH 的产物没人验。对比 openbox 验的是 `$ROOT_DEST_DIR${INS_PREFIX}/bin/openbox`（最终交付物）。当前脚本验的通过，不代表 install 后的那个也是静态。

5. **错误检测比 openbox 更糟** —— `v-lxde/build.sh:92` 的 `case` 结尾有 `exit 0`，**无条件返回 0**；再叠加 `oneBuild` 的 `set +e` + `test "0" != "$?"` 判的是 `find` 退出码（见 openbox 文档 8.4），失败一定被吞成 `err 0, pass`。openbox 的 `case` 没有 `exit`、`v-lxde` 连这个都没有了。

6. **`cache)` / `full)` 分支都是空的** —— `:82-87` 两个分支无内容，不会预下载源码，`full` 什么都不做。Dockerfile 里 `# sh /src/v-lxde/build.sh cache;` 本来就是注释掉的，等于从来没生效过。

### 7、主题不识别 + 图标不显示：原因分析

> **订正**：本节是 builder 容器环境侧的盘点（容器里到底装了什么），**不是问题的完整原因**。主线是 gdk-pixbuf loader 静态失效 + GTK2 编译期 prefix 烤死，见 `## 二、`。本节「无真实 GTK2 主题本体 / 无真实图标集 / 无名称来源」三条结论仍然成立，7.2 第三层的 prefix 值原写错了，已在文内订正。

**现象**：当前构建认不出 GTK2 / GTK3 主题，图标不显示。

**共同根因**：x11base 镜像是「最小 X11 + 组件产物隔离到 `/usr/local/static/<comp>/`」的模型，而 GTK 的主题 / 图标是**运行时全局数据**，走固定系统路径查。两套路径模型不兼容 —— 组件装得再干净，主题效果也不会出现。字体同理（openbox 的 fontconfig 重编到 `/usr/local/static/openbox/share/fontconfig`，运行期不设 `FONTCONFIG_PATH` / `FONTCONFIG_FILE` 就不生效）。

#### 7.1、GTK3 主题：不是配置问题，是 GTK3 根本没装

实测（builder-obox）：

```
ls /usr/lib/libgtk-3*      # No such file
ls /usr/include/gtk-3.0    # No such file
find /usr /usr/local -name settings.ini -path "*gtk*"   # 空
```

- **无 `libgtk-3`、无 `gtk-3.0` 头文件、无 `gtk-3.0/settings.ini`**
- lxtask 是用 `libgtk-x11-2.0` 编的（`v-lxde/build.sh:67` 的 `LIBS0` 写死 gtk2），**架构上就不读 GTK3 主题**
- lxappearance 那边 `v-lxde/build.sh:23` 硬关 `--enable-gtk3=no` → 连主题切换器自己都不认 GTK3 主题

要 GTK3 主题生效：装 gtk3 整链 + 编 gtk3 版 lxtask。Arch 的包名就是干这个的 —— `lxtask-gtk3`，`Replaces` / `Conflicts` 都指向 gtk2 版，两者互斥。

#### 7.2、GTK2 主题：入口配置和主题本体两层都缺

**第一层（入口）**：GTK2 读主题的唯一入口是 `gtk-theme-name`，来自 `/usr/etc/gtk-2.0/settings.ini`、`~/.config/gtk-2.0/settings.ini`、`~/.gtkrc-2.0`。实测这三个**全盘都不存在**，也无任何 gtkrc 文件 → `gtk_settings_get_default()->gtk-theme-name` 只能拿到编译期默认值，**根本没有机会去读任何主题**。

> **订正（2026-11-04）**：「无任何 gtkrc 文件」表述不精确。缺的是**入口** gtkrc（`/etc/gtk-2.0/gtkrc`、`/usr/local/etc/gtk-2.0/gtkrc`、`~/.gtkrc-2.0`）与 settings.ini —— 这几类确实全无；但**主题本体** gtkrc 存在：`/usr/share/themes/Raleigh/gtk-2.0/gtkrc`、`Default/gtk-2.0-key/gtkrc`、`Emacs/gtk-2.0-key/gtkrc`（Raleigh 本体在 `/usr` 前缀下，配合 `GTK_DATA_PREFIX=/usr` 可被找到，但效果=内置默认灰，见 二.2.2/二.4.2）。

**第二层（本体）**：`/usr/share/themes` 只有 `Default` / `Emacs` / `Raleigh`。openbox 装的那 9 个主题（Artwiz-boxed / Bear2 / Clearlooks / Mikachu / Natura / Onyx / Onyx-Citrus / Orang…）目录里**只有 `openbox-3/`**，`find ... -name gtkrc*` 无结果 → 是 openbox 私有主题（`themerc` + 位图），GTK 应用认不出来。

> **订正（2026-11-04）**：openbox 主题实为 **11 个**（多出 Clearlooks-3.4 / Clearlooks-Olive / Syscrash），且位于 **`/usr/local/static/openbox/share/themes/`**（隔离安装），**不在** `/usr/share/themes/`；`/usr/share/themes` 确实只有 Default/Emacs/Raleigh 三个。各 openbox 主题仍只含 `openbox-3/`、无 `gtk-2.0/gtkrc`，且不在 GTK2 查找路径（`/usr/local/share/themes` 或 `GTK_DATA_PREFIX=/usr` 的 `/usr/share/themes`）上 —— GTK 认不出的结论不变。

**第三层（查找路径）**：编译期前缀**实测是 `/usr/local`，不是 `/usr`** —— `pkg-config --variable=prefix gtk+-2.0` 报 `/usr` 的是 apk 装的 `gtk+2.0-dev` 的 `.pc` 文件，与静态链进二进制的 `libgtk-x11-2.0.a` 无关（后者 `strings` 只出现 `/usr/local` 系路径）。所以真实查找根是 `/usr/local/share/themes/`（详见二.2）。构建产物隔离在 `/usr/local/static/<comp>/` 下，不在查找路径上。

修法：装真实 GTK2 主题到**实际查找根** `/usr/local/share/themes/<name>/gtk-2.0/gtkrc`（或用 `GTK_DATA_PREFIX=/usr` 把主题根指到 `/usr/share/themes`，见二.2），并让 `gtk-theme-name` 拿到名字（`/etc/gtk-2.0/settings.ini`、`~/.config/gtk-2.0/settings.ini`、`~/.gtkrc-2.0`）。

#### 7.3、图标：图标主题是空壳

```
/usr/share/icons/hicolor/index.theme     # 存在
/usr/share/icons/hicolor/{16x16,22x22,...,512x512,scalable,symbolic}   # 13 个尺寸目录
/usr/share/icons/hicolor/16x16/{actions,apps,stock,...}                # 11 个类别目录
find /usr/share/icons \( -name '*.png' -o -name '*.svg' \) | wc -l     # 0
```

**实际图标数 = 0**。`hicolor-icon-theme` 装了，但它是父主题 / 骨架，本来就只带 `index.theme` 和目录结构，不带图标 —— 真实图标来自继承 hicolor 的具体图标集（Papirus / Oxygen / Adwaita / Humanist 等），**一个都没装**。

`v-lxde/build.sh:6` 留的注释印证了这点：

```sh
# apk add hicolor-icon-theme #need hicolor
```

作者知道要装 hicolor，但**装了也不够**（hicolor 是空的），得装真正的图标集。

叠加两个因素：

1. `gtk-icon-theme-name` 无来源（同 7.2 第一层的 `settings.ini` 缺失）→ GTK 回退内置 default theme
2. openbox 的窗口按钮图标是它自己 draw 的位图（`themes/*/openbox-3/*.xbm`），**不走 GTK icon theme** → openbox 有图标不代表 GTK 应用有。lxtask 的按钮 / 任务条目走 `gtk_icon_theme_load_icon`，找不到就画空白

修法：装真实图标集到 `/usr/share/icons/<name>`，并在 `settings.ini` 里写 `gtk-icon-theme-name=<name>`。

## 二、静态构建下图标与主题失效：问答实录

> **背景（对 一.7 的纠偏）**：「gtk 你管 builder 内环境干嘛，使用静态编译 lxtask 的环境是有的 其他程序正常」—— 一.7 走的是 builder 容器环境盘点，不是要的答案；要的是从**构建配置与二进制机制**上解释为什么图标不显示、主题认不出。
>
> **验证环境**：`builder-obox` / `builder-awe`（`alpine-builder-gtk224`），GTK2 **2.24.33** 源码仍在容器 `/tmp/gtk`，以下结论全部实读源码，不是推测。

### 1、图标：是否走 gdk-pixbuf，loader 动态插件机制是否在静态编译下失效

**问**：

> lxtask的图标显示用到gdk-pixbuf吗？是否它的动态插件机制在静态编译时失效导致？？

**答**：

#### 1.1、lxtask 的图标确实走 gdk-pixbuf

链接行里是写死的（`compile/src/v-lxde/build.sh:67`）：

```
LIBS0=" -lgdk-x11-2.0 -lgtk-x11-2.0 -latk-1.0 -lgdk_pixbuf-2.0 -lpangocairo-1.0 ..."
```

调用链：lxtask 用 GTK2 的 `gtk_icon_theme_load_icon()` 取图标 → GTK 内部就是 `gdk_pixbuf_new_from_file()` 解码 PNG。所以 `gdk-pixbuf` 是 lxtask 图标显示的必经环节，不是可选项。

#### 1.2、是的，动态插件机制在静态编译下失效 —— 这就是图标不显示的直接原因

gdk-pixbuf 的解码器（PNG/JPEG/XPM/ICO…）**不在 `libgdk_pixbuf-2.0.a` 里**，它是独立 loader 模块，运行时靠 **dlopen** 从 loader 目录（`<libdir>/gdk-pixbuf-2.0/2.10.0/loaders/`）动态加载，装配 loader 表。静态构建断在两步：

- **静态归档里没有 loader**。项目里 gdk-pixbuf 2.42.8 是 meson 静态编的，`docs/desk/lxde/pcmanfm-gnome-deps.md:203-205` 记录产出只有 `libstaticpixbufloader-jpeg.a` / `libstaticpixbufloader-png.a` —— loader 是被编成静态归档的，没有可 dlopen 的 `.so`。
- **就算 .so 在位，也 dlopen 不成功**。`common.sh` 的 LDFLAGS 是 `-Wl,--as-needed --static -static -Wl,--strip-all`，lxtask 又叠加 `LDFLAGS="-static "`，**通篇没有 `-rdynamic` / `--export-dynamic`** → 静态二进制没有动态符号表 → dlopen 的 loader 解析不到 `gdk_pixbuf_*` 符号。

结果：loader 表为空 → `gdk_pixbuf_get_file_type()` 返回 `GDK_PIXBUF_UNKNOWN` → `gdk_pixbuf_new_from_file()` 返回 NULL → GTK 画空框。**图标「缺失」，实际是「找不到解码器」**。

这个结论在 awesome 侧已经定案过（`pixbuf-self-decode.md`：静态构建里 loader 模块表不会装配），所以才被迫给 lgishim 自己写了 PNG/JPEG/XPM 自解码器。同一套 gdk-pixbuf，同样问题。

> **订正（2026-11-04）**：`docs/desk/lxde/pixbuf-self-decode.md` **不在本仓**（全仓 grep 无此文件）—— 该「awesome/lgishim 自解码器」结论属 awesome 项目侧，本条应标注为跨仓参考，勿在本仓 docs 内查找。

#### 1.3、但要划清边界：gdk-pixbuf 只是其中一层

修好 loader，图标也未必出来，还有几个**独立**的问题：

- **没有图标数据**：`/usr/share/icons/hicolor` 只有 index.theme 和目录骨架，0 个 png/svg（`hicolor-icon-theme` 本来就只带骨架，真图标来自继承它的图标集，一个都没装）
- **没有主题 / 图标名来源**：没有 settings.ini / gtkrc，`gtk-theme-name` / `gtk-icon-theme-name` 拿不到值
- **GTK2 编译期 prefix 烤死**：见二.2

#### 1.4、当时还没验证的一件事

上面第 2 点里「loader 目录实际状态」在本机没核实过 —— 历史 lxtask 构建在 `/mnt2/_misc2-2/_lxde/`，当前机器没有。容器里 `builder-obox`、`builder-awe` 两个 `alpine-builder-gtk224` 都开着，可进去确认 loader 目录 + `pixbuf-loaders.cache` + `pixbuf-loader.pc` 实际内容、`nm -D` 看二进制有无动态符号表。

> **订正（2026-11-04）**：本条已核实。builder-obox `/usr/lib/gdk-pixbuf-2.0/2.10.0/loaders/` 存在，含 ani/bmp/gif/icns/ico/pnm/qtif/tga/tiff/xbm/xpm 的 `.so` 及 `svg.a`/`svg.la`，**无 png.so / jpeg.so**；`nm -D /tmp/lxtask/src/lxtask` → **no symbols**（无动态符号表）。两处均坐实「loader 装配失败 / dlopen 无法解析符号」根因。

### 2、主题：prefix 烤死的关系、当前默认值、软链接调试、怎么改

**问**：

> 另外主题这块呢，识别不到，GTK2 编译期 prefix 烤死，与这个有关系是吧？它当前识别的默认值是啥？是否通过软链接的方式调试呢？如果要达成主题可以识别可用，要怎么改？

**答**：

#### 2.1、是的，prefix 烤死直接就是主题找不到的原因

主题根目录是这么拼出来的（`gtk/gtkrc.c:459-473`，`gtk_rc_get_theme_dir`）：

```c
var = g_getenv ("GTK_DATA_PREFIX");
if (var)
  path = g_build_filename (var, "share", "themes", NULL);
else
  path = g_build_filename (GTK_DATA_PREFIX, "share", "themes", NULL);
```

`GTK_DATA_PREFIX` 是宏，配出来的值就是 `/usr/local`（`u-gtk/build.sh:122` 是 `./configure --enable-static`，**没给 `--prefix`**；`strings /usr/lib/libgtk-x11-2.0.a` 只出现 `/usr/local`、`/usr/local/etc`、`/usr/local/lib`、`/usr/local/share/locale`，没有 `/usr`）。

所以 GTK2 找的是 **`/usr/local/share/themes/<name>/gtk-2.0/gtkrc`**，而 Alpine 把主题装在 `/usr/share/themes/`。差一层目录，全部落空。

#### 2.2、当前识别的默认值（写死在 `gtk/gtksettings.c`）

```
gtk-theme-name        默认 "Raleigh"   ← gtksettings.c:315
gtk-icon-theme-name   默认 "hicolor"   ← gtksettings.c:325
```

所以不是「没有主题名」。**名字有值，是路径不对**。GTK2 拿 "Raleigh" 去 `/usr/local/share/themes/Raleigh/gtk-2.0/gtkrc` 找，找不到 → 回退**内置 Raleigh 默认样式**（GTK 库自己带的灰色系统默认），这就是看到的那个样子 —— 看起来「认不出主题」，实际是「回退到内置默认」。

#### 2.3、默认 rc 文件的完整搜索顺序（`gtk/gtkrc.c:514-550`）

1. `GTK2_RC_FILES` 环境变量 —— **整表替换**，注意是 `GTK2_RC_FILES`，不是 GTK3 的 `GTK_RC_FILES`
2. 否则 `/usr/local/share/gtk-2.0/gtkrc`（烤死前缀，**不读环境变量**）
3. `g_get_system_config_dirs()` + `/gtk-2.0/gtkrc` → 即 `/etc/gtk-2.0/gtkrc`（受 `XDG_CONFIG_DIRS` 影响）
4. `/usr/local/etc/gtk-2.0/gtkrc`
5. `$HOME/.gtkrc-2.0`

#### 2.4、软链接能调试，但有更轻的三档，优先序如下

| 手段 | 代价 | 说明 |
|---|---|---|
| `GTK_DATA_PREFIX=/usr` | 零重编、零拷贝 | 只改主题根 → `/usr/share/themes`。**最省事的验证手段**，但只影响主题根，不影响第 3 节第 2 项 fallback gtkrc |
| `GTK2_RC_FILES=/usr/share/themes/<name>/gtk-2.0/gtkrc` | 零重编 | 直接喂 rc 文件，**完全绕过主题名查找**，可单独验证某个主题文件本身对不对 |
| `~/.gtkrc-2.0` 里 `include ".../gtkrc"` | 零重编 | 用户级，搜索顺序最后一位但一定会被查 |
| 软链接 `ln -s /usr/share/themes /usr/local/share/themes` | 改文件系统 | 能用，但 `/usr/local/share` 里还有 `locale`、awesome 自己的主题，整目录挂会有覆盖风险；逐个主题建软链接更安全 |

#### 2.5、要真正可用，得动四层

1. **数据层**：得装真实 GTK2 主题（含 `gtk-2.0/gtkrc`）。openbox 那 9 个主题不行 —— 目录里只有 `openbox-3/`，没有 `gtk-2.0/gtkrc`，GTK 应用认不出来。
2. **查找层**（三选一）：`GTK_DATA_PREFIX=/usr` → 软链接 → 重编 GTK2 加 `--prefix=/usr`（代价最大，牵动所有已构建 GTK2 组件，且和 `/usr/local/static/<comp>` 隔离模型冲突）。
3. **名称层**：让 `gtk-theme-name` 拿到你装的主题名。候选位置：`GTK2_RC_FILES`、`~/.gtkrc-2.0`、`/etc/gtk-2.0/gtkrc`。**订正：原写的是 `/etc/gtk-2.0/settings.ini`、`~/.config/gtk-2.0/settings.ini`，实测两个都不生效 —— GTK 2.24 根本不读 `settings.ini`，见 4.2(a)**。
4. **引擎层（隐藏坑）**：主题 gtkrc 里如果有 `-engine " Clearlooks "` 这类指令，引擎是 `<prefix>/lib/gtk-2.0/<version>/engines/*.so`（`gtk_rc.c:402/404`），**又是一次 dlopen**，静态构建下同 gdk-pixbuf loader 的毛病。所以选主题时要挑 **gtkrc 里不带 `-engine` 指令的**。另外 `u-gtk/build.sh:108` 带的是 `--disable-modules`，这个对引擎加载的影响未实测。

#### 2.6、一个容易搞混的点

lxtask 自己的 `--prefix=$TARGETPATH`（`/usr/local/static/lxde`，`Dockerfile:265`）**跟主题查找无关**，那只决定 lxtask 二进制装到哪。烤死的是 **GTK2 库自己的 prefix**（`/usr/local`）。两者不是一个东西。

### 3、musl 下编译的 lxtask 在 ubt22 环境下能用 gtk2 主题吗

**问**：

> 主题那块，musl下编译的lxtask在ubt22环境下能用gtk2主题吗

**答**：

能跑，但结论分两半：**主题「认得到」，但「出得了效果」的只有纯 rc 主题**。而且 musl/glibc 这层跟问题完全无关。

#### 3.1、musl 这层不参与

lxtask 是全静态（`ldd` → Not a valid dynamic program），musl 打包在二进制里，主机 libc 不参与任何符号解析；X11 协议 ABI 稳定。所以 musl 静态二进制的 lxtask 在 ubt22 上照跑。真正决定主题的只有**两件主机相关的事：路径、dlopen**。

#### 3.2、路径：还是烤死前缀那套，跟发行版无关

- 烤死 `/usr/local` → 查 `/usr/local/share/themes`
- 实测 ubt22：**`/usr/local/share` 存在，`themes` 子目录不存在**
- 加 `GTK_DATA_PREFIX=/usr` 或写 `~/.gtkrc-2.0` → 就能找到。这条在 ubt22 上通

#### 3.3、ubt22 实际有什么主题

（`docker-hdmi-desktop-desktop-1`，Ubuntu 22.04.5）

- `/usr/share/themes` 26 个目录，**只有 4 个带 `gtk-2.0/gtkrc`**：Raleigh / Greybird / Greybird-dark / MurrinaChrome（2026-11-04 实测为 **27** 个目录，带 `gtk-2.0/gtkrc` 的仍为这 4 个）
- openbox 那批（Artwiz-boxed、Bear2、Clearlooks、Natura、Onyx、Orang…）**没有 `gtk-2.0/gtkrc`**，GTK 认不出
- 无 `/etc/gtk-2.0/settings.ini`、无 `~/.config/gtk-2.0/settings.ini` → `gtk-theme-name` 停在编译默认 **"Raleigh"**

#### 3.4、出不出效果：分档

| 主题 | `engine` 指令数 | 静态构建下的实际效果 |
|---|---|---|
| Raleigh | **0**（gtkrc 只有注释） | 找到即「生效」，但等于内置默认灰色 → **视觉零变化** |
| Greybird / Greybird-dark | 30 | murrine 加载失败，**优雅降级**：gtkrc 里 947 行非 engine 的 style/widget 规则照吃 → 颜色/字号/边框宽度生效，圆角/渐变/阴影不生效 |
| MurrinaChrome | 6 | 同上，降级 |

两个事实叠起来：

- murrine 引擎走 `<prefix>/lib/gtk-2.0/<ver>/engines/*.so` dlopen（`gtk_rc.c:402/404`），静态二进制无 `-rdynamic` → 加载失败
- **这台 ubt22 引擎目录里只有 `libpixmap.so`，murrine 根本没装** —— 就算用动态 GTK2 的应用，在这台机器上也加载不了 murrine。所以这不是 musl 的锅，是环境本来就缺引擎

#### 3.5、图标这层，ubt22 也救不了

有意思的对比：ubt22 的 PNG/JPEG **是编进 `libgdk-pixbuf` 的**（`ldd` 显示直接链接 `libpng16.so.16`、`libjpeg.so.8`；loaders 目录里只有 ani/bmp/gif/icns/ico/pnm/qtif/svg/xpm，**没有 png.so / jpeg.so**）。

但那是**主机的 glibc 版库**，帮不上我们二进制里自带的那份 —— 我们的 PNG/JPEG 是独立的 `libstaticpixbufloader-*.a`，没链进 lxtask。所以图标在 ubt22 上照样不显示，跟主机有无 loader 无关。

#### 3.6、要真拿到主题视觉，三条路

1. **带一个纯 rc 主题**（gtkrc 里不含任何 `engine` 指令，只用 `style` / `font_name` / `border` / `bg` 等纯 rc 属性，Emacs 风格）→ 零依赖，静态下 100% 生效。**最推荐**
2. **解决引擎 dlopen**：链接加 `-Wl,--export-dynamic` 导出动态符号表 + 把 murrine engine .so 装到 `/usr/local/lib/gtk-2.0/2.10.0/engines/`。代价：重编 lxtask，且 glibc 版引擎 .so 要跟静态 musl 二进制的导出符号对上，风险不小
3. **放弃全静态**，动态链 GTK2 —— 那就不叫静态构建了

---

**一句话**：musl → ubt22 跑没问题；主题加个 `GTK_DATA_PREFIX=/usr` 就「认得到」，但真正能出效果的只有纯 rc 主题，Greybird 类会降级成半成品，murrine 这台机子压根没装；图标是另一条独立的死路。

### 4、greybird主题呢

**问**：

> greybird主题呢

**答**：

真跑了。Greybird 在静态 musl GTK2 下：**能识别、能部分生效、但视觉降级**。

#### 4.1、实验

在 builder-obox 编了一个 36M 静态 GTK2 测试程序（`ldd` = not a dynamic executable，`-rwxr-xr-x`），`docker cp` 进 `docker-hdmi-desktop-desktop-1`（Ubuntu 22.04.5，带 Xvfb + scrot），跑了三种配置截图对比。

编译要点：LIBS0 整体包在 `-Wl,--start-group ... -Wl,--end-group` 里，**且 `-lXinerama -lXfixes -lXrandr` 必须在 group 内**（放外面会剩 21 个 `XFixes*` / `XRR*` undefined）。lxtask 脚本能链过是因为它源码直接引用 `gdk_*`。

#### 4.2、关键发现

**(a) `settings.ini` 完全无效 —— GTK2 根本不读它（订正 2.5 第 3 条）**

`HOME=/tmp/hB` 里写了 `~/.config/gtk-2.0/settings.ini`（`[Settings]` + `gtk-theme-name = "Greybird"`），程序回读仍是 **`gtk-theme-name=Raleigh`**。

原因：`grep -rln settings.ini /tmp/gtk/gtk /tmp/gtk/gdk` → **空**。GTK 2.24 源码里压根没有 `settings.ini` 这个字符串，`GTK_PATH_SETTINGS` 也不存在。**settings.ini 是 GTK3 的机制**，GTK2 只读 gtkrc。

能用的注入方式是 `GTK2_RC_FILES=/tmp/myrc`（内容 `gtk-theme-name = "Greybird"`）→ 回读 **`gtk-theme-name=Greybird`** ✓

**(b) 补上了本张末尾挂着的待实测项 (a) —— dlopen 失败的真实报错**

```
GModule-CRITICAL: g_module_symbol: assertion 'module != NULL' failed
GModule-CRITICAL: g_module_close: assertion 'module != NULL' failed
```

**这就是 lxappearance 当年死掉的那个 gmodule 错误**，同一根因：静态二进制无动态符号表 → `g_module_open` 失败。lxappearance 的挂掉和 lxtask 的 loader 失效是同一条根。

**(c) Greybird 的 30 条 engine 指令全挂**

| 项 | 数据 |
|---|---|
| gtkrc 里 `engine "murrine"` | 27 处 |
| gtkrc 里 `engine "pixmap"` | 3 处 |
| `^style ` 块 | 49 个 |
| 非 engine 有效行 | 947 行 |
| gtkrc 里位图引用 | **0 个**（不碰 gdk-pixbuf） |
| 运行时报 | `Unable to locate theme engine in module_path: "murrine"` ×34、`"pixmap"` ×4 |

#### 4.3、截图对比

`default` 12477B / `Greybird` 12253B，md5 不同 —— **有真实变化，但只有半条**：

- Greybird 的 `bg_color:#CECECE` 等**非 engine 属性生效**了：窗口底色变浅暖灰、菜单栏变无边框扁平
- 按钮**丢失全部 bevel / 渐变 / 浮雕**（那些是 murrine 画的）—— 退化成扁灰矩形

#### 4.4、还有两件环境侧的事

- 这台 ubt22 的引擎目录里**只有 `libpixmap.so`，murrine 根本没装** → 就算动态 GTK2 应用，在这台机上也加载不了 Greybird
- 该 ubt22 的 `libgdk-pixbuf` 把 PNG/JPEG **编进库内**（`ldd` 直链 `libpng16.so.16` / `libjpeg.so.8`；loaders 目录无 png/jpeg.so）—— 跟 Alpine 静态构建「PNG/JPEG 是独立 `libstaticpixbufloader-*.a`」机制相反

#### 4.5、结论

Greybird 这种 murrine 系主题在静态构建下 = **配色能用、造型没了**。想要完整主题视觉，要么挑**纯 rc 主题**（无 `engine` 指令，Greybird 的 947 行证明了普通 `style` / `widget` 属性照常工作），要么走 `-Wl,--export-dynamic` + 补 murrine .so（未实测）。

### 3.1、主题路径与 GTK2 编译配置

#### 3.1.1、主题路径的编译选项：只有 `--prefix`

**结论**：GTK2 的主题根目录由**编译期 `--prefix` 决定**，不是 `--datadir`。权威证据 `gtk/Makefile.am:47`：

即 `GTK_DATA_PREFIX = configure --prefix`，主题根 = `$(prefix)/share/themes`（`gtk/gtkrc.c:470` 用 `g_build_filename(GTK_DATA_PREFIX,"share","themes")`）。

- **现状**：`u-gtk/build.sh` configure 实际是 `./configure --enable-static`（**未给 `--prefix`**）→ prefix=`/usr/local` → 找 `/usr/local/share/themes`（`strings libgtk-x11-2.0.a` 只出现 `/usr/local`，印证）。

#### 3.2.3、对**静态构建**的实际影响（这才是关键）

- **纯文件直读类**（fopen，不 dlopen）→ `--prefix=/usr` 真能生效：**主题 rc、locale 翻译、默认 gtkrc**。这就是为什么 `--prefix=/usr` 能救主题。
- **dlopen 类**（引擎/输入法/打印后端/gdk-pixbuf loader）→ **静态 musl 下 dlopen 是弱桩，结构上不可能**（详见 `### 3、`）——这部分**跟 `--prefix` 无关**，改 prefix 也救不了。⚠️ **撤回**此前「`-Wl,--export-dynamic` + 装 `.so`」的说法：静态二进制无 `.dynsym`/无动态段，且 loader 是 glibc 编译、跨 libc 调用（FS 寄存器/线程指针）必崩，`--export-dynamic` 救不了 dlopen 新开一个 `.so`。
- 所以：**`--prefix=/usr` 只对「主题/字体名/locale」这三样有正收益**，图标（loader）、引擎（murrine）、输入法、打印后端在静态下依旧死路，只能走**消除 dlopen**（自解码/静态注册/内置）或**放弃真静态**，见 `### 3、`。

### 3.3、dlopen 类在静态+跨 musl/glibc 下走不通：重新评估（2026-11-04，**纠正前述 `--export-dynamic` 说法**）

> **前提（用户拍板）**：dlopen 类功能——**图标 loader、主题引擎（murrine）、输入法（IM）、打印后端——全部都要，不能省去**。因此「禁用 IM / 禁用打印后端 / 用无 `-engine` 纯 rc 主题」这类**省功能方案一律不成立**，只接受「把功能做出来」的方案。

#### 3.3.1、为什么 dlopen 在静态 + 跨 musl/glibc 下结构上不可能（三层，无解）

> 证据链：上游 musl 源码 + 参考仓 `fk-awesomewm`（同款 gdk-pixbuf 问题已定案）+ 国内外社区（musl 邮件列表 / Crystal / Zig / kit-lang）。

- **第 1 层：musl 静态 `dlopen` 本身就是弱桩**。musl 的 `libc.a` 里 `dlopen` 是个空壳（`src/ldso/dlopen.c`）：直接 `__dl_seterr("Dynamic loading not supported"); return 0;`。真实现 `ldso/dynlink.c` **只编进 `libc.so`，从不进 `libc.a`**（musl 1.2.4 Makefile：`LDSO_OBJS` 只进 `libc.so`）。所以静态二进制里**根本没有动态加载器**，`dlopen` 永远返回 NULL。`-Wl,--export-dynamic` 只是让可执行文件向**已加载**的库导出符号，对 dlopen **新开**的 `.so` 无济于事——何况入口都不存在。
- **第 2 层：静态二进制没有动态段**。`readelf` 证实：`.dynsym` 段 = 0、无 dynamic section。而 loader `.so` 的 `DT_NEEDED` 是 `libgdk_pixbuf-2.0.so.0` / `libglib-2.0.so.0` / `libc.so.6`——我们链的是 `.a`，这些 `.so.0` **磁盘上不存在**，dlopen 第一步就死；就算打开，`.so` 里 `gdk_pixbuf_register_format` 也**无处解析**（无动态符号表）。
- **第 3 层（跨 libc 硬墙，核心）**：即使有 loader，loader 是 **glibc 编译**的，它调用的 `libc.so.6` 函数（malloc/pthread/TLS）依赖 glibc 的 **FS/GS 线程指针 + 全局态**（signal handler、prctl）。Rich Felker（musl 作者）原话：**「any attempt to run a foreign libc in the same process is inherently going to be poking at implementation internals」**。`foreign-dlopen`（社区最常用的用户态 ELF loader 绕法）实测 **musl+glibc 共存会抢 FS 寄存器崩溃**（issue #5），且只能调「纯 syscall 类」函数——而 gdk-pixbuf loader 必须回调 `gdk_pixbuf_register_format`，**跨不过去**。

**→ 定论：`dlopen` 在静态 + 跨 musl/glibc 下彻底走不通，无任何链接旗标能救。唯一出路是「消除 dlopen 依赖」或「放弃真静态」。**

**图标"不显示"的真因：路径/主题查找，非解码（2026-11-04 补充）：**

  - 图标主题搜索路径由 `g_get_system_data_dirs()` 决定：**默认返回 `/usr/local/share` + `/usr/share`（`/usr/local` 优先）**，再拼出 `$HOME/.icons`、`<dir>/icons`、`<dir>/pixmaps`。若 `/usr/local` 那层被组件隔离占用、无真实图标集，就会盖过后者的真实图标。
  - **`XDG_DATA_DIRS` 环境变量可完全覆盖默认路径**（实测 `XDG_DATA_DIRS=/custom/share` → `g_get_system_data_dirs()` 只返回 `/custom/share`；**空值**→ 回落默认）。**这就是运行时指向正确图标路径的环境变量**：设 `XDG_DATA_DIRS=/usr/share`（真实图标集所在）即可让 GTK 找到图标。
  - 主题名来源是 `gtk-icon-theme-name`（`gtksettings.c:322`、`gtkicontheme.c:411/513`），无 `settings.ini`/gtkrc 就回退默认 `hicolor`；`index.theme` 是主题识别必需（`gtkicontheme.c:944/1366`）。
- **端到端实测（2026-11-04，hdmi-desktop 容器 Xvnc `:313`）**：静态 `icon_test`（49M，链新 libgtk + 内置解码 gdk_pixbuf）跑 `gtk_icon_theme_lookup_icon("ac-adapter")`，三组对照：
  - **默认（`XDG_DATA_DIRS` unset）** → `ac-adapter: FOUND base=48`（走 `/usr/share` 默认路径）；
  - **`XDG_DATA_DIRS=/nonexistent`** → 全部 `MISSING`，且 Gtk-WARNING **"Could not find the icon 'ac-adapter'. The 'hicolor' theme was not found either"** —— 这正是"图标不显示"的报错；
  - **`XDG_DATA_DIRS=/usr/share`** → `ac-adapter: FOUND base=48`（恢复）。
  - **结论**：同一静态二进制，**仅改 `XDG_DATA_DIRS`** 就能让图标从"主题找不到/全 MISSING"变为 FOUND —— **路径/主题查找是真因，解码无关**（解码已内置，且该二进制无任何 loader `.so`）。"不显示"发生的环境 = 该路径下**没有真实图标集**（x11base 镜像 `/usr/share` 只有空 hicolor 骨架，正是这种环境）；Ubuntu 容器有真实图标集所以默认 FOUND。
- **结论**：图标解码**零改动**已通；**"不显示"另需**运行时让 `XDG_DATA_DIRS` 指向真实图标集目录（如 `/usr/share`）+ 确保 `gtk-icon-theme-name` 有值。二者都是运行时/配置层，**不改库**。

**输入法 IM —— 未启用，需重编 GTK2：**
- `/tmp/gtk/config.h`：`USE_GMODULE 1`，**无 `INCLUDE_IM_xim`**；`/tmp/gtk` 下**无 `libstatic-im-xim*`** 产物 → 当前 **IM 走 dlopen，未内置**。
- `configure.ac:806` 有 `AC_ARG_WITH(included_immodules,...)`，`configure:1780` 有 `--with-included-immodules=MODULE1,MODULE2,...`；`configure:23654-23680` 证实它生成 `INCLUDED_IMMODULE_OBJ=../modules/input/libstatic-im-xim.la` + `-DINCLUDE_IM_xim`，`modules/input/Makefile.am:35-39` 有 `libstatic-im-xim.la` 规则。
- **结论**：要内置 XIM，**必须重编 GTK2**，在 `u-gtk/build.sh` 的 `:123` **真正传** `--with-included-immodules=xim`（注意 `args1` 死代码坑：别塞进 `args=` 块）。这是**改库/重编**，不是零改动。

**→ ① 结论：图标 loader = 已内置零改动；IM = 需重编 GTK2（一个 configure 参数）。**

#### 3.3.7、③ 主题路径评估：GTK 编译改 `--prefix=/usr` 能否免设 XDG_DATA_DIRS（2026-11-04）

> **用户问题**：GTK 编译用 `/usr` 不用 `/usr/local`，以免额外设置 `XDG_DATA_DIRS` 环境变量，评估这样调整的其他影响。

**核心结论：改 GTK `--prefix` 对「图标主题路径」无效——图标路径由 glib 的 `g_get_system_data_dirs()` 决定，不是 GTK prefix。**
- **图标主题路径 ≠ GTK prefix**：`gtkicontheme.c:570` 用 `g_get_system_data_dirs()`（**glib** 的函数），**不是** `gtk_get_data_dir()`（=GTK_PREFIX/share）。→ 改 GTK `--prefix=/usr` **不能**改变图标主题搜索路径，也**不能**避免设 `XDG_DATA_DIRS`。
- **glib 的 `g_get_system_data_dirs` 默认 = `/usr/local/share` + `/usr/share`**（实测 `/tmp/xdg_test` 无 `XDG_DATA_DIRS` → `dir[0]=/usr/local/share/`、`dir[1]=/usr/share/`；**即使 glib 自身 `prefix=/usr`**），且 `/usr/local` 优先。要改这个默认只有两条路：① 运行时设 `XDG_DATA_DIRS`；② 重编 glib 改它的 datadir 常量。
- **glib 不是 x11base 自编译**：`compile/src/` 下**无 glib 构建脚本/源码**；builder 里是 **Alpine apk 预装 `glib-2.70.5`**（glib/glib-dev/glib-static，`libglib-2.0.a`=/usr/lib 4.9M，`glib-2.0.pc` `prefix=/usr`）。→ **无法通过改 x11base 仓库的构建脚本改 glib**；要改得自己拉 glib 源码重编（工作量大、影响基础库，**不建议**）。

**改 GTK `--prefix=/usr` 实际影响（其他影响评估）**：
- **对 GTK 自身数据路径有效**：`gtk_get_data_dir()` = `GTK_PREFIX/share` → 主题 gtkrc 默认 `/usr/share/gtk-2.0`；主题引擎目录 `<prefix>/lib/gtk-2.0/2.10.0/engines`；模块 `<prefix>/lib/gtk-2.0/2.10.0/...`。若真实主题在 `/usr/share`，这部分受益。`GTK_DATA_PREFIX` 环境变量可**运行时覆盖** `gtk_get_data_dir()`（主题 gtkrc 部分，前 3.2.1 已提）。
- **对图标主题路径无效**（见上）——lxtask「图标不显示」主因正在此层，改 GTK prefix **帮不上**。
- **重编成本**：GTK 全量重编（`configure --prefix=/usr` + `make`），中-高。
- **产物/冲突**：当前 GTK configure（`u-gtk/build.sh:124-125`）**未显式设 `--prefix`**（默认 `/usr/local`），args 块（:93-115）也无。若只静态链接（不 `make install`），`--prefix` 只改编译期 `GTK_PREFIX` 宏，不实际写 `/usr`，风险小；若 `make install` 会写 `/usr/share`、`/usr/lib`（x11base 镜像系统区，需确认可写/无冲突）。与 lxtask 的 `$TARGETPATH=/usr/local/static/lxde` 模型**不冲突**（GTK 是独立依赖库）。
- **`/usr/local` 残留**：`g_get_system_data_dirs` 仍含 `/usr/local/share`（glib 层），若该处有空的组件隔离目录会盖过 `/usr/share`——**与 GTK prefix 无关**，需单独处理。

**结论（免设环境变量且图标路径正确的可行选项，按性价比）**：
1. **运行时 `XDG_DATA_DIRS=/usr/share`**（轻量，**已实测有效**，最省）——仍是最优。
2. **把真实图标集放 `/usr/local/share/icons`**（默认 `g_get_system_data_dirs` 的 `/usr/local` 优先命中；镜像内容层，**无需环境变量、无需改库**）——x11base 镜像侧装图标即可。
3. 重编 glib 改 datadir（成本高、影响基础库，**不建议**）；改 GTK `--prefix=/usr` **对图标无效**，仅对主题 gtkrc/引擎路径有益，非本问题解药。

### 3.4、本地运行配置：静态 lxtask 用系统 Greybird 主题 + 图标（2026-11-04）

> **前提**：调试环境 = `docker-hdmi-desktop-desktop-1`（app-ubuntu-22.04，= maki 自身容器），**headless 用户**（`HOME=/_ext/home/headless`）。用户本地（headless）跑静态 lxtask 是**默认样式**，而 apt 动态 lxtask（`/usr/bin/lxtask`）正常（Greybird）。

#### 3.4.1、根因（已实测复现）
- 静态 lxtask 的 GTK2 `GTK_DATA_PREFIX` 在编译期**烤死**为 `configure --prefix=/usr/local/static/lxde`。GTK2 主题/图标查找以 `gtk_get_data_dir()` 为基准，它读 `GTK_DATA_PREFIX` 环境变量（若有），否则用**编译期前缀** `/usr/local/static/lxde`。
- 用户环境 `/usr/local/static/lxde/share/themes` **不存在**（实测 `No such file or directory`）→ 即使 headless 的 gtkrc 设了 `gtk-theme-name="Greybird"`，GTK2 也**加载不到 Greybird 的 gtkrc 文件**（在 `/usr/local/static/lxde/share/themes/Greybird/` 找，不存在）→ 静默回退默认主题。
- apt 动态 lxtask 的 `GTK_DATA_PREFIX=/usr` → 能加载 `/usr/share/themes/Greybird` → 正常。

#### 3.4.2、端到端验证（2026-11-04，headless + root Xvnc `:350`）

| 配置 | 窗口 | 背景像素 `(300,12)` | 日志证据 |
|---|---|---|---|
| 默认（无 `GTK_DATA_PREFIX`） | "Task Manager" 600×400 | `(220,218,213)`（GTK 默认米灰） | 无主题警告（未加载 Greybird） |
| `GTK_DATA_PREFIX=/usr` | "Task Manager" 600×400 | `(206,206,206)`（**Greybird 浅灰** `#cecece`） | `Unable to locate theme engine: "pixmap"` —— 这是 **Greybird gtkrc 被加载** 的直接证据（Greybird 用 pixmap 引擎画 checkbox/radio） |

#### 3.4.3、配置方案（推荐，**必须用 PNG 图标集**）
```sh
GTK_DATA_PREFIX=/usr GTK2_RC_FILES=$HOME/.gtkrc-lxtask ./lxtask
```
- **为什么必须 `GTK2_RC_FILES`**：headless 的 gtkrc 设 `gtk-icon-theme-name="Papirus-Bunsen-bluegrey"`，而 **Papirus 是纯 SVG（实测 509 svg / 0 png）**；静态 gdk-pixbuf **只内置 PNG/JPEG**（`nm` 实见 `_gdk_pixbuf__png/jpeg_fill_vtable`），**无 SVG 解码器**（系统也无 `libpixbufloader-svg`）→ **Papirus 图标在静态程序里解码不了、不显示**。必须覆盖为 **PNG 图标集 `elementary-xfce`**（Greybird 配套，PNG 可解码，v2 截图已证可用）。
- `~/.gtkrc-lxtask`（wrapper，绝对路径 include 不依赖数据前缀）：
  ```sh
  include "/usr/share/themes/Greybird/gtk-2.0/gtkrc"
  gtk-icon-theme-name = "elementary-xfce"   # PNG 图标集，静态可解码（Papirus SVG 不行）
  ```
- `GTK_DATA_PREFIX=/usr`：让静态程序从 `/usr/share` 找主题/图标（否则烤死 `/usr/local/static/lxde` 找不到）。
- **只设 `GTK_DATA_PREFIX=/usr` 不够**：会沿用 headless gtkrc 的 Papirus（SVG）→ 图标仍不显示，需上面的 wrapper 覆盖图标主题。
- 图标路径还依赖 `XDG_DATA_DIRS` 含 `/usr/share`（默认含；若被改则 `export XDG_DATA_DIRS=/usr/share`）。

#### 3.4.4、本环境注意
- headless `~/.gtkrc-2.0` 里 `include "/home/headless/.gtkrc-2.0.mine"` **路径与实际不符**（实际 HOME=`/_ext/home/headless`，`/home/headless` 不存在）——GTK 会警告但**不影响**后续 `gtk-theme-name`/`gtk-icon-theme-name` 设置。要消除警告可把该行改成 `include "/_ext/home/headless/.gtkrc-2.0.mine"` 或删掉。
- **Papirus 图标集（纯 SVG）静态下用不了**：无 SVG 解码器（gdk-pixbuf 只内置 PNG/JPEG）——用户本地图标集虽是 Papirus-Bunsen-bluegrey，但静态 lxtask **必须用 PNG 集（elementary-xfce）** 才能显示图标（见上）。

### 3.6、SVG 图标解码 + pixmap 引擎落地：librsvg 静态集成（2026-11-05，**推翻 3.4 的"必须用 PNG 图标集"限制**）

> 背景：3.4 结论是「静态 lxtask 只能解码 PNG/JPEG（gdk-pixbuf 只内置 png/jpeg loader），Papirus 纯 SVG 用不了，**必须用 PNG 集 elementary-xfce**」；3.5 末尾记了「Greybird 缺 pixmap 内置引擎 → `Unable to locate theme engine: "pixmap"` 警告」。本节把这两个限制**都消除**，静态 lxtask 直接用用户本地默认的 Papirus-Bunsen-bluegrey（纯 SVG）即可。

#### 3.6.1、SVG loader：gdk-pixbuf 内置 svg（librsvg 静态链入）

- 参照 fk-awesomewm 同环境（builder-awe，alpine3.15）已编译的 librsvg 静态库：`/usr/local/lib/librsvg-2.a`（2.40.21 C 版）+ `libcroco-0.6.a` + `/usr/lib/libxml2.a`，头文件 `/usr/local/include/librsvg-2.0/librsvg/`。**无需重编**。
- gdk-pixbuf（meson 构建，`/tmp/gdk-pixbuf/`）把 svg loader 编进 builtin：
  - `gdk-pixbuf/io-svg.c`：仿 `io-png.c` 的 `MODULE_ENTRY(function)` 宏，生成 `_gdk_pixbuf__svg_fill_vtable` / `_gdk_pixbuf__svg_fill_info`（`INCLUDE_svg` 时），并复制到 `/tmp/gdk-pixbuf/gdk-pixbuf/io-svg.c`。
  - `gdk-pixbuf-io.c`：加 `module(svg);` 声明 + `try_module(svg,svg)`（函数内展开）+ `load_one_builtin_module(svg)`（`gdk_pixbuf_io_init_builtin` 内）。**三处缺一不可**（`module()` 只是声明，`try_module` 才真正调用）。
  - `gdk-pixbuf/meson.build`：loaders 表加 `'svg'` 条目 + `c_args` 加 librsvg include 路径；`meson_options.txt`：`builtin_loaders` choices 加 `svg`；顶层 `meson.build`：`librsvg_dep = dependency('librsvg-2.0')` 加入 `loaders_deps`。
- 重建 `libgdk_pixbuf-2.0.a`（`/tmp/gdk-pixbuf/build/gdk-pixbuf/`，1.31MB，含 `io-svg.c.o`，`nm` 见 `_gdk_pixbuf__svg_fill_vtable` T）并替换 `/usr/local/lib/libgdk_pixbuf-2.0.a`（原版本 `.a.orig` 备份）。
- 验证：独立 `svgtest`（静态链新 gdk-pixbuf + librsvg）成功解码 32×32 SVG。

#### 3.6.2、pixmap 引擎：GTK2 `modules/engines/pixbuf` 内置进 libgtk

- pixmap 引擎源码 = GTK2 主源码树 `modules/engines/pixbuf/`（`pixbuf-main.c`，引擎名 `"pixmap"`；**不是**独立 gtk-engines 项目）。
- 符号冲突处理：`pixbuf-main.c` 的 `theme_init/theme_exit/theme_create_rc_style` 与 murrine（此前已内置）**同名**（均 `G_MODULE_EXPORT`）→ 重命名为 `pixmap_theme_init/exit/create_rc_style`，并**移除 `g_module_check_init`**（builtin 不需要，保留会导致链接重定义失败）。
- `gtk/gtkthemes.c`：`builtin_theme_engines[]` 数组加 `{ "pixmap", pixmap_theme_init, pixmap_theme_exit, pixmap_theme_create_rc_style }`（外加 extern 声明）。
- 重编 `gtkthemes.o` + 重打 `libgtk-x11-2.0.a`（`/tmp/gtk/gtk/.libs/`，36.1MB，含新 gtkthemes.o + `pixmap-*.o`；系统 `/usr/lib/libgtk-x11-2.0.a` 仍是**旧版**，链接时必须用 `-L/tmp/gtk/gtk/.libs` 优先）。

#### 3.6.3、链接命令（lxtask / icon_demo 共用，已验证）


- `pkg-config --static --libs gtk+-2.0` 输出含 `-lwebp -lzstd`，但系统无对应静态库（且 gdk-pixbuf builtin 不含 webp/zstd loader）→ **sed 剔除**，否则 `cannot find -lwebp`。
- `-lXfixes -lXrandr -lXcomposite -lXdamage -lXinerama`：GTK 的 `.pc` 未声明这些，但 gdk-x11 静态需要（gdkscreen-x11 / gdkwindow-x11 引用 XRR/XComposite/XDamage 符号）。
- 顺序：pkg-config 的 `--static` 输出保证静态依赖顺序（动态版 GTK_LIBS 顺序**不对**，cairo 需 Xrender/pixman 在其后）。

#### 3.6.7、优化：消除全部 GModule-CRITICAL 运行时警告（2026-11-05）

- **现象**：v2/v3 静态 GTK 程序 `gtk_init` 时 stderr 必报 `GModule-CRITICAL: g_module_symbol: assertion 'module != NULL' failed` + `g_module_close: assertion 'module != NULL' failed`（各 1 次）。
- **根因（源码核证，非推测）**：`gtk_init` 早期 `gtk_pre_parse_init()`（`gtk/gtkmain.c:676`）无条件调 `_gtk_module_has_mixed_deps(NULL)`；该函数（`gtkmain.c:636`）当 `module_to_check==NULL` 时执行 `module = g_module_open(NULL, 0)`（dlopen 主程序），**在静态 musl 下返回 NULL**，随后未判空仍调 `g_module_symbol(module,...)` 和（`module_to_check==NULL` 时）`g_module_close(module)` → 两个断言。与 pixmap 引擎无关（v2 无内置 pixmap 也报）。
- **修复（两处，最小侵入）**：
  1. `gtk/gtkmain.c` `_gtk_module_has_mixed_deps()`：`g_module_open` 后加 `if (!module) return FALSE;`（失败视为无混合依赖，正常继续）。
  2. `gtk/gtkmodules.c` `find_module()`：`if (_gtk_module_has_mixed_deps (module))` 加判空 `if (module && ...)`（防御 g_module_open 失败传 NULL）。
- **重编**：`gtkmodules.o`（需 `-DGTK_BINARY_VERSION=\"2.10.0\" -DGTK_LIBDIR=\"/usr/local/lib\" -DGTK_HOST=\"x86_64-pc-linux-musl\"`，这些宏由 automake `DEFS` 传、非 config.h）+ `gtkmain.o`，`ar r` 替换进 `/tmp/gtk/gtk/.libs/libgtk-x11-2.0.a`（36.0MB）。
- **重链**：lxtask（13.64MB）/ icon_demo（13.53MB）均用 3.6.3 链接命令。
- **验证（runtime 容器，Greybird + Papirus）**：
  - `icon_demo_v3` stderr：**仅** `[ic] svg ... OK`（5 个 SVG 全 OK），**无 GModule-CRITICAL**。
  - `lxtask_v3` stderr：**完全为空**（无 GModule-CRITICAL、无 unknown engine、无任何警告），窗口 600×400 正常。
- **对 3.3.5.1（`:630`）与 3.3.8（`:707`）的「GModule-CRITICAL 良性、暂不动」的修订**：该警告已消除，不再视为良性噪音。

### 3.7、构建与验证避坑清单（2026-11-05，汇总实战教训）

> 本节汇总整个 lxtask 静态化过程的技巧/避坑点，供后续维护与其它 GTK2 静态应用参考。

- **A. 网络与源码**
  - 1、**github 直连时通时断**（数据流中断）→ 统一 `export GITHUB=https://ghfast.top/https://github.com`；ghfast.top 仅 `git clone`/`ls-remote` 可用（codeload/raw 端点 403/404），须用正确仓库名（不存在仓库返回 401/404 假象）。
  - 2、**murrine 正确源码仓库 = `jlindgren90/murrine`**（GTK2 引擎源码，~30 contributors）；`shimmerproject/murrine` 是打包 spec 非源码，勿用。
- **B. 构建脚本坑**
  - 3、**murrine 合并路径**：autotools 静态产物在**根目录** `/tmp/murrine/*.o`（`.libs/` 仅 `.a/.la`）→ 用 `/tmp/murrine/.libs/*.o` 会 glob 不匹配、murrine 静默漏合并 → lxtask 链接报 `undefined theme_init`。必须 `/tmp/murrine/*.o`。
  - 4、**`DONE_RC=0` 是假象**：oneBuild 包装吞子命令非零退出（日志 `err 0, pass`）→ 判成功必须 grep 无 `FAILED`/`undefined reference`，不能只看返回码。
  - 5、**gtkmain.o/gtkmodules.o 重编宏**：需 `-DGTK_BINARY_VERSION="2.10.0" -DGTK_LIBDIR="/usr/local/lib" -DGTK_HOST="x86_64-pc-linux-musl"`（automake DEFS 传、非 config.h），否则符号/行为不符。
  - 6、**gdk-pixbuf svg loader 三处缺一不可**：`module(svg)` 声明 + `try_module(svg,svg)` + `load_one_builtin_module(svg)`（`module()` 只是声明，`try_module` 才真正调用）。
  - 7、**pixmap/murrine 符号同名冲突**：pixbuf-main.c 的 `theme_init/exit/create_rc_style` 与 murrine 同名（均 G_MODULE_EXPORT）→ 重命名 `pixmap_theme_*` 并**移除 `g_module_check_init`**（builtin 不需要，保留致链接重定义失败）。
- **C. 静态 GTK2 链接命令坑**
  - 8、**`-L/tmp/gtk/gtk/.libs` 必须优先**于 `/usr/lib`（`/usr/lib/libgtk-x11-2.0.a` 是旧版，无 pixmap 引擎）。
  - 9、**`pkg-config --static --libs gtk+-2.0` 含 `-lwebp -lzstd`**，系统无对应静态库 → `sed 's/-lwebp//g; s/-lzstd//g'` 剔除。
  - 10、**需补 `-lXfixes -lXrandr -lXcomposite -lXdamage -lXinerama`**（gdk-x11 静态额外依赖，`.pc` 未声明）；lxtask 另需 **`-lXcursor`**（gdkcursor-x11.o）、**`-lrsvg-2 -lcroco-0.6`**（svg loader 链入后 librsvg 依赖）。
  - 11、**静态顺序用 pkg-config `--static` 输出**（GTK_LIBS 动态版顺序对静态不对，cairo 需 Xrender/pixman 在其后）。
- **D. 路径/主题查找（非解码层）**
  - 12、**图标主题路径由 glib `g_get_system_data_dirs()` 决定，非 GTK prefix** → 改 GTK `--prefix` 对图标无效；运行时 `XDG_DATA_DIRS` 可完全覆盖默认路径。
  - 13、默认 dirs = `/usr/local/share` 优先 + `/usr/share` → 组件隔离占 `/usr/local` 会盖过真实图标集；`GTK_DATA_PREFIX` 只影响 GTK 自身数据路径（gtkrc/引擎/模块），**不影响图标**。
  - 14、主题名来自 `gtk-icon-theme-name`（`gtksettings.c:322`），无 settings.ini 回退 `hicolor`；`index.theme` 是主题识别必需。
- **E. dlopen 在静态+musl 下结构不可能**
  - 15、musl `libc.a` 的 dlopen 是弱桩（返回 "Dynamic loading not supported"）；静态二进制无 `.dynsym`/dynamic section → dlopen 的 .so 其 DT_NEEDED 磁盘不存在、首步即败；跨 libc（musl→glibc .so）FS/GS 线程指针+全局态冲突必崩。**正确路线 = 消除 dlopen 依赖**（内置 loader/engine）。
- **F. 容器/截图踩坑**
  - 16、`pkill -f "Xvnc :N"` 匹配自身命令行→自杀；用 pgrep/kill 按 PID。
  - 17、`xdpyinfo` 不可靠，用 `xwininfo -root`；Xvnc 启动慢需轮询；`docker exec` stdout 常被吞→重定向日志文件。
  - 18、无 WM 下 GtkWindow 高度偏大，截图裁剪内容区；headless 用户启动 Xvnc 卡住（无 socket）→ 用 root 启动 + headless 连接（`-ac` 禁访问控制）。
  - 19、headless 不能写容器 `/tmp`（Permission denied）→ 日志/截图写 headless HOME；`docker cp` 跨容器不支持 → 先 cp 到 host 再进目标容器，host `/tmp` headless 不可写 → 用项目目录中转。
- **G. 产包核验**
  - 20、静态产包是 **stripped**（xx-clang `-Wl,--strip-all`）→ `nm` 不可用，用 **`strings`** 查符号：`theme_init`（murrine）、`Pixbuf theme: Cannot load pixmap file`（pixmap 引擎）、`gdk_pixbuf_loader_*`/`RSVG_*`（svg loader）。
  - 21、运行验证：grep stderr 无 `unknown engine|pixmap|CRITICAL|GModule|Unable to locate`（应完全为空）。

### 4.1、GTK_DATA_PREFIX 免设与 glib/GTK2 编译的关系（说人话版，2026-11-06）

> 本节把 §3.3.7「主题路径/图标路径与 GTK prefix / glib 的关系」用最直白的话重讲一遍，
> 消除「一会说跟 glib 有关、一会说跟 gtk2 编译有关」的歧义。

**一句话：主题/引擎 归 GTK2 编译管；图标 归 glib 管。两码事，不矛盾。**

| 数据 | 谁管 | 决定因素 | 改什么能免设 |
|---|---|---|---|
| 主题 gtkrc / 引擎 / 模块 | **GTK2 编译** | 编译期 `--prefix`（= `GTK_DATA_PREFIX` 宏，现在 `/usr/local`） | GTK2 重编加 `--prefix=/usr` |
| 图标主题 | **glib** | `g_get_system_data_dirs()`（默认 `/usr/local/share` + `/usr/share`） | 不用改——本来就把 `/usr/share` 排在搜索里 |

- 「跟 gtk2 编译有关」说的是**主题**；「跟 glib 有关」说的是**图标**。前面 §3.3.7 / §3.4.1
  把两者揉在一起讲，容易误读成前后矛盾。

**要「免设、直接用系统 `/usr`」**：
1. **主题**：GTK2 编译加 `--prefix=/usr`（重编 GTK2 + 所有 gtk2 应用重链）→ 主题根变
   `/usr/share/themes`，免设。
2. **图标**：跟 GTK2 编译**无关**，glib 默认就扫 `/usr/share/icons`。图标放 `/usr/share`
   （或 `/usr/local/share`）就免设——**不用改 glib、不用改 GTK2**。

> 结论：**GTK2 编成 `--prefix=/usr`，主题放 `/usr/share/themes`、图标放 `/usr/share/icons`
> （发行版标准位），就全免设，一个环境变量都不用设。**

**为什么 ubt22 上免设就通**（2026-11-06 复核）：`/usr/local/share/themes` **不存在**，
`/usr/share/themes/Greybird/gtk-2.0/gtkrc` **存在**、`/usr/share/icons/Papirus*` **存在** →
主题/图标都落到 `/usr/share`，只设 `DISPLAY+HOME` 就出 Greybird+Papirus。

**订正**：§3.4.1 说「必须设 `GTK_DATA_PREFIX=/usr`」是**当时容器特例**（musl/box，主题不在
可达路径，且当时 libgtk 前缀烤死 `/usr/local/static/lxde`）——非普遍规律；11-05 的
pavucontrol §3.7 / v-sysmonitor §5 已实测订正（标准发行版免设即通）。

**跨发行版**：资源/配置文件由使用方自行准备——只要按发行版标准位放（主题 `/usr/share/themes`、
图标 `/usr/share/icons`），GTK2 编成 `--prefix=/usr`，即全免设、可移植。
