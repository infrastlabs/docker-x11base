#### 1.2、细化点清单（开工前确认，7 点）

1. **版本对齐**：librime 定版（1.x 最新 tag）；libibus（随 ibus 1.5.35）；icu 用 69.1（已装

   `ls /usr/lib/*.a` 核对；缺的自建。→ 决定 librime 是「apk 全包」还是「部分自建」。
3. **GTK2 im module 核心矛盾（最大风险）**：§5.1.4 只说了「im module 是 .so 不能静态链」，

   静态应用退化、输入走系统应用）。
4. **immodules.cache 生成**：静态 GTK 构建是否产 `gtk-query-immodules-2.0`？还是用系统 GTK 的
   `gtk-query-immodules` 生成？im module 装入 `$libdir/gtk-2.0/$gtk2_binary_version/immodules/`。
5. **ibus-rime 能否 `--disable-libnotify`**：CMakeLists 是否硬要求 libnotify；不能则需先建

6. **plum/rime-data 部署**：`--recursive` 克隆；默认输入方案（default/luna_pinyin）与
   rime 配置目录（`~/.config/ibus/rime`）。
7. **运行时 env**：`GTK_IM_MODULE=ibus QT_IM_MODULE=ibus XMODIFIERS=@im=ibus` +
   `ibus-daemon -drx` 启动（autostart/xinitrc）。

#### 1.3、开工思路（推荐顺序，6 步）

1. **apk 静态库盘点**（见细化点 2；icu-static/boost1.77-static/glog/yaml-cpp 已在索引，先装）。
2. **构建 ibus**（前置 dbus 已好 + gtk2/glib/x11/libxkbcommon）：`--disable-gtk3 --disable-gtk4

3. **im module 兼容性探针**（风险最大，**先做**）：静态 lxtask + `GTK_IM_MODULE=ibus` 在 hdmi

### 3、im module 兼容性探针（2026-11-06，hdmi Xvnc 实测——**推翻 §5.1.4 的 im module 思路**）

> 对应「细化点 3 / 开工思路 3」。用 **GtkEntry 最小静态 GTK2 程序**（`/tmp/probe-ime`，
> 13.8M 静态，`--prefix=/usr` 烤入）在 hdmi 容器 Xvnc 新 display 实测。

#### 3.1、实测结果（逐 config）

| 配置 | 结果 | 结论 |
|---|---|---|
| `GTK_IM_MODULE=ibus` | `Dynamic loading not supported` + `Loading IM context type 'ibus' failed` | **im module 方案不可行** |
| `XMODIFIERS=@im=ibus`（无 GTK_IM_MODULE） | 同上（`@im=ibus` 也把 `ibus` 当模块 dlopen） | 不可行 |
| `GTK_IM_MODULE=xim`（内置） | **rc=137，无任何警告** | ✅ **XIM 可行** |

#### 3.2、根因

- **静态 GTK2 构建不支持 dlopen 加载 im module**（`g_module_supported()` 为假 →
  `gtkimmodule.c` 报 `Dynamic loading not supported`）。§5.1.4「gtk2 im module 是 .so 不能
  静态链」只说对了一半——**是根本加载不了**（不只是不能静态链）。
- `GTK_IM_MODULE=ibus` / `@im=ibus`：`ibus` 不是内置 GType，GTK 走 module dlopen → 失败。
- `GTK_IM_MODULE=xim`：`xim` 是 **builtin**（`--with-included-immodules=xim`）→ 直接创建
  GtkIMContextXIM，无需 dlopen → 成功。

#### 3.3、修正后的方案（替代 §5.1.4 / §5.2 的 im module 思路）

- **静态 GTK2 应用用 XIM**：`GTK_IM_MODULE=xim`（builtin）+ `XMODIFIERS=@im=ibus` +
  `ibus-daemon`（带 XIM 支持）运行 → 应用经 XIM 协议连 ibus，ibus-rime 出中文。
- **im module `.so` 不再需要**（对静态应用）：§5.1.4 的「装 immodules.cache + .so」**废弃**；
  静态 GTK 的模块路径（`/usr/lib/gtk-2.0/<ver>/`）与 Ubuntu multiarch（`/usr/lib/x86_64-linux-gnu/
  gtk-2.0/`）不一致的问题也因此无关。
- **ibus / ibus-rime 仍需构建**：提供 `ibus-daemon`（XIM server）+ `ibus-engine-rime`；只是
  静态应用的接入从「im module」改成「XIM」。
- **待验证（Xvnc 实打）**：`ibus-daemon -drx` 起后，`GTK_IM_MODULE=xim XMODIFIERS=@im=ibus`
  下 `ibus engine rime` 能否在 GtkEntry 上屏中文——这是下一步验证点（需 ibus-rime 构建完成后）。

### 4、第 2 步：ibus 1.5.35 静态构建完成（2026-11-06）

> 执行「开工思路 2」。在 **builder-obox**（Alpine 3.15，`alpine-builder-gtk224`）实测，全部
> `xx-verify --static` 通过。前置：dbus/dbus-glib 已就位（§二）、glib/gio/gobject 2.70.5 静态
> `.a`（apk）、gdk-pixbuf 静态（librsvg-2.a 在 `/usr/local/lib`，自建）。

#### 4.1、configure 参数（实测确定）

```
--disable-gtk2 --disable-gtk3 --disable-gtk4 \
--disable-libnotify --disable-introspection --disable-vala \
--disable-appindicator --disable-systemd-services --disable-dconf --disable-wayland \
--disable-emoji-dict --disable-unicode-dict \
--enable-xim \
--prefix=/usr/local/static/ibus
```

- **必须 `apk add iso-codes iso-codes-dev`**：ibus 的 `PKG_CHECK_MODULES(ISOCODES,[iso-codes])`
  是**无条件必需**（configure.ac L870-875），无 disable 开关；`ISOCODES_PREFIX` 用于
  `ibusutil.c` 取 iso_639.xml。Alpine 的 `iso-codes` 是纯数据包，需 `iso-codes-dev` 才带 `.pc`。
- **关闭项**：gtk2/3/4 im module（静态应用走 XIM，im module 无用）、libnotify（无 `.a`）、
  introspection/vala（不产 gir/vala 绑定）、emoji/unicode dict（省 Unicode 数据下载）。
- **xim 必须保留**（`--enable-xim`）：`ibus-x11` XIM server 是静态 GTK2 应用接 ibus 的通道。

#### 4.2、静态链接的坑（逐一解决，全链式）

| 现象 | 根因 | 解决 |
|---|---|---|
| `pcre_*`/`inflate*`/`mnt_*`/`g_module_*`/`g_scanner_*` undefined | `--static` 下 glib/gio 的**传递静态依赖**（pcre/z/mount/blkid/ffi/gmodule）不在链上 | `make LIBS="$(pkg-config --static --libs gio-2.0)"` |
| `ffi_type_*` undefined | `--start-group` + `--as-needed` 冲突，`-lffi` 被丢弃 | **去掉 LDFLAGS 里的 `--as-needed`**，只留 `--static -static -Wl,--strip-all`；LIBS 用 `--start-group ... --end-group` |
| `jpeg_*`/`png`/`zstd`/`lzma`/`tiff`/`webp` undefined | `ibus-x11`（XIM server）链 gdk-pixbuf，需要完整 gtk2 静态依赖 | LIBS 追加 `$(pkg-config --static --libs gtk+-2.0)`；`apk add zstd-static` |
| `XRR*`/`XComposite*`/`XDamage*`/`Xinerama*`/`Xcursor*` | gdk-x11 需要 X 扩展静态库 | 追加 `-lXrandr -lXcomposite -lXdamage -lXfixes -lXi -lXinerama -lXcursor -lXrender` |
| `xcb_*`（take_socket/poll_for_event…） | libX11→libxcb 传递，被 `--as-needed` 丢 | 去掉 `--as-needed` 后 `--start-group` 重扫解决 |
| `rsvg_*`/`lzma_*`/`pixman_*`/`FT_*`/`Brotli*` | gdk-pixbuf→librsvg→libxml2/cairo/freetype 传递 | 追加 `-lrsvg-2 -lcroco-0.6 -lxml2 -llzma -lz -lpixman-1 -lfreetype -lbz2 -lpng16 -lharfbuzz -lgraphite2 -lbrotlidec -lbrotlicommon`（顺序：xml2 后跟 lzma/z） |
| `g_variant_builder_init_static` undefined（**仅 portal/**） | `portal`（flatpak portal backend）需 **glib ≥2.74**，Alpine 3.15 只有 2.70.5 | **不建 portal**（XIM 用不到）；`make -C <dir>` 逐个装，跳过 `portal`、`tools`（vala `Posix.Limits` 版本坑，仅 `ibus` CLI） |

> **最终 LIBS 全集**（`--start-group` 包裹）：
> `$(pkg-config --static --libs gio-2.0) $(pkg-config --static --libs gtk+-2.0)`
> `-lrsvg-2 -lcroco-0.6 -lcairo -lXrandr -lXcomposite -lXdamage -lXfixes -lXi -lXinerama`
> `-lXcursor -lXrender -lX11 -lxcb -lxcb-shm -lxcb-render -lxcb-randr -lXau -lXdmcp -lXext`
> `-lpcre -lxml2 -llzma -lz -lpixman-1 -lfreetype -lbz2 -lpng16 -lharfbuzz -lgraphite2`
> `-lbrotlidec -lbrotlicommon`

#### 8.1、架构事实（已从 ibus 1.5.35 源码核实）

- **面板是独立进程**，与客户端用何 toolkit 无关：面板注册 D-Bus 服务
  `org.freedesktop.IBus.Panel`（对象路径 `/org/freedesktop/IBus/Panel`，接口
  `IBUS_INTERFACE_PANEL`），daemon 用 `GDBusProxy`（`bus/panelproxy.c`）连接并调用其方法。
- **候选词渲染入口**：`IBusPanelService::update_lookup_table(table, visible)`（daemon→panel）。
  其余虚函数：`set_cursor_location(x,y,w,h)`、`update_preedit_text`、`update_auxiliary_text`、
  `show/hide_lookup_table`、`cursor_up/down_lookup_table`、`page_up/down_lookup_table`、
  `focus_in/out`、`destroy_context`（见 `src/ibuspanelservice.h`）。
- **面板注册流程**（照抄 GTK3 面板 `ui/gtk3/application.vala`：`bus.request_name(IBus.SERVICE_PANEL)`）：
  `ibus_bus_new()` → `ibus_bus_get_connection(bus)` → `ibus_panel_service_new(conn)`
  （`src/ibuspanelservice.c`：自动注册对象路径 `IBUS_PATH_PANEL`）→
  `ibus_bus_request_name(bus, IBUS_SERVICE_PANEL, 0)`。
- **daemon 拉起面板**：`ibus-daemon --panel=<cmdline>`（`bus/main.c:80` 选项，
  `main.c:315-317` 走 `execute_cmdline`）。默认面板从注册表组件查 `IBUS_SERVICE_PANEL`
  （已禁 gtk3，无默认面板，故需 `--panel=` 显式指定）。
- **候选位置来源**：`ibus-x11` 在 `client/x11/main.c:873` 调
  `ibus_input_context_set_cursor_location`；坐标来自 XIM `XNSpotLocation`

- **候选键选择不经面板**：按键走 XIM→ibus-x11→daemon→引擎 `ProcessKeyEvent`

#### 9.1、方案 D 细化（ibus-x11 内直接渲染候选弹窗）

**实现思路**

**架构**：把候选弹窗渲染直接放进 `ibus-x11` 进程（不再需要独立 panel + daemon 面板
D-Bus 链路）。ibus-x11 的每个 XIM 输入上下文（`x11ic->context`，`main.c:357`）本身就是
引擎的代理，**已连**这些信号：`commit-text`/`forward-key-event`/`update-preedit-text`/
`show|hide-preedit-text`/`enabled`/`disabled`（`main.c:364-377`）。**缺**：
`update-lookup-table`、`show|hide-lookup-table`、`update-auxiliary-text`、
`show|hide-auxiliary-text`、`update-property`、`property-activate`。方案 D 就是补连这些
信号，用 GTK2 画弹窗。

**可行性已核实**：
- ibus-x11 已静态（10.8MB），且**已链 GDK2**（`IA__gdk_x11_*` 符号在）。要加 `GtkWidget`
  只需 `gdk_init`→`gtk_init`（或后加）并补链 `libgtk-x11-2.0.a`（已具备，`/tmp/gtk/`）。
- 主循环是 `ibus_main()`（`main.c:1466`），GTK 的 GSource 会进该 GMainLoop，无需新循环。
- 候选位置复用现有 `_xim_set_cursor_location`（`main.c:839-877`，已把 XIM spot 经
  `XTranslateCoordinates` 转根坐标，兜底 `(0,xwa.height)`）→ 弹窗 `gtk_window_move(x, y+h)`。
- `libibus-1.0.a` 已有全部 lookup-table getter（候选/标签/光标/页/方向/round）。

**渲染组件（GTK2）**：
- 候选窗口：`GtkWindow(GTK_WINDOW_POPUP)` + `GtkVBox`+`GtkLabel` 列表；
  `get_candidate(i)`→`ibus_text_get_text`；`get_label(i)` 前缀（"1."、"a." 等）；
  `get_cursor_in_page` 高亮（`gtk_widget_modify_bg`）；`get_orientation` 横/竖；
  `get_page_size` 分页；`is_round` 循环。
- Aux 窗口：`update-auxiliary-text`/`show|hide-auxiliary-text` → 小窗口（rime「中/英」模式）。
- Property 窗口：`update-property` → 属性菜单/窗口；`property-activate` 回引擎
  （input context 有对应信号）。
- Preedit 弹窗：**XIM 默认 onspot，preedit 在应用内已画**，面板可不画；仅当需 overspot
  才补（可选）。
- 候选鼠标点击：`ibus_input_context_candidate_clicked()` 回引擎（键选词走 XIM→引擎，
  不经面板，已实测空格上屏）。
- 单例弹窗：多个 XIM IC 共享一个弹窗；`focus_in/out` 切换信号源、显示/隐藏。

**完整功能/显示效果对比（vs 原版 GTK3 panel）**

| 原版功能 | 方案 D 可达性 |
|---|---|
| 候选词弹窗（高亮/标签/分页/横竖/round） | ✅ 完全可达 |
| Auxiliary 文本（中/英模式） | ✅ 可达 |

**核心结论**：中文输入核心（候选弹窗 + aux + property）**完全可达**；**唯一大缺口是
语言栏/托盘 + 引擎切换**——但它依赖系统托盘（静态 GTK2 应用环境一般无托盘），且属桌面
集成职责，非输入核心。若要求**语言栏也达到原版**，方案 D 无法满足，需改用方案 A
（独立 GTK2 panel，可注册 `IBUS_SERVICE_PANEL` 服务，未来可加语言栏）。

**风险点**

1. **改核心组件**：patch `client/x11/main.c` 后需**重编 + 重链 ibus-x11**（补链 libgtk）；
   daemon/libibus/engine 不动。
2. **GTK2 混入**：现只链 GDK2，加 GtkWidget 需 `gtk_init` + 链 libgtk；确认不与现有
   `gdk_init` 冲突（改一处即可）。
3. **多 IC 单例**：需维护"当前 focus IC"，否则弹窗乱跳/串台。
4. **位置精度**：XIM spot 缺失时落窗口左下（兜底），功能可用但不贴光标。
5. **语言栏缺口**：见上，若坚持完整语言栏则不满足。
6. **维护性**：与上游 ibus 分叉，升级需重打补丁。
7. **静态体积/依赖**：ibus-x11 由 10.8MB 增大（加 GTK2 全套静态），且需 `gtk_init`
   引入的 locale/模块初始化。

#### 9.2、方案 B 分析（daemon 换回 1.4）

**1. 是否独立进程模式？** → **是**。1.4 与 1.5.35 同构：daemon 是私有 D-Bus 总线 owner，
面板是独立进程（`ui/gtk/ibus-ui-gtk`），daemon 经 component/`--panel` 拉起。且 1.4 的
`IBusPanelService` **已用 `GDBusConnection`**（ibus-1.4 docs 证实）——1.4 已是 GDBus
架构，非 dbus-glib。

**2. 面板语言？不是 vala 吧？** → **不是 vala，是 Python**。ibus 1.4.y `ui/gtk/` 全为
`.py`：`panel.py`/`main.py`/`candidatepanel.py`/`languagebar.py`/`icon.py`/`menu.py`/
`propitem.py`/`toolitem.py`/`engineabout.py`/`notifications.py`/`handle.py`/`i18n.py` +
`ibus-ui-gtk.in`（脚本）+ `gtkpanel.xml.in.in`，**无 `.c/.cpp/.vala`**，用 GTK2
（PyGObject/gi）。

**致命影响**：Python 面板需 Python 运行时 + PyGObject + GTK2 `.so` 内省 →
**打破纯静态目标**（本场景是静态 GTK2、无外部运行时）。

**3. 1.4 vs 1.5.35 功能差？**
- 面板：1.4=GTK2+Python；1.5=GTK3+Vala。
- **1.5 新增（1.4 无）**：Wayland IM v1/v2、emoji dict + emoji 面板扩展、unicode dict、
  GTK4 IM module、appindicator、systemd services、libnotify 通知（1.5.33）、preedit
  focus-mode/hint（1.5.33）、panel `set_content_type`/`set_cursor_location_relative`/
  `panel_extension`、`ibus start --type`、大量 XIM 修复、compose 表更新。
- 1.4 有：XIM、GTK2 IM module、memconf/dconf；无上述 1.5 项。

**4. 对应 ibus-rime？降到什么？** → **不需强制降级**：ibus-rime 1.6.1 用的 ibus API 在
1.4 全存在（`ibus_engine_update_preedit_text_with_mode` **2010 年加入**、1.4 docs 有；
`IBusLookupTable` 1.4 API 与 1.5.35 完全一致；engine 方法 1.4 有）。CMake 仅需 `ibus-1.0`
pkgconfig（无版本约束）→ 1.6.1 可对 ibus 1.4 重编。若实测遇 1.5-only API，才降
**ibus-rime 1.4.0（2019-01-28，1.4 系最后版，与 ibus 1.4 时代匹配）**；更早 1.2.x 太旧
（librime 0.9 依赖）。

**方案 B 结论**：独立进程✅、语言=Python（非 vala）❌、功能差如上、ibus-rime 1.6.1 可对
1.4（如需降→1.4.0）。**不推荐**：1.4 面板是 Python+PyGObject+GTK2，与"纯静态、无 GTK3、
无外部运行时"冲突；且整栈降级（daemon/libibus/x11）损失 1.5 大量修复；最终仍得自己补面板
（等价方案 A 还多降级）。

#### 9.3、结论建议

- 若接受**语言栏/托盘暂缺**（输入核心候选+aux+property 完整）→ **方案 D** 可行，
  可细化 patch 清单。
- 若要求**语言栏也达到原版** → 方案 D 不满足，应回到**方案 A**（独立 GTK2 panel）。
- 方案 B（降 1.4）**不建议**（面板是 Python，与静态目标冲突）。

#### 11.2、静态重链——libtool `--start-group` 剥落（根因）

`make` 的 libtool 链接**剥落** `-Wl,--start-group/--end-group`（展平为 .a 列表），
导致常见顺序要求的 undefined symbols（libcairo→XRender/XCB/pixman、
freetype→BZ2/Brotli/Z、gtk→gmodule、X11→xcb/Xau、Xau→Xdmcp 等）。

**绕过**：直接调用 `xx-clang -static`（不经 libtool），带完整键名。所需**额外**静态库：

- `-lpangocairo-1.0`（`pango_cairo_*`，GDK 渲染）
- `-lXcomposite -lXdamage`（GDK X11）
- `-lXcursor -lXrandr -lXfixes -lXinerama`
- `-lbz2`（freetype ftbzip2）
- **rsvg stub**：`libgdk_pixbuf-2.0.a` 含 `io-svg.c.o` 需 `rsvg_*`，但无
  `librsvg-2.0.a`。用 stub 对象提供 6 个 rsvg 符号（handle_new/write/close/

`/tmp/link_ibus_x11.sh`（已含全部键名）。

**答**：

##### 11.7.6.1、GTK_IM_MODULE=ibus 为啥不行？

因为 **ibus 这个模块和「候选窗到底谁来画」是两回事**，它把候选丢给了我们根本没有的东西：

- `GTK_IM_MODULE=ibus` → GTK 加载 ibus 的 im 模块 → 该模块**自己连 dbus 直通 ibus-daemon**，自己建一个输入上下文，**根本不经过 ibus-x11**。
- 引擎出了候选后，daemon 会把候选表交给 **panel（输入法面板）** 来显示。
- 但我们的 daemon 是用 `-p disable` 启动的（**没有 panel**），候选表没人画 → 屏幕上什么都不出。

一句话：`GTK_IM_MODULE=ibus` 走的是「im 模块 → daemon → panel」这条路，而方案 D 恰恰没有 panel。所以这条路是死路。

##### 11.7.6.2、ibus-x11 的作用是干嘛？

**它是 XIM 服务器（X Input Method Server），是「老式 XIM 协议」和 IBus 之间的桥。**

- 在 X 显示上注册一个 XIM server。
- 走 XIM 的客户端（设了 `XMODIFIERS=@im=ibus`、`GTK_IM_MODULE=xim`）连到它。
- 它把客户端的 XIM 按键事件翻译成 IBus 按键事件发给 daemon；把 daemon 的 commit/preedit/候选表翻译回 XIM 发给客户端。
- **方案 D 的关键**：我们 patch 过的 ibus-x11 在收到候选表时，**自己用 GTK2 把候选窗画出来**（进程内弹窗），不需要 panel。

所以：`GTK_IM_MODULE=ibus` 完全绕开 ibus-x11；只有 `GTK_IM_MODULE=xim` 才会经过 ibus-x11，我们的候选窗才有机会被调用。

##### 11.7.6.3、GTK_IM_MODULE=xim 是 fcitx 用的吗？会改通用配置认知吗？有隐患吗？

**fcitx 默认不是用 xim。** fcitx 用 `GTK_IM_MODULE=fcitx`（它自己的 GTK 模块），xim 只是它的**兜底**。所以别把 xim 当成 fcitx 的标配。

**它确实改变了通用配置认知——这是实打实的偏离。** 现代主流是 `GTK_IM_MODULE=ibus/fcitx`（直接连各自的 daemon），xim 是**遗留（legacy）通用协议**。把它设成默认，等于让所有 GTK 应用走 XIM，这是「降级到老路」。

**隐患（要如实告诉你）：**
- **单点故障**：所有输入都依赖 ibus-x11 这个进程；它崩了/没起来，整个输入就断了（im 模块那套有重连逻辑，XIM 没有）。
- **XIM 是弃用协议**：GTK3/GTK4、部分新工具对 XIM 支持弱或有 bug（光标定位、内嵌 preedit、候选选字都有坑）。
- **Qt 应用不吃这套**：Qt 看 `QT_IM_MODULE`，不看 `GTK_IM_MODULE`。所以 Qt 应用还得单独配。
- **各应用对 XIM 处理不一致**：老 GTK2 应用普遍没问题，但个别应用有 XIM 专属 bug。

##### 11.7.6.4、要保持原有 ibus 设定（GTK_IM_MODULE=ibus），可以怎么调？

有两条正路，都是**把「画候选」这件事从 panel 搬到别处**：

- **方案 A（改 im 模块）**：构建并 patch 我们自己的 GTK2 im 模块 `im-ibus.so`，让它在收到候选表时**像 ibus-x11 一样自己弹 GTK2 候选窗**。这样 `GTK_IM_MODULE=ibus` 就能用。**但注意：我们现在的静态 ibus 根本没构建这个 im 模块**（libexec 里只有 `ibus-engine-simple`、`ibus-x11`），得先把它建出来再 patch，工作量不小。
- **方案 B（自己写 GTK2 panel）**：写一个极简 GTK2 面板组件，实现 `org.freedesktop.IBus.Panel` 协议，daemon 不再 `-p disable` 而是用它。这条路 `GTK_IM_MODULE=ibus` 保持不动，但要自己实现 panel 协议，也不省事。

**我的建议（务实）**：我们桌面基本是 **GTK2 应用**（pcmanfm/geany/engrampa/lxtask…），GTK2 对 XIM 支持成熟，出问题概率低。所以：
- **短期**：用 `GTK_IM_MODULE=xim` 先把方案 D 验证通、能用（现在候选窗已经出来了）。
- **长期（如果要回到标准配置）**：优先做**方案 A**（patch im-ibus.so），它改动最小、还能保留 `GTK_IM_MODULE=ibus` 的通用习惯。

#### 11.7.9、问答复核：A2 桥接确认 + 系统应用 im 模块依赖 / 跨发行版可行性（2026-11-07 00:47）

**问（用户）**：上面的答复也写到记录文档。我理解下：意思就是都是通过 panel 模式了，新的方案

**① 你对 A2 的理解——正确。** 修正后的方案 A = 把 ibus 的 im 模块**静态注册进我们的 libgtk**，
让静态 musl GTK2 应用也能走 ibus；它和系统 im 模块的角色**完全一样**（连 daemon、把候选转发给
panel），只是「dlopen 加载」换成「静态注册」。所以 A2（GTK2 库侧做桥 → 方案 B 的 panel）这个
说法成立：**所有客户端最终都汇聚到 panel 显示候选**。

**② im-ibus.so/ibus.so 对系统（apt）应用是否必须、是否 dlopen？——必须，且是 GTK dlopen 的。**

时它加载 `im-ibus.so`（GTK2）/`ibus.so`（GTK3）/gtk4 im。应用本身不直接 dlopen，是 GTK 框架 dlopen。

**③ Q1：系统是否还得装 apt ibus？两套 ibus 冲突？静态意义何在？**
- 系统 im 模块（`im-ibus.so`）来自 **`ibus-gtk`/`ibus-gtk3`/`ibus-gtk4`** 小包 + 运行时库
  `libibus-1.0-5`。它**只是客户端**（连 daemon、转发候选），**不包含 ibus-daemon**。
- 所以：**系统可以装 apt 的 im 模块小包，但不跑 apt 的 ibus-daemon**；我们的静态 ibus-daemon
  独占 `org.freedesktop.IBus`，系统 im 模块连到**我们的** daemon。**只要不启动 apt 的 daemon
  （禁 systemd 服务/autostart），就没有两套 daemon 冲突。**
- **静态意义**：我们的 ibus-daemon + panel（+ 静态 im 模块给静态应用）**自包含、可跨发行版移植**，
  不依赖 apt ibus-daemon；系统应用只是借用 distro 自己的 im 模块客户端 .so。**这不是「两套 ibus」，
  而是「一个 daemon（我们的）+ 一堆客户端 im 模块（distro 的）」。**

**④ Q2：静态版 ibus 自己提供这个动态库？能否零外部依赖？跨 musl/glibc、跨版本？**
- **不能，也不该。** 理由：
  1. im 模块 .so 装入系统应用，必须和该应用的 **gtk/glib/ibus ABI 一致**。若把自己那份 gtk 静态
     塞进 .so → 和宿主 gtk **符号冲突**（同进程两份 gtk）；若链系统共享 gtk/ibus → 那和 distro 自带
     的 im 模块**没区别**，自建无意义。
  2. **跨 libc 不可能**：.so 要么 glibc、要么 musl，一个文件不能同时兼容两者。
  3. **跨版本不可能**：glibc 符号版本化（`GLIBC_2.x`）+ gtk/ibus ABI 随发行版而变，一份 .so 无法
     覆盖「旧到新所有发行版」。
- **结论**：**系统应用的 im 模块必须来自 distro 本身**（它负责匹配自家 gtk/glib/ibus ABI）。
  我们**不提供**跨发行版 im .so。**可移植/静态的部分 = 我们的 daemon + panel + 静态 im 模块
  （给静态应用）**；系统应用侧靠 distro 的 im 模块，正好各司其职。

**③ Q1：apt 还得装 ibus？两套冲突？静态意义？**
- 系统 im 模块来自 **`ibus-gtk`/`ibus-gtk3`/`ibus-gtk4`** 小包 + `libibus-1.0-5`，它**只是客户端**，**不含 daemon**。
- 所以：**装 im 模块小包，但不跑 apt 的 ibus-daemon**；我们的静态 daemon 独占 `org.freedesktop.IBus`，系统 im 模块连到**我们的** daemon。只要禁掉 apt daemon 的自启，**就没有两套 daemon 冲突**。
- **静态意义**：我们的 daemon + panel +（静态应用用的静态 im 模块）**自包含、可跨发行版移植**，不靠 apt ibus-daemon。这不是「两套 ibus」，而是「**一个 daemon（我们的）+ 一堆 im 模块客户端（distro 的）**」。

**④ Q2：静态版自己提供这个动态库？零依赖？跨 musl/glibc、跨版本？**
**不能，也不该。** 三个硬理由：
1. im 模块 .so 必须和宿主应用的 **gtk/glib/ibus ABI 一致**；把自家 gtk 静态塞进去 → 同进程两份 gtk **符号冲突**；链系统共享 gtk → 跟 distro 自带的一样，自建没意义。
2. **跨 libc 不可能**：一个 .so 要么 glibc 要么 musl，不能同时兼容两者。
3. **跨版本不可能**：glibc 符号版本化（`GLIBC_2.x`）+ gtk/ibus ABI 随发行版而变，一份 .so 盖不住「旧到新」。

**所以：系统应用的 im 模块必须来自 distro 本身**（它负责匹配自家 ABI）。我们**不提供**跨发行版 im .so。**可移植/静态的部分 = 我们的 daemon + panel + 静态 im 模块（给静态应用）**，系统应用侧靠 distro 自己的 im 模块——正好各司其职。

**定案（用户已确认）**：方案 **A2（静态 im 模块，给静态应用）+ B（panel，给所有客户端）**，daemon 用我们的。**开工顺序**：先 **B（panel）**——覆盖最多客户端（系统 GTK2/3/4 + Qt + 静态应用），用系统 zenity（`GTK_IM_MODULE=ibus`）最快验证；后 **A2**（静态 im 模块）。
