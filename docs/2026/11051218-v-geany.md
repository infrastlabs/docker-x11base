## 一、现状与决策（开工前拍板）

### 1、现状盘点

- **`compile/src/v-geany/build.sh` 是模板，未开过工**：它是从别处（pcmanfm/lxtask 式 GTK2 静态骨架）
  拷过来的模板，`git clone --depth=1 --branch=1.3.1 $GITHUB/lxde/geany` —— **仓库错**（上游是
  `geany/geany`，不是 `lxde/geany`）且 **geany 没有 1.3.1 这个 tag**。从未在容器里实跑过。
- **`vers.txt` 同错**：`geany|1.3.1|git clone --depth=1 --branch=1.3.1 $GITHUB/lxde/geany`，需一并修正。
- **builder 依赖已齐**：`builder-obox`（alpine-builder-gtk224）里 GTK2 静态链全在 ——
  `libgtk-x11-2.0.a`(8.9M)、`libgdk-x11-2.0.a`、`libgdk_pixbuf-2.0.a`(1016K)、
  atk/pango/cairo/fontconfig/X11/Xrender/Xft/freetype/fribidi/harfbuzz/xml2/pcre/jpeg/png 全部 `.a`；
  **`libstdc++.a`(20.2M)+`libsupc++.a` 也在**（Scintilla 是 C++）。
- **geany 尚无产包**：`/usr/local/static/geany` 不存在，需从零构建。
- **图标链路已打通**（lxtask 已验证，见 `260926-lxtask-解析与优化.md` 3.3.5/3.6）：
  gdk-pixbuf 的 PNG/JPEG loader 已通过 `builtin_loaders=[png,jpeg]` 烤进 `libgdk_pixbuf-2.0.a`
  （`_gdk_pixbuf__png/jpeg_fill_vtable` 符号在，无需 dlopen）；SVG loader 经 `u-gtk` patch 内置；
  murrine/pixmap 引擎已 `ar r` 进 `libgtk-x11-2.0.a`。geany 图标走同一套，不用再折腾 loader。

### 2、拍板

- **版本：geany 1.34.0**（2018-12-16，GTK2）。理由：`docs/desk/geany-1.34.0.md` 已实测过该版本
  （`gtk2`），风险最低；geany **1.38.0 起删 GTK2**（PR#2602）、2.0 起强依赖 GTK3.24，而本套
  基础设施是 GTK2，只能用 ≤1.37.1。
- **仓库：`$GITHUB/geany/geany`**（上游），勿再用 `lxde/geany`；`vers.txt` 的 `1.3.1` 一并改为 `1.34.0`。
- **代理：`ghfast.top` 已失效**，改用直连 `https://github.com` 或可用镜像（见 1.4 网络）。

### 3、四大障碍与对策（相对 pcmanfm 的增量）

1. **Scintilla 是 C++** —— `docs/desk/geany-1.34.0.md` 的死结 `undefined reference to
   'operator delete(void*)'` 就是**最终 `src/geany` 链接没用 C++ 驱动/没带 libstdc++**。对策：
   - 最终链接走 `CXX=xx-clang++`（geany 的 `geany_LINK` 应已用 CXXLINK），并**显式在 LIBS 组加
     `-lstdc++ -lsupc++`**（两个 `.a` 都在），用 `-Wl,--start-group` 包住。
2. **libgeany 是共享库** —— 构建产物是 `src/.libs/libgeany.so` + `src/geany`（链接它）。静态必须出
   `libgeany.a`：`./configure` 加 `--enable-static --disable-shared`，或 make 时让 libtool 选 `.a`。
3. **运行时数据** —— geany 依赖 `share/geany`（filedefs/snippets/tags/plugins）。
   `--prefix=$TARGETPATH` 会装到 `$TARGETPATH/share/geany`，运行 `$TARGETPATH/bin/geany` 按 exe
   相对路径能找到。**插件目录留空**（插件是 gmodule/dlopen，静态下同 lxtask 的墙，跳过即可，
   不影响核心编辑器）。
4. **可选特性裁掉** —— `--disable-vte`（VTE 是 GTK2 终端组件，非必需）+ `--disable-html-docs
   --disable-pdf-docs --disable-api-docs`（`geany-1.34.0.md` 已有）。

### 4、网络（克隆源候选）

- 容器内 `curl https://github.com` 返回 200（外网通），但 `git ls-remote github` 曾**卡死**（git 协议
  疑似被限）；`gitee g-system` 无公开 geany 镜像（`fk-geany` 需认证）。
- 候选克隆源，按优先级：
  1. 直连 `https://github.com/geany/geany`（`--branch=1.34.0`）。
  2. 镜像 `hub.nuaa.cf` / `hub.njuu.cf`（`geany-1.34.0.md` 曾用 `https://hub.njuu.cf/geany/geany`）。
  3. 其它 `ghproxy` 类代理（`ghfast.top` 已失效）。
- 开工前先实测哪条能通，再写死进 `build.sh` / `vers.txt`。

## 二、构建过程与结果

### 1、源码获取（网络实况，2026-11-05）

- **`ghfast.top` 已失效**（用户确认）；`hub.njuu.cf`/`hub.nuaa.cf` 也不通（前者 DNS 解析失败）。
- **builder 容器外网不可达**：`builder-obox` 内 DNS 能解析（`getent hosts github.com` 有 IP），但
  `git clone`/`git ls-remote`/`curl` 到 github、gh-proxy、gitee 全挂（超时或 401），**只有 host 能通**。
- **host 可通 `gh-proxy.com`**（实测 `code=200 size=5118123`，5.1M 真 tarball）。
- 落地：host 用 `curl -L https://gh-proxy.com/https://github.com/geany/geany/archive/refs/tags/1.34.0.tar.gz`
  下载 → `docker cp` 进 `builder-obox:/tmp/geany-1.34.0.tar.gz` → 解包 `/tmp/geany`（离线复用）。
- `build.sh` 已兼容：`/tmp/geany/configure.ac` 存在则复用；否则若 tarball 在则解包，最后才 git clone
  `$GITHUB/geany/geany`（正常网络环境走这条）。

### 2、配置

```sh
./configure --enable-static --disable-shared \
  --disable-vte --disable-html-docs --disable-pdf-docs --disable-api-docs \
  --prefix=$TARGETPATH
```

- **关键**：`configure.ac:27 LT_INIT([disable-static])` 默认**只出 .so**；`--enable-static` 覆盖之，
  `--disable-shared` 强制纯静态（`checking build static libraries... yes / shared... no`）。
- `--disable-vte`：VTE 是 GTK2 终端组件，非必需；`--disable-*-docs` 跳文档。
- 静态链 `LIBS0` 沿用 pcmanfm/lxtask 那套（gtk/gdk/atk/pixbuf/pango/cairo/fontconfig + rsvg/croco 供
  gdk-pixbuf 内置 svg loader 解析），**增量加 `-lstdc++ -lsupc++ -lgcc -lgcc_eh -lgthread-2.0`**。

### 3、构建（关键坑：libtool 不转发 `-static`）

- `src/Makefile.am` 的 `geany_LINK` 用 **`--tag=CC`**（`src/Makefile:243/803`），且 `make` 时把
  `-static` 放 `LDFLAGS` **被 libtool 当模式标志吞掉、不转发给驱动** → 产物仍是动态
  （实测 `ldd` 显示 `libgtk-x11-2.0.so.0`/`libstdc++.so.6` NEEDED）。
- 用 `-Wl,-static` 虽转发到驱动，但和 libtool 展开的 `libscintilla.la dependency_libs` 交互，
  产生 500+ 个 `pixman/ffi/freetype/_Unwind_Resume` undefined（顺序错乱）。
- **正解：绕过 libtool，直接静态链接**：
  ```sh
  cd /tmp/geany/src
  xx-clang++ -static -Wl,--strip-all -o $TARGETPATH/bin/geany main.o .libs/libgeany.a \
    -Wl,--start-group -lXinerama -lXfixes -lXrandr -lstdc++ -lsupc++ -lgcc -lgcc_eh -lgthread-2.0 $LIBS0 \
    -Wl,--end-group -lintl
  ```
  - 用 `xx-clang++`（C++ 驱动）→ 自动带 libstdc++（Scintilla 是 C++，主程序却用 `--tag=CC`，故
    `operator delete` 等符号缺失——`geany-1.34.0.md` 当年死结）。
  - `-lgcc -lgcc_eh` 必须：`-static` 下 `-lgcc_s` 只有 `.so`（`/usr/lib/libgcc_s.so` 是
    `GROUP(libgcc_s.so.1 -lgcc)` 脚本），需补静态 `libgcc_s.a`（copy libgcc.a，build.sh 已做）。
- **产物**：14.3M，`ELF 64-bit LSB executable, statically linked, stripped`；`xx-verify --static` rc=0；
  `ldd` → `Not a valid dynamic program`；`readelf -d` → 0 NEEDED；日志 `undefined reference`/`attempted
  static link` = 0。
- `make install` 装数据（`share/geany`：filedefs/snippets/tags/templates/colorschemes/geany.gtkrc）
  后再用上面命令**覆盖** `bin/geany`（避免 make install 重链成动态），`xx-verify` 兜底。

### 4、运行验证（hdmi-desktop Xvnc）

- 静态 geany 拷到 `docker-hdmi-desktop-desktop-1`（app-ubuntu-22.04，glibc），Xvnc `:998`：
  - **`geany ALIVE after 5s`**（未崩溃，跨 libc 静态可用）。
  - 窗口创建：`0x200003 "Error"`(297x128) + 主窗 `0x200001 "geany"`。
  - 日志：`GModule-CRITICAL`（g_module_symbol/close `module != NULL`）+ `Gtk-WARNING: Unable to locate
    theme engine in module_path: "pixmap"/"murrine"` —— 均**非致命**，与 lxtask 的 dlopen 墙同源。
- 结论：**geany 1.34.0 静态构建成功，跨发行版可运行**。

## 三、FAQ 问与答（2026-11-05 追加）

### 1、插件目录留空，有哪些影响？APT 版本默认加载哪些插件？

- **APT（Ubuntu 22.04 hdmi）geany 1.38 实测**：只装了 `geany` + `geany-common`，**没装 geany-plugins**。
  默认插件目录 `/usr/lib/x86_64-linux-gnu/geany/` 就 **6 个核心内置插件**（随 geany 主包）：
  `classbuilder.so`（类骨架）、`export.so`（HTML/LaTeX 导出）、`filebrowser.so`（文件树侧栏）、
  `htmlchars.so`（HTML 实体）、`saveactions.so`（保存动作）、`splitwindow.so`（分屏）。
  > geany-plugins（拼写/终端/git/projectorganizer 等大集合）是**独立包**，hdmi 未装，不在默认加载内。
- **我们静态 geany（1.34.0）**：因 `--disable-shared`，plugins 子目录产出 **`.a`（非 `.so`）**，`make
  install` 装进 `lib/geany/`；运行期插件装载走 `g_module_open`（dlopen）→ 静态 musl 下 `.a` 打不开 →
  GModule-CRITICAL 噪音（运行日志里那几条 `module != NULL`），插件**一个都加载不了**。
- **影响**：核心编辑器 100% 可用（编辑/高亮/会话/构建/文件类型/模板/搜索）；**缺上述 6 个核心插件功能**；
  无 geany-plugins（hdmi 本就没装，无差异）。
- **处置（用户拍板）**：**`--disable-plugins` 先不处理**（`configure --help` 确认存在，默认=no）。
  反正插件 dlopen 在静态下必失败，留着 `.a` 只让 geany 空扫白忙；**后续按体验再考虑集成必要内置插件**
  （插件已是 `.a`，可走静态注册进 geany，同主题引擎 builtin 手法）。

### 2、主题引擎 pixmap/murrine 报 dlopen 找不到——不能复用新 gtk2 库直接解决吗？

- **能。u-gtk 那边已经有 pixmap 了**（订正此前"需把 pixmap 加进 builtin 表"的误判）：
  - builder-awe 的 `gtkthemes.c` builtin 表**同时注册 murrine + pixmap**：
    `{ "murrine", theme_init, ... }, { "pixmap", pixmap_theme_init, pixmap_theme_exit, pixmap_theme_create_rc_style }`
    （`gtk_theme_engine_load` 先查 builtin 再 dlopen）。
  - awe 的 `libgtk-x11-2.0.a`（9.3M，11-04）里 murrine 对象（`murrine_draw.o`/`murrine_style.o`/...）
    与 pixmap 引擎对象（`pixbuf-draw.o`/`pixbuf-main.o`/...）**都已 `ar r` 合并**，且
    `theme_init`/`theme_exit`/`theme_create_rc_style` + `pixmap_theme_*` 均为 **T（已定义）**。
- **geany 为什么还报错**：geany 在 **builder-obox** 构建，链的是 **box 的旧 `libgtk-x11-2.0.a`**
  （8.9M，2023-12-23 基镜像内置，**无 `builtin_theme_engines`、无 murrine/pixmap 对象**），不是
  awe 那份 patched 的。所以 murrine + pixmap 都落 dlopen → 都警告。
- **正解**：geany 改链 **awe 的 patched libgtk-x11-2.0.a**（拷 awe 的 `libgtk-x11-2.0.a` 等静态库到
  box，或直接在 awe 里 build geany），重链后 murrine/pixmap 主题**都不再报**。
- ⚠️ **待复核**：仓库 `u-gtk/gtkthemes-builtin-murrine.patch` 只含 `murrine`，**没有 `pixmap`** 条目；
  awe 实际源有 murrine+pixmap。即**仓库 patch 与 awe 源不一致**——要可复现，需把 repo patch 补上
  `pixmap` 条目（`{"pixmap", pixmap_theme_init, pixmap_theme_exit, pixmap_theme_create_rc_style}` +
  对应 `extern` 声明）。

> **订正（2026-11-05 复核完成）**：
> - **仓库 patch 已补 pixmap 条目**：`u-gtk/gtkthemes-builtin-murrine.patch` 现含
>   `{ "pixmap", pixmap_theme_init, pixmap_theme_exit, pixmap_theme_create_rc_style }` + 对应 `extern`，
>   hunk 计数已同步为 `@@ -57,13 +57,57 @@`；实测对 pristine `gtkthemes.c` `patch -p1` 干净 apply，
>   结果 builtin 表**同时有 murrine+pixmap**（与 awe 源一致）→ **可复现**。
> - **geany 已实际改链 awe 的 patched libgtk**：box 的 `/usr/lib/libgtk-x11-2.0.a` 已换 awe 版
>   （9.79M，含 murrine+pixmap 对象 + file/lpr 打印后端），旧 2023 版备份在 `/usr/lib/.gtk-old-2023/`；
>   重链后产物 16.6M 静态、`xx-verify` rc=0、0 NEEDED；**hdmi Xvnc :999 实跑：pixmap/murrine 警告
>   全部消失**，只剩 GModule-CRITICAL（插件 dlopen，非致命）。

### 3、打印后端 lpr/file 未定义符号——u-gtk 的 libgtk 为什么还会断链？

- **现象**：geany 静态链用 awe 的 `libgtk-x11-2.0.a` 时，`gtkprintbackend.o` 报
  `undefined reference to _gtk_print_backend_lpr_init/_exit/_create`（file 同理）。
- **根因**：`gtk2-2.24.33-lxtask-static.patch` 在 `gtkprintbackend.c` 注册了 **file/lpr 内置后端**
  （`print_backend_builtins[]` 引用 `_gtk_print_backend_{file,lpr}_*`），但 **u-gtk/build.sh 从未把
  这两个后端编出来 `ar r` 进 libgtk**——`make` 只出 `.so` 模块（且 `--disable-modules` 后不编）。
  lxtask/pcmanfm 从不拉入 `gtkprintbackend.o`（懒链接）故一直没炸；**geany 会拉入**（有打印功能）→ 断链。
- **修复（2026-11-05，u-gtk/build.sh）**：`gtk()` 在 pixmap 合并后新增 "Building print backends
  (file/lpr, static)"：手动编 `modules/printbackends/{file,lpr}/gtkprintbackend{file,lpr}.c` 为 `.o`，
  `objcopy --redefine-sym` 把 `pb_module_init/exit/create` 重命名为 `_gtk_print_backend_{file,lpr}_*`，
  再 `ar r` 进 `libgtk-x11-2.0.a`（同 murrine/pixmap 合并模式）。这样 libgtk **自含** 打印后端，
  geany 链接命令**无需**再加 `-lstatic-printbackend`（若链旧 libgtk 缺符号需手动补）。
- **影响面**：这是 u-gtk 的**潜在坑**（不止 geany）——任何会拉入 `gtkprintbackend.o` 的静态应用都会炸。
  现在 u-gtk 产出完整 libgtk，后续组件不再踩坑。

### 4、GtkBuilder 静态 dlsym 找不到类型——geany 弹 "Cannot start" Error 对话框

- **现象**：geany 启动弹模态 "Error" 对话框（`Geany-ERROR: Cannot create user-interface: Invalid
  object type 'GtkAccelGroup'`），主窗口只剩 10×10（UI 未构建）。点 OK 后 geany 崩溃（SIGTRAP）。
- **根因**：geany 用 **GtkBuilder** 加载 `geany.glade`。GTK2 的 `gtkbuilder.c:
  _gtk_builder_resolve_type_lazily()` 用 **`g_module_open(NULL)` + `g_module_symbol`（dlsym）** 按
  `GtkAccelGroup → gtk_accel_group_get_type` 动态解析 get_type。**纯静态可执行无 `.dynsym`**
  （`-static` 下 ld 不生成动态符号表，`-rdynamic`/`--export-dynamic` 均无效），dlsym 找不到符号 →
  `g_type_from_name` 返回 INVALID → "Invalid object type" → geany Error 对话框。
  同时 `g_module_open(NULL)` 返回 NULL → `g_module_symbol(NULL)` → **GModule-CRITICAL**（同源）。
- **为什么 lxtask/pcmanfm 没炸**：它们不用 GtkBuilder 加载含 `GtkAccelGroup` 等类型的 glade（或不走到
  dlsym 缺失的类型），懒链接没拉入 `gtkaccelgroup.o`/`gtktextview.o` 时也不会报（未实例化）。
  **geany 会**（主 UI 是 glade，含 40 个 Gtk 类型）。
- **修复（2026-11-05，u-gtk 新增 `gtkbuilder-static-types.patch`）**：在 `gtkbuilder.c` 的
  `_gtk_builder_resolve_type_lazily()` 加**编译期静态类型表 fallback**（覆盖 geany.glade 的 40 个
  `Gtk*`/`AtkObject` 类型），`module==NULL` 或 dlsym 失败时查表调 `*_get_type()`。这样**纯静态下
  GtkBuilder 也能解析类型**，geany 不再弹 Error、主窗口正常；GModule-CRITICAL 一并消失。
- **注意**：静态表函数返回 **GType**（不是函数指针），resolve 里直接 `gtype = _gtk_builder_static_type_func(name)`
  （曾误当函数指针调用导致段错误，已修正）。

## 四、打印后端合并方式复盘——objcopy/ar vs 纯源码 patch（2026-11-05 追加）

> 用户指出 `1ab64ab` 的 "objcopy --redefine-sym + 手动 ar r" 合并 `.o` 进 libgtk 的方式**不正规**，
> 问能否改**对应 lib 库仓库的代码做 patch**（让 make 自然产出）。此节记录答复明细与开工决策。

### 1、现状：两处"合并 .o 进 .a"性质不同

- **gtkbuilder（d6af8ff）——已正规**：`gtkbuilder-static-types.patch` 改的是 GTK 源码
  `gtk/gtkbuilder.c`，`make -C gtk` **自然编出**含静态类型表的 `libgtk.a`。容器里"手工重编
  gtkbuilder.o + `ar r`"只是**避免重跑 GTK 全量构建**（省时），`build.sh` 已落 patch，**从零可复现**。
- **print backends（1ab64ab）——确不正规**：根因是 GTK 设计——file/lpr 后端**官方即动态模块**
  （`pb_module_init/exit/create` 为模块入口，编成 `.so`）；`--disable-modules` 后 `make` 根本不产出。
  而 lxtask-static.patch 在 `gtkprintbackend.c` 声明的是**内置后端**符号 `_gtk_print_backend_{file,lpr}_*`，
  两者名字对不上 → 只能 objcopy 改名 + 手动编 + `ar` 塞进 libgtk.a。

### 2、现有 objcopy/ar 实现明细（1ab64ab，`u-gtk/build.sh` gtk() 内）

```sh
# gtk2-2.24.33-lxtask-static.patch 在 gtkprintbackend.c 注册了 file/lpr 内置后端
# (print_backend_builtins 引用 _gtk_print_backend_{file,lpr}_*)。make 默认只出 .so 模块
# (--disable-modules 后不编) → 手动编这两个 .c 为 .o，并把 pb_module_* 重命名为
# _gtk_print_backend_{file,lpr}_* 后 ar 进 libgtk.a（同 murrine/pixmap 模式）。
# 不做这步：任何会拉入 gtkprintbackend.o 的应用（geany 等）报 undefined reference。
TOP=$(pwd)
PB_CFLAGS="-DHAVE_CONFIG_H -I$TOP -I$TOP/gtk -I$TOP/gdk -DGTK_PRINT_BACKEND_ENABLE_UNSUPPORTED"
for n in file lpr; do
  ( cd modules/printbackends/$n && \
    xx-clang $PB_CFLAGS $(pkg-config --cflags gtk+-2.0) -c gtkprintbackend$n.c -o /tmp/gpb-$n.o ) \
    || { log "PRINTBACKEND $n build FAILED"; exit 1; }
  objcopy --redefine-sym pb_module_init=_gtk_print_backend_${n}_init \
          --redefine-sym pb_module_exit=_gtk_print_backend_${n}_exit \
          --redefine-sym pb_module_create=_gtk_print_backend_${n}_create /tmp/gpb-$n.o
done
ar r ./gtk/.libs/libgtk-x11-2.0.a /tmp/gpb-file.o /tmp/gpb-lpr.o
log "Merged file/lpr print backends into ./gtk/.libs/libgtk-x11-2.0.a"
```

- 符号映射（源码侧）：`file/lpr` 两文件各 3 个模块入口
  `pb_module_init/exit/create`（`GTypeModule` 标准入口）被 `objcopy --redefine-sym` 改名成
  `_gtk_print_backend_{file,lpr}_init/exit/create`（与 `gtkprintbackend.c` 的 builtin 表对齐）。
- 前提：`xx-clang`（交叉 clang）、`pkg-config --cflags gtk+-2.0`、`objcopy` 在构建容器内可用；
  两个 `.c` include `gtk/gtkprinter-private.h` + 本地 `gtkprintbackend*.h`，cairo-pdf/ps/svg 头在源内。

### 3、可改成纯 patch 的正规方案（Patch 1 + Patch 2，用户拍板开工）

- **Patch 1（源码级改名）**：改 `modules/printbackends/file/gtkprintbackendfile.c` 和
  `lpr/gtkprintbackendlpr.c`，把 `pb_module_init/exit/create` → `_gtk_print_backend_{file,lpr}_init/exit/create`
  （各 3 处 × 2 文件），**去掉 objcopy 依赖**。
- **Patch 2（构建系统）**：把这两个 `.c` 加入 `gtk/Makefile.am` 的 `libgtk_2_0_la_SOURCES`，
  使 `make -C gtk` 自动编译进 `libgtk-x11-2.0.a`，**彻底删掉 1ab64ab 的 objcopy+ar 段**。
- **可行性前提（已验证）**：`gtk/Makefile.am` 的 `INCLUDES` 有 `-I$(top_srcdir)` + `-I$(top_srcdir)/gdk`，
  `"gtk/gtkprinter-private.h"` 可解析；`gtkprintbackend*.h` 是本地头（编译器按 `.c` 所在目录找）；cairo 已在
  libgtk 链接里。但 **Patch 2 需重新 `autogen.sh` + `configure` + 全量 `make -C gtk`**（20+ 分钟），
  并重新 `xx-verify` 验证 file/lpr 符号真进库、geany 不再断链。
- **权衡**：改动量与验证成本高于现有 objcopy 方案；但用户认可"改对应 lib 库代码做 patch"更正规。
- **产出**：新增 `u-gtk/gtk2-2.24.33-printbackends-static.patch`（Patch 1+2 合一），
  `u-gtk/build.sh` 删 objcopy+ar 段、改应用此 patch。
