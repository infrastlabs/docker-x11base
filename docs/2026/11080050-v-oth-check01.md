## 一、磁盘 tab 卡顿无响应排查（2026-11-08 完成）

### 1、过程概要（现象 → 根因 → 修复 → 验证）

**现象**
- 真机验证：gnome-system-monitor 切到磁盘 tab（File Systems）时界面卡顿无响应。

**复现**
- `docker-hdmi-desktop-desktop-1`（Ubuntu 22.04，TigerVNC 1.13.1）起新 Xvnc `:560`（1280x800，
  -SecurityTypes None -localhost -ac）+ openbox + gsm（`TMPDIR=/var/tmp HOME=/root`）。
- xdotool 激活窗口 + `ctrl+Next`×3 切到磁盘 tab。
- **采样**：gsm 主线程 `state=Rl`、`wchan=0`、CPU 持续 33~41%——**忙循环（running）而非阻塞等待**
  （排除 IO 阻塞；对照 S/D 状态未出现）；`xdotool getwindowname` 超时无响应（UI 冻结）。

**排查**
- gdb 附加 `bt` 只能取到 `0xefb9de in ??`（二进制 stripped、无 CFI），无法直接定位调用栈。
- 源码定位：磁盘 tab 刷新 `cb_update_disks`（`src/disks.cpp`）→ 每个挂载点 `add_disk()` →
  `get_icon_for_device()` → `get_icon_for_path()` → **`Gio::VolumeMonitor::get_mounts()`**。
  该函数在 `cb_update_disks` 循环内**每挂载点**调用一次，每轮刷新重复枚举。
- **对照实验**：patch `get_icon_for_device` 跳过 VolumeMonitor（固定默认图标）→ 重编重链 →
  重测：主线程 `state=Sl` + `wchan=poll_schedule_timeout`（空闲事件循环），`xdotool getwindowname`
  返回正常（rc=0）——**磁盘 tab 恢复响应**。

**根因**
- gsm 静态链 gio 无 gvfs volume monitor 模块 + headless 无 dbus 会话总线 → `VolumeMonitor::get()`
  /`get_mounts()` 在每挂载点每轮刷新时重复枚举/忙处理，主线程（GTK 主循环）忙冻结 → 磁盘 tab 卡顿
  无响应。对照验证：跳过 VolumeMonitor 后 UI 恢复正常（41% CPU 忙 → 空闲等待）。

**修复（落仓）**
- 新增 `compile/src/v-sysmonitor/gsm-disk-icon-static.patch`：`get_icon_for_device` 用固定
  `drive-harddisk` 图标，绕过 `Gio::VolumeMonitor`（headless 下挂载匹配本就不命中，实际无图标损失）。
- `compile/src/v-sysmonitor/build.sh`：源码就位后统一应用该 patch（`.gsm` 缓存源码与下载分支都覆盖）。

**验证（通过）**
- 干净源码 `patch -p1 --dry-run` OK + 实际应用 OK。
- 重编 `disks.o`（-std=c++11）+ 重链（19.2M static stripped）+ 拷 hdmi 重测：主线程
  `Sl + poll_schedule_timeout`（空闲），磁盘 tab X 响应正常，不再卡顿。
- 产物：`/usr/local/static/gsm/bin/gnome-system-monitor`（19.2M，statically linked, stripped）。

**备注**
- 磁盘 tab 图标固定默认硬盘图标（headless 下 VolumeMonitor 匹配本就不命中，无功能损失）。
- 若后续需真实设备图标，可改为每轮只枚举一次 VolumeMonitor 并缓存（本轮以"消除无响应"为先）。

## 二、xfdisp-settings 分析：配置直接生效免依赖 + 屏蔽其余二进制（2026-11-08 分析）

### 1、分析处理思路

#### 1.1、xfce4-display-settings 配置直接应用（免 xfconf / xfsettingsd 依赖）

**现状机制（源码实证，4.12.4）**
- `dialogs/display-settings/xfce-randr.c`：**`xfce_randr_apply()` 只做一件事**——写 xfconf
  `displays` 通道属性 `/Schemes/Apply`（`xfconf_channel_set_string(channel, "/Schemes/Apply", scheme)`），
  **不直接调 XRandR 应用**。
- `main.c`：应用按钮 `display_setting_apply` → `xfce_randr_apply(..., display_channel)`；且启动需
  `xfconf_init` + `xfconf_channel_new("displays")`（无 xfconf daemon 会 `g_error` 退出）。
- **真正应用靠 `xfsettingsd`**：守护监听 xfconf `/Schemes/Apply`（`xfsettingsd/displays.c`）→
  调 `XRRSetScreenConfig` 等实际应用 RandR。
- → 用户真机只有 xfce4-display-settings（无 xfsettingsd 运行 / 无 xfconf daemon）→ 配置只写
  xfconf 无人应用 → **"配置后不生效"**。

**处理思路（三选一）**
- **思路 A（推荐，真"免依赖"）**：patch `xfce_randr_apply`——在写 xfconf 之外/替代，**直接用
  libXrandr 应用当前配置**（`XRRSetScreenConfig` 等；`xfce-randr.c` 已持有完整 RandR 状态
  outputs/modes/positions，可提取 set）。配置持久化改本地文件（`~/.config/xfce4/xfconf/` 或
  `~/.config/xfce4/display`），不依赖 xfconf daemon + xfsettingsd。
- **思路 B（最小改动，不"免"）**：跑静态 `xfsettingsd`（已构建，10 二进制之一）+ xfconf daemon
  → 链路补齐，配置即生效。需 xfconf/xfsettingsd 运行时依赖。
- **思路 C**：GUI 生成 xrandr 命令并调用（x-xrandr 已实现）绕开 xfsettingsd；丢 GUI 原子性、迂回。

**结论**：思路 A 最符"配置后直接应用生效，免 xfconf/xfsettingsd"，需 patch xfce-randr.c（加
直接 RandR 应用）+ 本地配置存储。

#### 1.2、xfce4settings 屏蔽其他 8 个二进制生成

**现状（build.sh `xfce4settings()`）**
- `make -C` 逐目录构建 10 个：`xfsettingsd`、`xfce4-settings-editor`、`xfce4-settings-manager`、
  `dialogs/display-settings`、`dialogs/appearance-settings`、`dialogs/keyboard-settings`、
  `dialogs/mime-settings`、`dialogs/mouse-settings`、`dialogs/accessibility-settings`。
- `link_bin` 静态链 10 个二进制 + 验证循环 10 个。
- 产物：`xfsettingsd`、`xfce4-settings-editor`、`xfce4-settings-manager`、`xfce4-display-settings`、
  `xfce4-appearance-settings`、`xfce4-keyboard-settings`、`xfce4-mime-settings`、
  `xfce4-mouse-settings`、`xfce4-accessibility-settings`、`xfce4-find-cursor`。

**屏蔽方法（只留用户指定两个：xfsettingsd + xfce4-display-settings）**
1. `make -C` 循环只保留 `xfsettingsd` + `dialogs/display-settings`（删 editor/manager/各 dialog）。
2. `link_bin` 只保留 `xfsettingsd`（13 个 .o 含 displays.o）+ `xfce4-display-settings`
   （6 个 .o：main/display-name/edid-parse/foo-marshal/scrollarea/xfce-randr）。
3. 验证循环只验 2 个（`xx-verify --static`）。
- 改后产物：`/usr/local/static/xfce4settings/bin/` 仅 2 个二进制（xfsettingsd + xfce4-display-settings），
  其余 8 个不再构建（对应 make 目录删、link_bin 删、verify 删）。

### 2、ristretto 分析：免 xfconf 依赖（打不开→根因→处理思路）（2026-11-08 分析）

> 用户反馈：真机 headless（纯 Xvnc+openbox，无 xfconf daemon/dbus 会话总线）下 ristretto **打不开**
> （崩溃）。此前认为 ristretto 免 xfconf 依赖（未列入 xfconf 链）。本节实证（源码 0.8.5）：
> **并非免依赖**——无条件调用 libxfconf，且 `xfconf_init` 失败返回值被忽略 → 坏 channel → SIGSEGV。
> 处理思路：仿 xfdisp，`xfconf_init` 判返回值 + 全 xfconf 调用点判 `xfconf_is_initialized`/`channel` 保护。

#### 2.1、现象与复现

**现象**
- 真机 headless 下 ristretto 打开图片直接崩溃/无窗口。

**复现（hdmi 容器 Xvnc+openbox）**
- 起新 Xvnc `:563`（1280x800）+ openbox（无 dbus/xfconfd）。
- 运行：`DISPLAY=:563 DBUS_SESSION_BUS_ADDRESS=unix:path=/tmp/nonexistent-bus TMPDIR=/var/tmp HOME=/root /usr/local/static/ristretto/bin/ristretto /tmp/A.png`
- **结果**：大量 xfconf/dbus_g_proxy CRITICAL 断言 → **Segmentation fault (rc=139)**。

**对照（完整 `:1` 会话）**
- `:1` 有 openbox+dbus+xfconfd，`su headless` 跑 ristretto 开 /tmp/A.png → **正常**，窗口 1440x797 渲染出图。
- → "打不开"只在**无 xfconf daemon/dbus** 环境复现。

#### 2.2、根因（源码实证 0.8.5）

**二进制实证**
- `/usr/local/static/ristretto/bin/ristretto`（14.8M static stripped）含 **66 处 xfconf 字符串**（xfconf 静态链入，非 dlopen 弱依赖）。

**源码 xfconf 调用点（全部无条件）**
- `main.c:126` `xfconf_init(NULL);`（**返回值被忽略**）、`main.c:187` `xfconf_shutdown();`
- `settings.c:149` `settings->priv->channel = xfconf_channel_new("ristretto");`
- `settings.c:192~335` **20 处** `xfconf_g_property_bind[_gdkcolor](channel, ...)`（绑定 20 个属性）
- `xfce_wallpaper_manager.c:415` `channel = xfconf_channel_new("xfce4-desktop")`、`:423` `xfconf_channel_get_bool(...)`、`:326/334/339/719` `xfconf_channel_set_*`
- `gnome_wallpaper_manager.c` 仅 `#include <xfconf.h>`，**无 xfconf 调用**（安全）。

**失败链**
1. `xfconf_init(NULL)` 失败（无 dbus 会话总线）但**返回值被丢弃** → 代码继续。
2. `xfconf_channel_new("ristretto")` 返回**外观有效但内部 proxy=NULL 的 XfconfChannel**（因 xfconf 未初始化）。
3. 20 处 `xfconf_g_property_bind` → 内部 `dbus_g_proxy_call(proxy=NULL)` → 断言
   `dbus_g_proxy_call: assertion 'DBUS_IS_G_PROXY (proxy)' failed`、`g_propagate_error: assertion 'src != NULL' failed`。
4. 断言后继续用 NULL/坏对象 → **SIGSEGV**。

> 与 xfdisp 区别：xfdisp `g_error` **裸报错退出**（可见报错），ristretto `xfconf_init` 失败**静默继续** →
> 坏 channel → **段错误**（无明确报错，更难查）。根因同类（xfconf_init 未判返回值）。

#### 2.3、处理思路（修复方案）

**方案 A（推荐，真"免依赖" + 保留有 xfconf 时的持久化）**
- `main.c`：`xfconf_ok = xfconf_init(NULL);`（判返回值）；失败 `g_message` 警告但继续；`xfconf_shutdown()` 仅 `xfconf_ok` 时调用。
- `settings.c`：`channel = xfconf_is_initialized() ? xfconf_channel_new("ristretto") : NULL;`（`xfconf_is_initialized()` 是 libxfconf 公开 API，比判 `channel!=NULL` 更准——坏 channel 非 NULL）；20 处 `xfconf_g_property_bind` 包进 `if (channel) { ... }`（不绑定时用 `rstto_settings_init` 已设的内存默认值）。
- `xfce_wallpaper_manager.c`：`channel = xfconf_is_initialized() ? xfconf_channel_new("xfce4-desktop") : NULL;`；`:423` `get_bool` 改 `channel ? get_bool(...) : TRUE`；`:326/334/339/719` `set_*` 加 `if (channel)` 保护。
- 效果：无 xfconf daemon → 用内存默认值正常打开（免依赖）；有 xfconf → 原行为（持久化）。

**方案 B（编译期剔除）**：源码 `#ifdef XFCONF_DISABLE` 屏蔽全部 xfconf 调用。改动大（3 文件全改），且丢有 xfconf 时的持久化。不推荐。

**结论**：方案 A。与 xfdisp 的 xfconf_init 判返回值思路一致，但多了"**用 `xfconf_is_initialized()` 判 channel 有效性**"这一层（ristretto 坏 channel 非 NULL，只判 NULL 不够）。

#### 2.4、验证要点
- 重链产物 `xx-verify --static` + `file`（statically linked, stripped）。
- 裸 Xvnc（无 dbus）：ristretto 打开图片**正常出窗口**（不再段错误）；`grep -c "dbus_g_proxy\|CRITICAL"` 日志 =0。
- 完整 `:1` 会话：**仍正常**（有 xfconf 时行为不回归）；改偏好设置仍持久化（有 xfconf daemon 时）。
- 注意 xfce_wallpaper_manager 是**第二崩溃点**（默认 `desktop-type`=xfce 启动即构造），必须一并修，只修 settings.c 不够。

#### 2.5、实施结果（2026-11-08，方案 A 落仓）

**patch（`compile/src/v-xfce4/ristretto-xfconf-dbus-free.patch`，6 文件）**
- `util.h`：`extern gboolean xfconf_ok;`
- `main.c`：`xfconf_ok = xfconf_init(NULL)` 判返回值（失败 `g_message` 警告不崩）；`xfconf_shutdown` 仅 `xfconf_ok` 时调。
- `settings.c`：`xfconf_ok` 才 `xfconf_channel_new("ristretto")`；20 处 `xfconf_g_property_bind` 包 `if (channel)`（无 xfconf 用内存默认值）。
- `xfce_wallpaper_manager.c`：`xfconf_ok` 才 `channel_new("xfce4-desktop")`；`get_bool`/`set_*` 加 `if (channel)`。
- `thumbnailer.c`：`call_queue_sync`/`call_dequeue_sync` 加 `if (priv->proxy)`（无 dbus 会话总线时缩略图降级不崩）。
- `main_window.c`：`filemanager_proxy` 判空——`g_dbus_proxy_call_sync` 仅 proxy 非空；属性对话框降级内部实现。

**build.sh**
- `ristretto()`：源码就位后统一应用该 patch（`grep xfconf_ok` 防重复）。

**验证（hdmi 容器）**
- 裸 Xvnc（无 dbus）：ristretto 打开 /tmp/A.png **正常出窗**（timeout 12s RC=137 仍活），仅 WARNING 提示、无 dbus_g_proxy/GIO 断言，**不再段错误**。
- 有 dbus 无 xfconfd：**正常**（RC=137）。
- `:1` 完整会话（dbus+xfconfd）：**正常**（RC=137，无回归）。
- 产物 `xx-verify --static` OK + `file` statically linked stripped；部署 hdmi 替换（备份 `ristretto.bak-xfconf`）。

#### 2.6、真机验证反馈：hdmi 内置环境打不开——`/usr/bin/ristretto` 仍为发行版（2026-11-08 补充）

**反馈**：真机免 xfconf 可用；但 hdmi 容器自带 xvnc/openbox 环境"好像不能直接打开用"。

**排查（实证）**
- hdmi 容器有**两个 ristretto**：发行版 `/usr/bin/ristretto`（GTK3 动态，258KB，未打补丁）与静态免 xfconf `/usr/local/static/ristretto/bin/ristretto`（15MB）。
- PATH 不含 `/usr/local/static/ristretto/bin` → 裸跑 `ristretto` 走**发行版**。
- 实测发行版裸环境（无 dbus）：`xfconf-CRITICAL: xfconf_init() must be called...` + `g_dbus_proxy_call_sync_internal` 断言——**与修复前静态版同类的未修复 bug**（RC=137 仍活但功能损坏：缩略图/设置失效）。
- 静态免 xfconf 版在裸环境/`:1`/有 dbus 无 xfconfd 三态均**正常**（见 2.5）。

**根因**
- 部署只替换了 `/usr/local/static/ristretto/bin/ristretto`，**未建 `/usr/bin/ristretto` 符号链接**（openbox/lxtask 均按 `_link.sh` 模式链接到 `/usr/local/static/*/bin`，ristretto 漏了）→ 裸命令仍走发行版。

**处理（部署）**
- hdmi：`/usr/bin/ristretto -> /usr/local/static/ristretto/bin/ristretto`（发行版备份 `/usr/bin/ristretto.distro-0222`）。
- 复验：裸环境裸跑 `ristretto` → 正常出窗（RC=137），仅 WARNING，**不再有发行版 CRITICAL**。
- 后续：`_link.sh` 模式应覆盖 ristretto（部署即建链接），避免再漏。

**结论**：hdmi 内置环境"打不开"是**部署漏了 `/usr/bin/ristretto` 链接**（发行版未打补丁二进制顶替），非 xfconf 补丁问题；静态免 xfconf 版本身三态全过。

## 三、pcmanfm/thunar 右键「当前目录打开终端」分析（2026-11-08 分析）

### 1、分析处理思路

> 用户反馈：pcmanfm/thunar 右键菜单要加「**当前目录打开 terminal**」项；**pcmanfm 的 desktop 文件
> 执行不要跳框二次选择**（直接执行）。本节省源码实证（libfm 1.3.2 / pcmanfm gitee fk-libfm、
> fk-pcmanfm）分析机制与处理思路。

#### 1.1、pcmanfm「Open Terminal」菜单项（内建，机制）

- **菜单项**：`src/tab-page.c:60` / `src/desktop-ui.c:54`——GTK action `{"Term", "utilities-terminal",
  N_("Open in Termina_l")}`，action 名 `Term`，绑定 `on_open_folder_in_terminal()`。
- **回调**：`tab-page.c:809 on_open_folder_in_terminal()` → `pcmanfm_open_folder_in_terminal(win, dir)`
  （`src/pcmanfm.c:619`）。
- **执行逻辑**（`pcmanfm.c:619-659`）：
  1. `if(!fm_config->terminal)` → 报「Terminal emulator is not set.」并打开偏好设置；
  2. `FM_CHECK_VERSION(1,2,0)` 分支 → **`fm_terminal_launch(cwd_str)`**（libfm `base/fm-terminal.c`），
     `cwd_str` = 当前文件夹路径（**`fm_path_to_str(dir)`，即当前目录**，非所选路径——右键任意处
     都是「当前目录开终端」）。
- **前提**：`pcmanfm_can_open_path_in_terminal(dir)`（`pcmanfm.c:605`）——native 路径恒 TRUE，
  非 native 需 `g_file_get_path` 非空。

#### 1.2、libfm `fm_terminal_launch` 机制（`base/fm-terminal.c`）

- `FmTerminal` 抽象（`program`/`open_arg`/`noclose_arg`/`launch`/`desktop_id`/`custom_args`）。
- `_fm_terminal_init()`：读 `PACKAGE_DATA_DIR/terminals.list`（系统终端表，各终端的
  `open_arg`/`noclose_arg`/`launch`）→ `on_terminal_changed(fm_config)` 按 `fm_config->terminal`
  匹配 basename → `default_terminal`。
- `fm_terminal_launch(dir)`：`fm_terminal_dup_default()` 取默认终端 → 若 `desktop_id` 有则用
  `GDesktopAppInfo`，否则 `program + launch`；`custom_args` 追加；`g_shell_parse_argv` 解析 →
  `g_spawn_async`（`child_setup` 设 `setpgid` 防随父死）。
- **关键**：`fm_config->terminal` 来自 `libfm.conf` `[config] terminal=`（`fm-config.c:268`），
  **默认 NULL**（`fm-config.c:151`）→ 未配则 Open Terminal 报错。当前 hdmi 已配
  `terminal=x-terminal-emulator %s`。

## 四、GTK 主题差异根因与方向1修复（2026-11-08 分析）

### 1、分析处理思路

> 用户反馈：设 `GTK_DATA_PREFIX=/usr` 时 **lxtask 有主题、pcmanfm 无**；不设则**都无主题**。
> 怀疑 builder-awe 的 gtk2 静态库本应免设该变量（内置主题），或 hdmi 程序未更新。
> 本节省源码实证 + 库级符号分析定位根因，并按方向1（重建含 builtin murrine 注册的
> gtk2 库再重链 pcmanfm）修复。

#### 1.1、根因（库级符号实证，2026-11-08）

**主题链路（hdmi）**
- `~/.gtkrc-2.0`（LXAppearance 生成）设 `gtk-theme-name="Greybird"`、
  `gtk-icon-theme-name="Papirus-Bunsen-bluegrey"`。
- Greybird `gtk-2.0/gtkrc` 大量引用 `engine "murrine"` 和 `engine "pixmap"`。
- GTK2 `gtk_theme_engine_load()`（`gtkthemes.o`）用 `g_module_open` **动态加载引擎 `.so`**，
  路径 = `gtk_get_data_dir()/lib/gtk-2.0/2.10.0/engines/`。

**hdmi 引擎 `.so` 位置**
- 只在 **multiarch**：`/usr/lib/x86_64-linux-gnu/gtk-2.0/2.10.0/engines/`
  （`libmurrine.so`、`libpixmap.so`）。
- **非 multiarch** `/usr/lib/gtk-2.0/2.10.0/engines/` **不存在**——GTK_DATA_PREFIX=/usr 时
  GTK2 找的正是这个路径 → 找不到 `.so`。

**builder-awe 库级证据**
- `/usr/lib/libgtk-x11-2.0.a`（11/6 19:20，37.5M）：`ar t` 含 `murrine_draw.o`/
  `murrine_rc_style.o`，但 `gtkthemes.o` 的 `nm` 只显示 `g_module_open`/`g_module_symbol`
  动态加载、**无 `murrine_register` 引用** → **标准版，无内置注册**。
- **pcmanfm 重链命令**（`pcmanfm-relink.log`）：`-L/usr/local/lib`，**无**
  `-L/tmp/gtk/gtk/.libs` → 链 `/usr/lib/libgtk-x11-2.0.a`（标准版）。
- **lxtask 链接命令**（`ld_lxtask.sh`）：`-L/tmp/gtk/gtk/.libs -L/usr/local/lib` → 链
  **含 builtin 注册的 gtk 库**（该目录当时存在，现已被清理）。

**结论（两程序链接的 gtk2 静态库不同）**

| 程序 | 链接的 gtk2 静态库 | 引擎加载 | 结果 |
|---|---|---|---|
| lxtask | 打了 `gtkthemes-builtin-murrine.patch`（内置注册 murrine/pixmap） | 内置，不依赖 `.so` | ✅ 有主题 |
| pcmanfm | `/usr/lib` 标准版（动态加载，无内置注册） | 找非 multiarch `.so` → 失败 | ❌ 无主题 |

- 准确说：**不是 hdmi 程序未更新，而是 pcmanfm 重链时用了没打 builtin 主题 patch 的
  gtk 库**——builder-awe 含 patch 的库（`/tmp/gtk/gtk/.libs`）在 pcmanfm 11/8 重链前已
  被清理/替换为标准版 `/usr/lib/libgtk-x11-2.0.a`；lxtask 是在该目录还在时（11/6）链的。
- **方向1（选定）**：重建含 builtin murrine 注册的 gtk2 库（重新应用
  `gtkthemes-builtin-murrine.patch` + `stock_gtkthemes.c`）再重链 pcmanfm——不依赖
  GTK_DATA_PREFIX、不依赖引擎 `.so`，与 lxtask 同款。
- **备选（方向2）**：把 hdmi 引擎 `.so` 放到非 multiarch 路径
  `/usr/lib/gtk-2.0/2.10.0/engines/`（运行时补丁，包需带 `.so`，不如内置干净）。

#### 1.2、方向1修复（完成，2026-11-08）

**关键判断**
- 现有 `/usr/lib/libgtk-x11-2.0.a`（37.5M，11/6 19:20）**已含** murrine 引擎对象
  （`theme_init`/`theme_exit`/`theme_create_rc_style` 均为 T 定义）和 pixmap 引擎
  （`pixmap_theme_*`），**唯独 `gtkthemes.o` 是标准版**——`gtk_theme_engine_load()` 只走
  `g_module_open` 动态加载，**不查内置表**（`nm` 无 `theme_init` 引用）。
- 所以**无需重建整个 gtk**，只需把 **patch 版 `gtkthemes.o`**（含 `builtin_theme_engines[]`
  内置注册表）替换进该库，即可让内置 murrine 生效——与 lxtask 同款。

#### 1.5、静态版打开即崩溃（Glib::FileError）——TARGETPATH 未设退回 static_temp1（2026-11-08 补充）

> **现象**：hdmi 容器 `:1` 下点开静态 pavucontrol 直接崩（`rc=134`），stderr 仅
> `terminate called after throwing an instance of 'Glib::FileError'`。

**根因**（`strings` + 复现实证，2026-11-08）：

  构建时 `TARGETPATH` **未设**，退回 common.sh 默认 `static_temp1`（非最终部署路径）。
- 但部署到 `/usr/local/static/pavucontrol/`，glade 在 `/usr/local/static/pavucontrol/share/pavucontrol/`；
  找不到 glade → `Glib::FileError` → `SIGABRT`（rc=134）。

**复现/确认**（Xvnc `:1`，headless 属主，`PULSE_SERVER=unix:/tmp/pulse-avS8fJ3Lnh9c/native`）：
- 无任何链接：`rc=134` + `Glib::FileError`；

- build.sh **不加** `export TARGETPATH=...`（两入口规则见 AGENTS.md §3.2）——本地调试调用前

  （`.cc` 比 `.o` 旧 → make 跳过）→ 删 `/tmp/pavucontrol/src/*.o` 再跑 build.sh
  （经典 autotools 坑：改 prefix 必须清 `.o` 重编）。
- 重编后 `strings` 确认 glade 路径 = `/usr/local/static/pavucontrol/share/pavucontrol/pavucontrol.glade`；

**验证**（Xvnc `:1`，**最终部署路径**，无 static_temp1 链接）：

**教训**：① 改 prefix 后必须清 `.o` 重编（configure 不会自动重编）；② 本地调试必须显式传

## 六、ristretto 主题：实为回退默认主题，根因=旧 gtk2 `.a` 前缀 `/usr/local`，重链修复（2026-11-08）

### 1、w-xlunch：`ar r` 直改系统 libImlib2.a

位置：`compile/src/w-xlunch/build.sh`（约 L132，`imlib2()` 函数内）。

```sh

```

- 用途：imlib2 的 loader 默认是 dlopen 动态模块；xlunch 静态链需把它们**编进 libImlib2.a**，
  于是把 png/svg/jpeg 的 `*_load2`/`*_save`/`*_formats`（用 `-Dload2=` 等重命名避免符号冲突）
  与 `loaders.o` 直接 `ar r` 进系统静态库。
- 风险：
  1. **原地改系统库** `/usr/local/lib/libImlib2.a`，任何后续链接 imlib2 的二进制都会带上这些
     loader（通常无害，但隐式依赖）。
  2. 重跑脚本时 `ar r` 幂等（同对象覆盖），不会重复，但 `/tmp/builtin` 不清理则陈旧对象残留。
  3. 若系统库来自 apk 且被升级/覆盖，改动丢失且脚本未检测。
- 更优：把 loader 编进**私有**归档（如 `/usr/local/static/xlunch/libImlib2.a` 拷贝后 `ar r`），
  不碰系统库。或改用 `objcopy --redefine-sym` 方案（u-gtk 旧方案已废弃）。

### 2、v-ibus：boost_signals 空桩归档

位置：`compile/src/v-ibus/build.sh`（约 L317，ibus-rime 相关）。

```sh
cat > "$STUBDIR/boost_signals_stub.c" <<'EOF'
/* boost_signals 空桩：Alpine 3.15 boost1.77 无此库（signals2 为 header-only）。
 * 哨兵符号仅保证归档非空可链；librime 不引用真实 boost::signals 符号。 */
int rime_boost_signals_stub(void){ return 0; }
EOF
xx-clang -c "$STUBDIR/boost_signals_stub.c" -o "$STUBDIR/boost_signals_stub.o"

```

- 用途：librime 1.9.0 用 boost::signals2（header-only，无需真实符号），但 CMakeLists 的
  `RIME_DEPS` 引用 `libboost_signals.a`；Alpine 3.15 boost1.77 无此库 → 链接找不到。
  注入含哨兵符号的空归档，防 `-lboost_signals` 解析失败。
- 风险：桩放在 `/tmp/ibus-rime-build`（不进源目录，避免 aux_source_directory 误编）——
  安全。但若 librime 未来改用真实 boost::signals（非 header-only），空桩会掩盖缺失符号，
  造成**运行时未定义行为**。
- 结论：可接受的工作区，但需注释注明「仅当 librime 仍 header-only signals2 时有效」。

### 3、v-pavucontrol / v-sysmonitor：GTK2 print backend 空桩（受 gtk 重建影响）

位置：`compile/src/v-pavucontrol/build.sh`（约 L76）、`compile/src/v-sysmonitor/build.sh`（约 L131）。

```sh
cat > /tmp/pav-stub.c <<'EOF'
int _gtk_print_backend_file_init(void){return 0;}
int _gtk_print_backend_file_exit(void){return 0;}
void* _gtk_print_backend_file_create(void){return 0;}
int _gtk_print_backend_lpr_init(void){return 0;}
int _gtk_print_backend_lpr_exit(void){return 0;}
void* _gtk_print_backend_lpr_create(void){return 0;}
EOF
xx-clang -c /tmp/pav-stub.c -o /tmp/pav-stub.o
ar rcs /tmp/libstatic-printbackend.a /tmp/pav-stub.o
# 链接时置于 -lgtk-x11-2.0 之前
xx-clang++ -static ... /tmp/libstatic-printbackend.a -lgtkmm-2.4 ... -lgtk-x11-2.0 ...
```

- 用途：GTK2 print backend（file/lpr）通常由 libgtk 注册；这两应用早期链接缺
  `_gtk_print_backend_file_*`/`_gtk_print_backend_lpr_*`，故用空桩提供 no-op 实现。
- **2026-11-08 gtk 重建影响**：重建后的 `/usr/lib/libgtk-x11-2.0.a`（`-DGTK_PRINT_BACKENDS="file,lpr"`）
  **已定义**这些符号（`T _gtk_print_backend_file_init/exit/create`、`_gtk_print_backend_lpr_*`）。
  ⇒ 桩与 libgtk 现为**重复定义**：
  - 若桩归档在链接时被拉取（其符号先于 libgtk 未定义）→ 后续 libgtk 再定义同符号 → **multiple definition 错误**。
  - 若未被拉取 → 桩为死代码，可删除。
- 风险：桩覆盖真实 gtk 实现 → 若应用走 print backend（打印），行为为 no-op；且重建 gtk 后
  可能直接导致这两应用**静态链接失败**（重复符号，除非桩不被拉取）。
- 结论：**需在下次重建 pavucontrol/gsm 时验证**——先尝试去掉桩链接，若失败再加
  `--allow-multiple-definition` 或保留桩但注释说明冲突。

### 4、v-engrampa：`--allow-multiple-definition`

位置：`compile/src/v-engrampa/build.sh`（约 L69）。

```sh
xx-clang -static -Wl,--strip-all -Wl,--allow-multiple-definition -o .../engrampa \
  *.o ../copy-n-paste/.libs/libeggsmclient.a \
  -L/usr/local/lib -lm \
  -Wl,--start-group -lXinerama -lXfixes -lXrandr $LIBS0 -lintl -Wl,--end-group
```

- 用途：`libeggsmclient.a`（copy-n-paste）与 `$LIBS0`（gtk/glib/X 闭包）间存在同名符号，
  用宽松开关掩盖，避免链接失败。
- 风险：`--allow-multiple-definition` 会**静默**选择第一个定义，可能选错实现导致运行时怪问题；
  掩盖了真正的符号冲突来源。
- 结论：建议定位具体重复符号，改用更精确手段（如 `--wrap`、对象裁剪、或仅对冲突库用
  `--allow-multiple-definition` 缩小范围）。
