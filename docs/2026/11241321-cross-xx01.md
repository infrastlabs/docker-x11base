### 1、改造思路与实施（2026-11-24 16:33）

#### 1.1、改造方案（2026-11-24 16:40）

##### 1.1.1、改造思路

现状编译在 target 环境（qemu 模拟）跑，`CC=xx-clang` 但 target=host，非真正交叉；u-gtk 的 `.a` 装 `/usr/lib`（host/target 环境）。改造为：编译 stage 在 **x86 原生跑 + xx 交叉**——① Dockerfile 编译 stage `FROM --platform=$BUILDPLATFORM <builder> AS <comp>` + `COPY --from=tonistiigi/xx / /` + `ARG TARGETPLATFORM`；② u-gtk/u-gtkmm 交叉，`.a` 改装 `$(xx-info sysroot)/usr/lib`、`.pc`/头到 `$(xx-info sysroot)/usr/lib/pkgconfig` 与 `usr/include`；③ 各应用 configure `--host=$(xx-clang --print-target-triple)` + `--build=...`，最终 `xx-clang++ -static --sysroot=$(xx-info sysroot)` + `xx-info-pkg-config`；④ 应用静态 bin 仍 `$TARGETPATH/bin`，rootfs stage `COPY --link` 进镜像。

##### 1.1.2、产物位置与隔离



| 产物 | 放哪（交叉时） | 识别用上 |
|---|---|---|
| 静态库（u-gtk/u-gtkmm/依赖 `.a`） | `$(xx-info sysroot)/usr/lib` | `--sysroot=$(xx-info sysroot)` 自动；`-L$(xx-info sysroot)/usr/lib` |
| `.pc` | `$(xx-info sysroot)/usr/lib/pkgconfig` | `xx-info-pkg-config`（`pkg_config_libdir`）；configure `PKG_CONFIG_SYSROOT_DIR`+`PKG_CONFIG_PATH` |
| 头文件 | `$(xx-info sysroot)/usr/include` | `--sysroot`；`-I` |
| 应用静态 bin | `$TARGETPATH/bin`（`/usr/local/static/<comp>`） | rootfs `COPY --link` |

**不打架机制**：① buildx multi-platform 每个 target **独立构建实例**（独立容器/文件系统，`$TARGETPATH` 各实例独立）；② `xx-info sysroot` 按 TARGETPLATFORM 天然隔离（各 triple 独立 sysroot）。jlesage 实证：编译产物每 target 一份、最终镜像 per-target。**避免**：不同 arch 产物放同一共享位置（需 per-arch 命名 `$CACHE/<comp>/<triple>/`）。

##### 1.1.3、提前验证的点

① xx 工具链可用（`xx-clang --print-target-triple`/`xx-info sysroot`/`xx-verify`）；② **u-gtk 交叉**（最高风险，先验一个库如 pango/gdk-pixbuf，再全栈）；③ `xx-apk` 装 target 依赖（musl-dev/gtk+-dev）；④ `xx-info-pkg-config --libs gtk+-2.0` 返回 sysroot 路径（不误用 host `.pc`）；⑤ 链接顺序/`--start-group`（gtk 静态链已知坑，交叉下复验）；⑥ 每个产物 `xx-verify --static` + qemu-user 运行（`qemu-aarch64`/`qemu-arm`，无需真机）。

##### 1.1.4、实施顺序



| 阶段 | 内容 | 理由 |
|---|---|---|
| 0 | xx 工具链 + 最小组件（xdpyprobe 已用 xx-clang）交叉验证 | 打通工具链 |
| 1 | **u-gtk**（GTK2 栈）交叉，`.a` 进 sysroot | 所有 GTK2 应用依赖，最大风险先行 |
| 2 | **lxtask**（首个简单 GTK2 应用）交叉验证 | 用 u-gtk 产物验证 GTK2 交叉链路通（纯 gtk2，无需 gtkmm） |
| 3 | **u-gtkmm**（gtkmm 栈，链 gtk2）交叉 | gsm 依赖 |
| 4 | **gsm**（gtkmm 应用）交叉验证 | 验证 GTK2+GTKMM 交叉链路通 |
| 5 | 余下（pcmanfm/geany/lxde…、w-*、x-*、suckless；纯 X11 openbox/fluxbox 已证） | 按依赖拓扑推进 |

##### 1.1.5、编译环节可独立于 buildx（docker build 直接交叉，2026-11-24 16:47）

**问题**：xx 交叉编译能否直接用 `docker build`（不依赖 buildx 插件），把编译环节从 buildx 链接独立出来，本地无 buildx 也能编译？

**答案：可以**。关键在**交叉编译不依赖 buildx 的 multi-platform 调度**——`TARGETPLATFORM` 由 build-arg 传入即可：

- **单架构交叉编译**（核心）：`docker build --build-arg TARGETPLATFORM=linux/arm64 --target <comp> <ctx>`——`xx-clang`/`xx-go` 由 `TARGETPLATFORM` 驱动（`--target` 设 triple），编译 stage `FROM --platform=$BUILDPLATFORM`（docker build 默认 build 平台 = x86），**无需 buildx**。
- **多架构聚合**：多次 `docker build`（各传不同 `TARGETPLATFORM`）产出各架构产物，最后 **`docker manifest create/annotate/push`** 聚合（docker 内置命令，无 buildx）。
- **与 buildx 的区别**：buildx 一次 `--platform a,b,c` 搞定多平台 + manifest 聚合；docker build 需**多次**（每 target 一次）+ 手动 manifest 聚合。**编译环节本身（xx 交叉）两者都能跑**，只是编排方式不同。

**为什么可行**：`docker build` 底层即 buildkit，支持 `--build-arg`；`TARGETPLATFORM` 是普通 build-arg（buildx 只是自动注入，docker build 可手动传）。编译 stage 固定 `--platform=$BUILDPLATFORM`（build 平台），靠 `TARGETPLATFORM` 交叉 → **不需要 buildx 的 `--platform linux/arm64`（那才需 buildx/binfmt）**。

**注意**：
- 需 builder 镜像含 xx 工具链（`tonistiigi/xx` 或镜像内装 `xx-clang`/`xx-info`/`xx-verify`/`xx-apk`）。
- 单架构交叉验证（本地无 buildx）推荐用此方式：`docker build --build-arg TARGETPLATFORM=linux/arm64 --target u-gtk .`，产物 `xx-verify --static` 验证。
- CI 仍可保留 buildx 做多平台镜像打包；**编译环节**建议独立成单架构 `docker build`（可并行/可本地复现）。

#### 1.2、实施方案对比（最小化代码改动，2026-11-24 17:27）

核心现状（决定改动面）：

- `compile/src/Dockerfile`：**32 个编译 stage**（`FROM base/basemm/pulseaudio/dbus AS xxx`）+ 2 个 builder 基座（`base`/`basemm`）。当前**未加** `--platform=$BUILDPLATFORM`，仅 `base`/`basemm` 声明 `ARG TARGETPLATFORM`（子 stage 不继承，需各自声明）。
- `compile/src/common.sh`：已 `CC=xx-clang`/`CXX=xx-clang++`/静态 LDFLAGS；但**无 sysroot 重定向**（`.a` 全装 host `/usr/lib`，交叉链接需 target sysroot）。
- `compile/buildx.sh`：`--platform linux/amd64,linux/arm64,linux/arm` + qemu（当前慢的根因：**整个编译在 qemu 下跑**，`xx-clang` 实为空转——build 平台==target 平台）。
- 组件构建系统分布：autotools `./configure` ~22 个、meson 3 个（pasystray/x-dbus/x-rofi）、cmake 5 个（ibus/w-tint2/x-rofi/tigervnc/x11vnc）、纯 Makefile 3 个（suckless/xperp/w-hsetroot）、xdpyprobe 已 xx-clang。

##### 1.2.1、方案一：编排切平台 + 组件逐个 xx 适配（推荐，最终形态）

**做法**：一次性把所有编译 stage 切到原生构建平台交叉编译，build.sh 交叉适配按已定顺序增量（u-gtk→lxtask→u-gtkmm→gsm→余下），未适配组件用现有 `COMPILE_*=no` 关掉，适配一个开一个。

**改动范围**：

| 文件 | 改动 |
|---|---|
| `compile/src/Dockerfile` | `base`/`basemm` + **32 个编译 stage** 的 `FROM ... AS xxx` → `FROM --platform=$BUILDPLATFORM ... AS xxx`（**~34 处**）；每编译 stage 补 `ARG TARGETPLATFORM`（**~32 处**，子 stage 不继承）；合计 **~66 行**。`ff`（打包 stage）保持 target 平台不动 |
| `compile/src/common.sh` | 加 sysroot 条件导出：`SYSROOT=$(xx-info sysroot)`、`PKG_CONFIG_SYSROOT_DIR`、`PKG_CONFIG_PATH=$SYSROOT/usr/lib/pkgconfig`、CPPFLAGS `--sysroot`；**~10-15 行**（须 `TARGETPLATFORM` 存在才设，防破坏本地构建） |
| `compile/src/*/build.sh`（~30 个） | 交叉适配：autotools 加 `--host=$(xx-info triple)`（~2-5 行/个）；meson 加交叉文件（+10-20 行）；cmake 加 toolchain（+10-20 行）；**`.a` 落 sysroot**（u-gtk/u-gtkmm/x-pulseaudio/x-dbus/w-tint2 等共享栈，改 `$(xx-info sysroot)/usr/lib`）；b_deps `apk add`→`xx-apk add`。合计 **~200-400 行**，跨 30 文件 |
| `compile/buildx.sh` | 基本不动（buildx 仍 `--platform a,b,c`，每 stage 在 build 平台跑，产物按 target 隔离） |
| workflow | 不动（保留 buildx 多平台打包）；可选拆单架构并行编译 |

**优点**：真正原生跨架构（arm64/arm 提速 5-15x，治本）；符合已定实施顺序；增量验证风险可控；产物一致（每 target 一份，buildx 聚合）。

**缺点**：改动面最大（~30 个 build.sh 全要交叉适配）；**u-gtk/u-gtkmm 静态栈交叉最难**（configure 运行测试、`.la` 陷阱、march 变体——9 坑）；共享 `.a` 落位 sysroot 是全项目连锁改动；适配期被 `COMPILE_*=no` 关掉的组件产物缺失，需等适配。

##### 1.2.2、方案二：独立 xx 交叉入口（并行渐进，现有 qemu 构建零改动）

**做法**：新增独立 `Dockerfile.xx`（复用 base 镜像），只先做骨架组件（xdpyprobe + u-gtk + lxtask，验证 GTK2 交叉链路）；现有 `Dockerfile`/qemu 全量构建完全不动。产物经 `docker build --build-arg TARGETPLATFORM=linux/arm64 --target ...` 单架构产出（本地可复现）。

**改动范围**：

| 文件 | 改动 |
|---|---|
| `compile/src/Dockerfile.xx`（新增） | ~60-80 行（FROM `--platform=$BUILDPLATFORM base` + `ARG TARGETPLATFORM` + 3-4 个 stage，各 `xx-verify` 验证） |
| `compile/src/u-gtk/build.sh`、`v-lxde/build.sh`(lxtask) | 交叉适配（同方案一相应部分），**~40-60 行** |
| `.github/workflows/docker-image-x11-base.yml` | 新增 job（可选）：`docker build --build-arg TARGETPLATFORM=...` 单架构编译验证；**~20 行** |
| 现有 `Dockerfile`/`buildx.sh` | **0 改动** |

**优点**：现有 CI 零风险（qemu 全量照跑）；可完全并行推进；产物本地可复现（无需 buildx 插件）；符合"编译环节独立成单架构 docker build"（已认可）；最低落地风险。

**缺点**：两套构建逻辑并存（维护/漂移负担）；arm64 提速**只在最终切换回方案一后才体现**（本方案只是验证通道，不替代 qemu）；最终仍需收敛到方案一。

##### 1.2.3、方案三：编排级最小改动（仅 FROM 平台 + ARG，不动 build.sh）

**做法**：只改 Dockerfile 的 FROM 平台 + 每 stage `ARG TARGETPLATFORM` + common.sh sysroot 导出；**不动任何 build.sh**。

**改动范围**：

| 文件 | 改动 |
|---|---|
| `compile/src/Dockerfile` | `~66 行`（34 处 `--platform=$BUILDPLATFORM` + 32 处 `ARG TARGETPLATFORM`） |
| `compile/src/common.sh` | `~10-15 行`（sysroot 条件导出） |
| `compile/src/*/build.sh` | **0 改动** |

**优点**：改动最小、最快（~80 行）；可用作**阶段 0 快速打通管道**——先只启用纯 Makefile/无 configure 运行测试、无外部静态库的组件（xdpyprobe/suckless/xperp/w-hsetroot），它们 `CC=xx-clang make` 即可交叉成功。

**缺点**：**对项目核心（GTK2/gtkmm/pulse/xfce 等）不可行**——这些组件的 `.a` 在 host `/usr/lib`（x86），交叉链接拉不到 target sysroot → 链接失败；且 autotools `./configure` 没 `--host` 时 configure 运行测试程序用 host 跑 target 二进制 → fail（openbox "C compiler cannot create executables" 教训、AGENTS 避坑）。**只对无需外部静态库 + 无 configure 运行测试的组件有效**（约占 1/5）。

##### 综合评估

| 维度 | 方案一（全量切平台+适配） | 方案二（独立 xx 入口） | 方案三（编排级最小） |
|---|---|---|---|
| 改动量 | 大（~66+15+200~400 行，30 文件） | 中（~80-120 行，新增 1 文件） | **最小**（~80 行） |
| 对核心 GTK2/gtkmm | 可行（须适配） | 可行（先 u-gtk/lxtask 验证） | **不可行** |
| 提速收益 | **5-15x（治本）** | 仅验证，不替代 qemu | 仅 1/5 组件 |
| 风险 | 高（u-gtk 最难） | **最低**（现有 CI 不动） | 低（但核心无收益） |
| 与已定顺序兼容 | 完全 | 部分（先骨架） | 只做阶段 0 |

**建议路径**：**先方案三当"阶段 0"**（~80 行，纯 Makefile 组件打通 xx 交叉管道，验证 `docker build --build-arg TARGETPLATFORM` 本地复现），**再按方案一顺序推进**（u-gtk→lxtask→u-gtkmm→gsm→余下）——即先最小后全量，与已定实施顺序吻合。方案二仅在"现有 qemu 构建不能动"时作为隔离验证通道。

#### 1.3、xx-info 交叉检测实测（路径1确认 + 序列订正，2026-11-24 18:36）

> **订正（2026-11-24 18:36）**：经 xx-info 实测，1.2 建议路径调整为 **方案二→方案三→方案一**（用户拍板）——先用方案二 sandbox 攻坚所有卡点大项（零破坏 qemu），再方案三主 Dockerfile 编排打通，最后方案一全量落地。原"方案三先行"作废。

**实测环境**：`builder-g224`（`alpine-builder-gtk224-2` 镜像），amd64 宿主，`TARGETPLATFORM` 环境变量驱动 `xx-info`。

`xx-info`（tonistiigi/xx）按 **执行平台 arch（`uname -m`）vs TARGETPLATFORM arch** 自动判 native/cross——正是交叉适配向 qemu 向后兼容的关键信号。

**实测值**：

| TARGETPLATFORM | uname -m | arch | triple | sysroot | is-cross |
|---|---|---|---|---|---|
| `linux/amd64`（native） | x86_64 | amd64 | `x86_64-alpine-linux-musl` | `/` | rc=1（否） |
| `linux/arm64`（cross） | x86_64 | arm64 | `aarch64-alpine-linux-musl` | `/aarch64-alpine-linux-musl/` | rc=0（是） |
| `linux/arm/v7`（cross） | x86_64 | arm | `armv7-alpine-linux-musleabihf` | `/armv7-alpine-linux-musleabihf/` | rc=0（是） |

`xx-info env` 另暴露：`XX_ARCH/XX_TRIPLE/XX_MARCH/XX_PKG_ARCH/XX_LIBC/XX_OS/XX_OS_VERSION/XX_VENDOR`。可用子命令：`arch os variant triple sysroot march env is-cross`。

**结论（路径1成立）**：

- **native（build==target，含 qemu 下 stage 在 target 原生跑）**：`xx-info sysroot`=`/`、`is-cross`=false → `$(xx-info sysroot)/usr/lib`=`/usr/lib`（同现状）、`--host=$(xx-info triple)`=native triple（configure 当原生处理）。**build.sh 用 xx-info 派生参数，qemu 构建不受影响。**
- **cross（xx 模式，stage 在 build 平台 amd64 跑）**：`sysroot`=独立 target 目录、`is-cross`=true → `.a` 落 target sysroot、`--host`=cross triple。**交叉生效。**
- → build.sh 交叉适配（用 xx-info）**天然向后兼容 qemu**，无需额外条件 guard；`xx-info is-cross` 可用于必须区分的分支（如跳 configure 运行测试）。

**注意项**：

- **target sysroot 目录默认不存在**（`/aarch64-alpine-linux-musl/` No such file）——须先 `xx-apk add` 装 target `musl-dev`/`gtk+-dev` 等填充，或 u-gtk 自编 `.a` 落入。方案二攻坚 u-gtk 时解决。

**关键前提：build.sh 是共享文件**。`compile/src/*/build.sh` 和 `common.sh` 被**主 Dockerfile（qemu）和 Dockerfile.xx（sandbox）共用**（都 `COPY ./src /src`）。所以方案二给 build.sh 加的交叉适配（`--host`、`.a`→sysroot、`xx-apk`）会同时影响正在跑的 qemu 构建。要让方案二真正"零破坏 qemu"，交叉适配必须**对 qemu 向后兼容**，两条路：

1. **xx-info 自动检测（首选）**：build.sh 一律用 `xx-info triple`/`xx-info sysroot`/`xx-info-pkg-config` 派生参数。若 xx-info 在 qemu 下（build==target，stage 在 target 原生跑）能返回 native-safe 值（sysroot=`/`、triple=当前 arch），则 `--host=$(xx-info triple)` 在 qemu 下==native triple（configure 当原生处理）、sysroot 路径==`/usr/lib`（同现状）→ qemu 不受影响，xx cross 下自动切交叉。这条路最干净，但取决于 xx-info 在 qemu 下的行为，需先实测验证。
2. **条件 guard（保底）**：用"执行 arch != target arch"判断是否真交叉（`xx-info is-cross` 若提供，或 `uname -m` vs `xx-info arch`），真交叉才走 sysroot/`--host` 分支，否则走原路径。

> ⚠️ **不能用 `BUILDPLATFORM != TARGETPLATFORM` 当 guard**：qemu 下两者本就不同（amd64 runner 编 arm64），会误判激活交叉分支搞坏 qemu。判据必须是**执行平台 arch vs target arch**。

**scope 澄清**：方案二原定义只做"骨架（xdpyprobe+u-gtk+lxtask）"。重排后扩到**所有难组件**（u-gtk/u-gtkmm/gsm/pulse/xfce4/pcmanfm/geany/lxde…），easy 组件（suckless/xperp/w-hsetroot）留给方案三。

**结论**：先实测 xx-info 在 qemu/native/cross 下的行为（见 1.3 实测表）——确认路 1 成立（`is-cross` 按 `uname -m` vs target arch 判，native 返回 sysroot=`/`、is-cross=false），build.sh 用 xx-info 一把梭、qemu 自动兼容。

- **apk 静态库补全**（lxtask 链接期缺失，`xx-apk add`）：`libxrandr-dev`(无.a 不用) `libxcursor-dev libxcomposite-dev libxinerama-dev`(dev 含.a) `libgpg-error-static expat-static zlib-static bzip2-static brotli-static graphite2-static pixman-static`。**Alpine 无 `libxrandr-static`/`libxdamage-static`**（该两库只能源码构建）。

**本轮两个关键发现（静态链接模式）**：

- **`-static` 拉全部传递静态库**：动态链接时 `.so` 自含传递依赖，静态链接需每个 `.a` 显式存在——`-static` 开启后才暴露缺 `libexpat.a`/`libz.a`/`libbz2.a`/`libbrotlidec.a`/`libbrotlicommon.a`/`libgraphite2.a`/`libpixman-1.a`（apk 静态包补齐）。判静态成功**别只信 `make` rc=0**：`file` 应 `statically linked`（否则可能误链 `.so` 成动态——初测 `-L...` 缺 `-static` 产物动态，且 make 因产物 up-to-date 跳过重链，**须 `rm` 产物强制重链**）。
- **复用树 stale `.o` 坑**：`/tmp/libxrandr` 曾含 native x86-64 `.o`，cross configure 后 `make` 复用 → `libXrandr.a` 误 x86-64。**cross 构建前必须 `rm -rf` 源码树**（`file`/`ar p | file` 核对 arch 兜底）。

##### 3.2.4、方案三 qemu→交叉切换机制与其他需调整处（2026-11-25 13:30）

> 用户问 2c：buildx 模式是怎么从 qemu 模拟切换到交叉编译来的？其他地方有需要调整的吗？

**切换机制（4 步链）**：

1. `FROM --platform=$BUILDPLATFORM ... AS <comp>` → 编译 stage 从 target 平台（qemu 模拟）改到 **build 平台（x86 原生）** 跑。
2. `ARG TARGETPLATFORM` → buildx/`--build-arg` 注入目标平台；**BuildKit 会把已声明 ARG 自动导出到 RUN 的 env**（实测 `printenv` 有 `TARGETPLATFORM`，**无需 `ENV`**）。
3. `xx-clang`（**基座镜像已烤入**，`/usr/bin/xx-clang`）读 env `TARGETPLATFORM` → 设目标 triple/sysroot，交叉编译。
4. `common.sh xx_cross_init`（方案二已做）读 `TARGETPLATFORM` → 设 `XX_SYSROOT/XX_CROSS_FILE/XX_TRIPLE` → build.sh 走交叉路径。

qemu 退役范围：编译 stage 不再跑 qemu；**仅最终 runtime/ff stage 保留 target 平台（仍 qemu）**——它们产目标架构镜像，不动。

**其他地方需要调整——一个关键漏项**：

- **① 基座 stage 必须创建目标 sysroot（方案三计划漏了，最关键）**：
  - **实测**：基座镜像 `alpine-builder-gtk224-2` **没烤入 ARM sysroot**（fresh 容器 `/aarch64-alpine-linux-musl` 不存在；`crt1.o`/`libc.a` 无）。方案二的 sysroot 是**运行时 `xx-apk` 手动装的**，不在镜像里。
  - 所以交叉链接会报 `cannot find crt1.o/libc.a/-lgcc`（最小用例复现）。**修**：base/basemm stage 加 `xx-apk add musl-dev gcc`（创建 sysroot + crt1.o/libc.a/libgcc.a）。**加此行后最小用例产出 aarch64 static**。
  - gtk2 组件的其余静态库仍由 u-gtk `apkdeps` 的 `xx-apk` 补（方案二已做）；纯组件（suckless/xperp/xdpyprobe）只需 base 的 musl-dev/gcc。

**不需要的（已确认）**：

- `ENV TARGETPLATFORM=$TARGETPLATFORM` —— **不需要**（ARG 自动进 RUN env，实测）。
- `COPY --from=tonistiigi/xx / /` —— **不需要**（基座镜像已含 xx-clang/xx-info/xx-apk）。
- `ff`/最终 runtime stage —— **不动**（保持 target 平台）。
- CI workflow —— **不用改**（setup-qemu/buildx 已有；qemu 只留最终 stage）。

**修正后方案三改动量**：`compile/src/Dockerfile` ~66 行（34 FROM `--platform` + 32 ARG）+ **base/basemm 各 ~2-4 行 `xx-apk add musl-dev gcc`**（共 +4~8 行）；common.sh、build.sh 仍 **0 改动**。

#### 4.2、共享交叉环境配方（autotools 类，照搬 x-xbindkeys/v-engrampa，2026-11-25 15:20）

每个组件在 build.sh 里加一个 `<comp>_cross()`（**守 `[ -n "$XX_CROSS_FILE" ]`，native 全空 → 原路径零影响**）：

```sh
<comp>_cross(){
  CROSS_HOST=""; MAKE_CC=""
  if [ -n "$XX_CROSS_FILE" ]; then
    CROSS_HOST="--host=$(xx-info triple)"
    MAKE_CC="CC=xx-clang"
    export CC=xx-clang
    export PKG_CONFIG=/usr/bin/pkg-config
    export PKG_CONFIG_LIBDIR="$XX_SYSROOT/usr/local/lib/pkgconfig:$XX_SYSROOT/usr/lib/pkgconfig:$XX_SYSROOT/usr/share/pkgconfig"
    export PKG_CONFIG_SYSROOT_DIR="$XX_SYSROOT"
    unset PKG_CONFIG_PATH
    export ac_cv_func_realloc_0_nonnull=yes   # 交叉下 configure run-test 不能跑 → 显式 yes
    export ac_cv_func_malloc_0_nonnull=yes
    export ac_cv_prog_cc_cross=yes
    export LDFLAGS="-L$XX_SYSROOT/usr/lib -L$XX_SYSROOT/usr/local/lib $LDFLAGS"  # 追加, 保留 common.sh 原值
    # sysroot 按需补静态库(仅列该组件实际 -l 依赖): xx-apk add <pkgs>
    log "<comp>: CROSS ($XX_TRIPLE)"
  fi
}
```

接线四处：① 构建函数首行调 `<comp>_cross`；② `./configure ... $CROSS_HOST`（native 空）；③ `make $MAKE_CC ...`（加 `CC=xx-clang`）；④ verify 改分支：

```sh
if [ -n "$XX_CROSS_FILE" ]; then
  file $TARGETPATH/bin/<BIN> | grep -qE "ARM.*statically linked" || { log "<COMP> file 非 ARM static"; exit 1; }
else
  xx-verify --static $TARGETPATH/bin/<BIN> || { log "<COMP> xx-verify FAILED"; exit 1; }
fi
```

make-only 组件（`suckless`/`xperp`）无 configure → 不用 `$CROSS_HOST`，只 `make $MAKE_CC` + 显式 `-L` sysroot 前缀。

##### 4.7.1、openbox 交叉明细（✅ arm64 + armv7，2026-11-25 20:30）

**关键：适配要落到 Dockerfile 实调的脚本**。Dockerfile fluxbox stage（L155）调的是 `bash /src/fluxbox/build.sh.xft.sh fluxbox`（`--enable-imlib2` 那版），**不是** `build.sh`。早前子任务把交叉适配写进了 `build.sh`（用 `--disable-imlib2` 绕开 imlib2）——跑不对脚本，白做。本次把 `fb_cross()` + 交叉 configure/make/verify 迁到 `build.sh.xft.sh`。

**imlib2 无需源码建**：arm64/armv7 两 sysroot 里 `libImlib2.a` 已是 **ARM**（此前 w-xlunch 等组件交叉时 `DESTDIR=$(xx-info sysroot)` 装入），直接链即可，不必像预估的那样源码交叉建 imlib2。

**修法**（`build.sh.xft.sh`，守 `[ -n "$XX_CROSS_FILE" ]`，native 零影响）：
- `fb_cross()`：`CC=xx-clang`+`CXX=xx-clang++`+`ac_cv_prog_cxx_cross=yes`（fluxbox=C++）；pkg-config sysroot 三目录；`LDFLAGS` 前置 sysroot 两个 `-L`；xx-apk 补 fribidi/xpm/xml2/X11 静态栈；`libXrandr.a` 无 apk 包→借 openbox `libxrandr()`；**清洗 sysroot `.la`**（注释 `dependency_libs` + 裸 `libdir` 补 sysroot 前缀，同 openbox 4.7.1，防 libtool 拖原生 `.a`）。
- configure 加 `--build=$(TARGETPLATFORM= xx-clang --print-target-triple)`（宿主）+ `--host=$(xx-info triple)`（target）。
- make 交叉走 `$MAKE_CC LDFLAGS="$LDFLAGS -static" LIBS="$FB_LIBS"`（`--start-group` 包全 X11/imlib2/fribidi/fontconfig/freetype/xpm/xml2/压缩/pthread/m）。
- verify 交叉用 `file` 判 ARM static，native 仍 `xx-verify`。

**armv7 特有坑**：`src/Ewmh.cc:923` C++11 narrowing（`unsigned int`→`long` initializer list）被 clang 当 **error**（`-Wc++11-narrowing`）→ 编译失败。arm64 不触发（类型宽度/codegen 不同）。修：`fb_cross()` 里 `export CXXFLAGS="-Wno-c++11-narrowing $CXXFLAGS"`（仅 cross 生效）。

**commit**：`build.sh.xft.sh` + 本节 docs 见 fluxbox 交叉提交。

##### 4.7.3、x-x11vnc 交叉明细（✅ arm64 + armv7，2026-11-25 22:03）

**产物**：`x11vnc` 在 arm64 `ELF ARM aarch64 statically linked`、在 armv7 `ELF 32-bit ARM EABI5 statically linked`。`X11VNC_RC=0`。

**依赖链逐个交叉适配**（x11vnc 链 `libvncserver`+`libXtst`+`libXi`，三者 sysroot 原本都缺 ARM `.a`）：
- **libvncserver（cmake）**：原 `make`/`make install` 会连带编 examples/client_examples(backchannel)+test/* 可执行，交叉下 link 全挂（host `x86_64-ld` + ARM `libpng.so` → `file in wrong format`）。改 **lib-only**：`cmake` 配交叉（`-DCMAKE_C_COMPILER=xx-clang`+FIND_ROOT_PATH=sysroot+`BUILD_SHARED_LIBS=OFF`）后只 `make vncserver vncclient`（目标名无 lib 前缀/无 .a 后缀），再手动装 `libvncserver.a`/`libvncclient.a`+`rfb/` 头（含构建期生成的 `rfb/rfbconfig.h`）+`.pc` 到 sysroot。中途试过 sed 注释 CMakeLists 的 foreach/examples——多行 `add_executable(test_tj...` 续行参数被截断 → cmake Parse error，放弃 sed 改 lib-only。
- **libxtst（autotools）**：`libxtst()` 加 `x11vnc_cross` 调用（共享 PKG_CONFIG_LIBDIR 指 sysroot）+ `--host` + `DESTDIR=$XX_SYSROOT`。否则 configure 找不到 `xi`/`xtst.pc`。
- **libxi**：复用 `w-tint2/build.sh libxi`（本就 cross-aware），b_deps 并行跑偶发 rc=127（race），串行单独跑即过 → ARM `libXi.a`。
- **x11vnc 本体**：configure 的 LDFLAGS 补 sysroot 两个 `-L`（`usr/lib`+`usr/local/lib`），否则 link-test 找不到 `-lXtst` → `C compiler cannot create executables`。

**armv7 特有坑**：`xx-apk add` 批量装依赖时含不存在的 `libssl-dev`（Alpine 无此包名，是 `openssl-dev`）→ 整条 apk add 中止；且个别包走网络 fetch 失败 → `|| true` 容忍（所需头/.pc 已在 sysroot）。`b_deps` 并行跑 3 依赖偶发 race，验证时串行。

**commit**：`build.sh` + 本节 docs 见 x11vnc 交叉提交。

#### 4.8、x-tigervnc 交叉攻坚（✅ arm64 + armv7，2026-11-25 19:12）

TigerVNC 是方案一里最复杂的组件：**cmake（common/vncpasswd）+ autotools（xserver）双构建系统**，外加 5 个自编依赖（gnutls/libxfont2/libfontenc/libtasn1/libxshmfence）+ 1 个 sysroot apk 依赖（libxkbfile）。四个根因全在此前 qemu 原生构建下不会暴露，纯交叉特有。

##### 4.8.1、arm64（aarch64）——✅ 验证通过

**产物**：`Xvnc`、`vncpasswd` 均 `ELF 64-bit LSB executable, ARM aarch64, statically linked, stripped`，`readelf -h` Machine=AArch64。`BUILD_RC=0`。

**四个根因与修法**：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| ① | vncpasswd/Xvnc 全编成 x86-64 | `tigervnc_cross()` 只 export `XX_CROSS_FILE`/`XX_ARCH`，但 **xx-clang/xx-info 认的是 `TARGETPLATFORM`**（`linux/arm64`），不认 XX_* → 全退回宿主 x86_64 | `tigervnc_cross()` 从 cross-file 的 `cpu_family` 推导 `TARGETPLATFORM` 并 export |
| ② | `configure: cannot run C compiled programs ... use --host` | xserver + 5 个依赖子构建的 `--build`/`--host` 都填 `xx-info triple`（现同返 aarch64）→ build==host → autoconf 不认为交叉 → 跑测试程序失败 | `--build` 改 `$(TARGETPLATFORM='' xx-info triple)`（宿主 x86_64），`--host` 留 target |
| ③ | `clang: /usr/local/lib/libxshmfence.a: No such file` | xserver configure 经 pkg-config 探测把裸 `-L/usr/local/lib` 写进 `XSERVER_SYS_LIBS`（容器 amd64 真实目录，内有同名 .la）→ libtool 优先命中并拼出裸 `.a` 路径 | 交叉时 sed 把 Makefile 的裸 `-L/usr/local/lib` 换成 sysroot 三个 `-L`（`lib`+`usr/lib`+`usr/local/lib`）；并清空 sysroot `.la` 的 `dependency_libs` |
| ④ | `undefined reference to FT_*/FontEnc*` | `XSERVER_SYS_LIBS` 缺 freetype/fontenc，且静态链顺序敏感 | `XSERVER_SYS_LIBS` 改 `--start-group`/`--end-group` 包全（含 `-lxkbfile -lfreetype -lfontenc -lxshmfence`），`libz.a` 在 `$XX_SYSROOT/lib`（非 usr/lib）补 `-L` |

**附带发现**：`libxkbfile` 在 sysroot 里有现成 aarch64 apk 包 `libxkbfile-dev`（头文件在 `X11/extensions/XKBfile.h`），**无需源码建**——删除了误加的 `libxkbfile()` 函数。4 个依赖库（fontenc/tasn1/xshmfence/Xfont2）已交叉建为 ARM `.a` 装进 sysroot。

**commit**：`41fab6e3`（build.sh）、`779a7df4`（docs）。

##### 4.8.2、armv7（armv7l）——✅ 验证通过

**产物**：`Xvnc`、`vncpasswd` 均 `ELF 32-bit LSB executable, ARM, EABI5 version 1 (SYSV), statically linked, stripped`。`BUILD_RC=0`。

- **sysroot/工具链**：`/armv7-alpine-linux-musleabihf` + `/tmp/xx-cross-armv7l.ini`（`cpu_family='armv7l'`）均已就位。
- **补一个 case 分支**：`_march='armv7l'` 原落到 `*)` → `linux/armv7l`（碰巧 xx-info 还认）。显式加 `arm|armv7l) _tpf="linux/arm/v7"`，与 buildx 平台串一致。
- **4 个自编依赖**（fontenc/tasn1/xshmfence/Xfont2）串行重建为 **ARM EABI5** `.a` 装进 armv7 sysroot。
- **⚠️ b_deps 并行 race（armv7 特有）**：`b_deps` 用 `doExec ... &` **并行**跑 4 个依赖，在 armv7 下**全 rc=1**（arm64 时是好的）；**逐个串行跑全 rc=0**。根因未深挖（疑共享 sysroot/xx-env 的 apk 或 pkg-config 并发冲突）。**规避**：验证时按 `libfontenc→libtasn1→libxshmfence→libxfont2→tigervnc` **串行**执行。CI 若复现需把 x-tigervnc 的 `b_deps` 改串行或在依赖间加锁。
- arm64 的四个根因修法（TARGETPLATFORM/`--build`=宿主/裸 `-L`→sysroot/`--start-group`）对 armv7 同样生效，无需额外改动。
