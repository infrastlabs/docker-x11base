### 5. 读出来的 6 个代码疑点

`compile/src/v-lxde/build.sh:51-78`

1. **`$branch` 未定义** —— 脚本头部不像 v-tint2 那样声明 `branch="--branch=0.6.13"`，`lxtask():56` 的 `git clone --depth=1 $branch $GITHUB/lxde/lxtask` 里 `$branch` 是空串 → 隐式克隆默认分支。`vers.txt` 声明的是 `master`，行为一致但隐式，镜像切换后可能落到错的分支。

2. **`--prefix=$TARGETPATH` 把产物装到 GTK 查找路径之外** —— `lxtask():60` 传 `--prefix=$TARGETPATH`，产物落 `/usr/local/static/lxde/bin/lxtask`。这与 openbox 一致（openbox 也是 `INS_PREFIX=$TARGETPATH`，见 `openbox/build.sh:28`，同样没有 `/usr/local` 那层），两者取件路径模型统一。**但问题在另一头**：GTK 的主题/图标是走全局系统路径查的（`/usr/share/themes`、`/usr/share/icons`、`/usr/etc/gtk-2.0/settings.ini`），构建产物隔离在 `/usr/local/static/<comp>/` 下，**装了也查不到**。见第七章第 2、3 点。

3. **`make LDFLAGS="-static "` 整体覆盖** —— `lxtask():69` 把 LDFLAGS 整个替换，不像 openbox 用 `LDFLAGS="$LDFLAGS -Wl,--start-group $OB_LIBS -Wl,--end-group"` 追加并包裹。`-lgpg-error` / `-lgdk_pixbuf-2.0` / `-lmount` / `-lblkid` 这些传递库**没有 `--start-group` 保护**，能链过靠的是 `LIBS0` 里 OB_LIBS 排在 ex0 / ex1 之后，链接顺序恰好够。这是脆的——增删一个库就可能翻车。

4. **`xx-verify` 验的是构建树，不是安装产物** —— `lxtask():77` 验 `/tmp/lxtask/src/lxtask`；安装到 TARGETPATH 的产物没人验。对比 openbox 验的是 `$ROOT_DEST_DIR${INS_PREFIX}/bin/openbox`（最终交付物）。当前脚本验的通过，不代表 install 后的那个也是静态。

5. **错误检测比 openbox 更糟** —— `v-lxde/build.sh:92` 的 `case` 结尾有 `exit 0`，**无条件返回 0**；再叠加 `oneBuild` 的 `set +e` + `test "0" != "$?"` 判的是 `find` 退出码（见 openbox 文档 8.4），失败一定被吞成 `err 0, pass`。openbox 的 `case` 没有 `exit`、`v-lxde` 连这个都没有了。

6. **`cache)` / `full)` 分支都是空的** —— `:82-87` 两个分支无内容，不会预下载源码，`full` 什么都不做。Dockerfile 里 `# sh /src/v-lxde/build.sh cache;` 本来就是注释掉的，等于从来没生效过。

### 6. 待办

**硬阻塞（必须先解）**：拿源码。三条路待选：

- **A** 把 `lxde/lxtask` 镜像到 `g-system/` 或 `g-aicoder/` 下（跟其他 `fk-*` 一致），改 `$GITHUB` 路由后接上验证
- **B** 给一个当前能通的 tarball 直链，加 `down_catfile` 走 curl（绕开 git）
- **C** 先不动下载，只修不依赖源码的 4 处：`--prefix` 布局、`LDFLAGS` 覆盖、verify 目标、`exit 0`

C 单独做没意义——改完无法验证静态链接是否真成立，只能等源到了再回头验。A / B 任一到位后，剩下的是把疑点 1-6 一并修掉，并按 openbox 的路子补一章「落仓改动明细」。

**修的时候对齐 openbox 的口径**（openbox 文档五章已定型）：

- 依赖库装进 `apkdeps`，不要脚本内 `apk add`

- `case` 结尾不要 `exit 0`，或者显式 `return $?`
- 别信 `oneBuild` 的 `err 0, pass`，自己 `xx-verify --static` + `grep -c "undefined reference\|attempted static link"` 兜底

### 7. 主题不识别 + 图标不显示：原因分析

> **订正**：本节是 builder 容器环境侧的盘点（容器里到底装了什么），**不是问题的完整原因**。主线是 gdk-pixbuf loader 静态失效 + GTK2 编译期 prefix 烤死，见 `## 二、`。本节「无真实 GTK2 主题本体 / 无真实图标集 / 无名称来源」三条结论仍然成立，7.2 第三层的 prefix 值原写错了，已在文内订正。

**现象**：当前构建认不出 GTK2 / GTK3 主题，图标不显示。

**共同根因**：x11base 镜像是「最小 X11 + 组件产物隔离到 `/usr/local/static/<comp>/`」的模型，而 GTK 的主题 / 图标是**运行时全局数据**，走固定系统路径查。两套路径模型不兼容 —— 组件装得再干净，主题效果也不会出现。字体同理（openbox 的 fontconfig 重编到 `/usr/local/static/openbox/share/fontconfig`，运行期不设 `FONTCONFIG_PATH` / `FONTCONFIG_FILE` 就不生效）。

#### 7.1 GTK3 主题：不是配置问题，是 GTK3 根本没装

实测（builder-obox）：

```
ls /usr/lib/libgtk-3*      # No such file
ls /usr/include/gtk-3.0    # No such file
find /usr /usr/local -name settings.ini -path "*gtk*"   # 空
```

- **无 `libgtk-3`、无 `gtk-3.0` 头文件、无 `gtk-3.0/settings.ini`**
- lxtask 是用 `libgtk-x11-2.0` 编的（`v-lxde/build.sh:67` 的 `LIBS0` 写死 gtk2），**架构上就不读 GTK3 主题**
- lxappearance 那边 `v-lxde/build.sh:23` 硬关 `--enable-gtk3=no` → 连主题切换器自己都不认 GTK3 主题

要 GTK3 主题生效：装 gtk3 整链 + 编 gtk3 版 lxtask。Arch 的包名就是干这个的 —— `lxtask-gtk3`，`Replaces` / `Conflicts` 都指向 gtk2 版，两者互斥。

#### 7.2 GTK2 主题：入口配置和主题本体两层都缺

**第一层（入口）**：GTK2 读主题的唯一入口是 `gtk-theme-name`，来自 `/usr/etc/gtk-2.0/settings.ini`、`~/.config/gtk-2.0/settings.ini`、`~/.gtkrc-2.0`。实测这三个**全盘都不存在**，也无任何 gtkrc 文件 → `gtk_settings_get_default()->gtk-theme-name` 只能拿到编译期默认值，**根本没有机会去读任何主题**。

**第二层（本体）**：`/usr/share/themes` 只有 `Default` / `Emacs` / `Raleigh`。openbox 装的那 9 个主题（Artwiz-boxed / Bear2 / Clearlooks / Mikachu / Natura / Onyx / Onyx-Citrus / Orang…）目录里**只有 `openbox-3/`**，`find ... -name gtkrc*` 无结果 → 是 openbox 私有主题（`themerc` + 位图），GTK 应用认不出来。

**第三层（查找路径）**：编译期前缀**实测是 `/usr/local`，不是 `/usr`** —— `pkg-config --variable=prefix gtk+-2.0` 报 `/usr` 的是 apk 装的 `gtk+2.0-dev` 的 `.pc` 文件，与静态链进二进制的 `libgtk-x11-2.0.a` 无关（后者 `strings` 只出现 `/usr/local` 系路径）。所以真实查找根是 `/usr/local/share/themes/`（详见二.2）。构建产物隔离在 `/usr/local/static/<comp>/` 下，不在查找路径上。

修法：装真实 GTK2 主题到**实际查找根** `/usr/local/share/themes/<name>/gtk-2.0/gtkrc`（或用 `GTK_DATA_PREFIX=/usr` 把主题根指到 `/usr/share/themes`，见二.2），并让 `gtk-theme-name` 拿到名字（`/etc/gtk-2.0/settings.ini`、`~/.config/gtk-2.0/settings.ini`、`~/.gtkrc-2.0`）。

#### 7.3 图标：图标主题是空壳

```
/usr/share/icons/hicolor/index.theme     # 存在
/usr/share/icons/hicolor/{16x16,22x22,...,512x512,scalable,symbolic}   # 13 个尺寸目录
/usr/share/icons/hicolor/16x16/{actions,apps,stock,...}                # 11 个类别目录
find /usr/share/icons \( -name '*.png' -o -name '*.svg' \) | wc -l     # 0
```

**实际图标数 = 0**。`hicolor-icon-theme` 装了，但它是父主题 / 骨架，本来就只带 `index.theme` 和目录结构，不带图标 —— 真实图标来自继承 hicolor 的具体图标集（Papirus / Oxygen / Adwaita / Humanist 等），**一个都没装**。

`v-lxde/build.sh:6` 留的注释印证了这点：

```sh
# apk add hicolor-icon-theme #need hicolor
```

作者知道要装 hicolor，但**装了也不够**（hicolor 是空的），得装真正的图标集。

叠加两个因素：

1. `gtk-icon-theme-name` 无来源（同 7.2 第一层的 `settings.ini` 缺失）→ GTK 回退内置 default theme
2. openbox 的窗口按钮图标是它自己 draw 的位图（`themes/*/openbox-3/*.xbm`），**不走 GTK icon theme** → openbox 有图标不代表 GTK 应用有。lxtask 的按钮 / 任务条目走 `gtk_icon_theme_load_icon`，找不到就画空白

修法：装真实图标集到 `/usr/share/icons/<name>`，并在 `settings.ini` 里写 `gtk-icon-theme-name=<name>`。

#### 7.4 下游 rootfs 侧：零配置

`seckill-system` 全量 grep `gtk-theme` / `gtk2` / `gtk3` / `icon-theme` / `hicolor` / `.themes` / `settings.ini`：**0 命中**。即下游 rootfs 也没有任何主题 / 图标注入，不是「上游没装、下游补了」的情况，而是两端都没有。

## 二、静态构建下图标与主题失效：问答实录

> **背景（对 一.7 的纠偏）**：「gtk 你管 builder 内环境干嘛，使用静态编译 lxtask 的环境是有的 其他程序正常」—— 一.7 走的是 builder 容器环境盘点，不是要的答案；要的是从**构建配置与二进制机制**上解释为什么图标不显示、主题认不出。
>
> **验证环境**：`builder-obox` / `builder-awe`（`alpine-builder-gtk224`），GTK2 **2.24.33** 源码仍在容器 `/tmp/gtk`，以下结论全部实读源码，不是推测。

### 1. 图标：是否走 gdk-pixbuf，loader 动态插件机制是否在静态编译下失效

**问**：

> lxtask的图标显示用到gdk-pixbuf吗？是否它的动态插件机制在静态编译时失效导致？？

**答**：

#### 1) lxtask 的图标确实走 gdk-pixbuf

链接行里是写死的（`compile/src/v-lxde/build.sh:67`）：

```
LIBS0=" -lgdk-x11-2.0 -lgtk-x11-2.0 -latk-1.0 -lgdk_pixbuf-2.0 -lpangocairo-1.0 ..."
```

调用链：lxtask 用 GTK2 的 `gtk_icon_theme_load_icon()` 取图标 → GTK 内部就是 `gdk_pixbuf_new_from_file()` 解码 PNG。所以 `gdk-pixbuf` 是 lxtask 图标显示的必经环节，不是可选项。

#### 2) 是的，动态插件机制在静态编译下失效 —— 这就是图标不显示的直接原因

gdk-pixbuf 的解码器（PNG/JPEG/XPM/ICO…）**不在 `libgdk_pixbuf-2.0.a` 里**，它是独立 loader 模块，运行时靠 **dlopen** 从 loader 目录（`<libdir>/gdk-pixbuf-2.0/2.10.0/loaders/`）动态加载，装配 loader 表。静态构建断在两步：

- **静态归档里没有 loader**。项目里 gdk-pixbuf 2.42.8 是 meson 静态编的，`docs/desk/lxde/pcmanfm-gnome-deps.md:203-205` 记录产出只有 `libstaticpixbufloader-jpeg.a` / `libstaticpixbufloader-png.a` —— loader 是被编成静态归档的，没有可 dlopen 的 `.so`。
- **就算 .so 在位，也 dlopen 不成功**。`common.sh` 的 LDFLAGS 是 `-Wl,--as-needed --static -static -Wl,--strip-all`，lxtask 又叠加 `LDFLAGS="-static "`，**通篇没有 `-rdynamic` / `--export-dynamic`** → 静态二进制没有动态符号表 → dlopen 的 loader 解析不到 `gdk_pixbuf_*` 符号。

结果：loader 表为空 → `gdk_pixbuf_get_file_type()` 返回 `GDK_PIXBUF_UNKNOWN` → `gdk_pixbuf_new_from_file()` 返回 NULL → GTK 画空框。**图标「缺失」，实际是「找不到解码器」**。

这个结论在 awesome 侧已经定案过（`pixbuf-self-decode.md`：静态构建里 loader 模块表不会装配），所以才被迫给 lgishim 自己写了 PNG/JPEG/XPM 自解码器。同一套 gdk-pixbuf，同样问题。

#### 3) 但要划清边界：gdk-pixbuf 只是其中一层

修好 loader，图标也未必出来，还有几个**独立**的问题：

- **没有图标数据**：`/usr/share/icons/hicolor` 只有 index.theme 和目录骨架，0 个 png/svg（`hicolor-icon-theme` 本来就只带骨架，真图标来自继承它的图标集，一个都没装）
- **没有主题 / 图标名来源**：没有 settings.ini / gtkrc，`gtk-theme-name` / `gtk-icon-theme-name` 拿不到值
- **GTK2 编译期 prefix 烤死**：见二.2

#### 4) 当时还没验证的一件事

上面第 2 点里「loader 目录实际状态」在本机没核实过 —— 历史 lxtask 构建在 `/mnt2/_misc2-2/_lxde/`，当前机器没有。容器里 `builder-obox`、`builder-awe` 两个 `alpine-builder-gtk224` 都开着，可进去确认 loader 目录 + `pixbuf-loaders.cache` + `pixbuf-loader.pc` 实际内容、`nm -D` 看二进制有无动态符号表。

### 2. 主题：prefix 烤死的关系、当前默认值、软链接调试、怎么改

**问**：

> 另外主题这块呢，识别不到，GTK2 编译期 prefix 烤死，与这个有关系是吧？它当前识别的默认值是啥？是否通过软链接的方式调试呢？如果要达成主题可以识别可用，要怎么改？

**答**：

#### 1) 是的，prefix 烤死直接就是主题找不到的原因

主题根目录是这么拼出来的（`gtk/gtkrc.c:459-473`，`gtk_rc_get_theme_dir`）：

```c
var = g_getenv ("GTK_DATA_PREFIX");
if (var)
  path = g_build_filename (var, "share", "themes", NULL);
else
  path = g_build_filename (GTK_DATA_PREFIX, "share", "themes", NULL);
```

`GTK_DATA_PREFIX` 是宏，配出来的值就是 `/usr/local`（`u-gtk/build.sh:122` 是 `./configure --enable-static`，**没给 `--prefix`**；`strings /usr/lib/libgtk-x11-2.0.a` 只出现 `/usr/local`、`/usr/local/etc`、`/usr/local/lib`、`/usr/local/share/locale`，没有 `/usr`）。

所以 GTK2 找的是 **`/usr/local/share/themes/<name>/gtk-2.0/gtkrc`**，而 Alpine 把主题装在 `/usr/share/themes/`。差一层目录，全部落空。

#### 2) 当前识别的默认值（写死在 `gtk/gtksettings.c`）

```
gtk-theme-name        默认 "Raleigh"   ← gtksettings.c:315
gtk-icon-theme-name   默认 "hicolor"   ← gtksettings.c:325
```

所以不是「没有主题名」。**名字有值，是路径不对**。GTK2 拿 "Raleigh" 去 `/usr/local/share/themes/Raleigh/gtk-2.0/gtkrc` 找，找不到 → 回退**内置 Raleigh 默认样式**（GTK 库自己带的灰色系统默认），这就是看到的那个样子 —— 看起来「认不出主题」，实际是「回退到内置默认」。

#### 3) 默认 rc 文件的完整搜索顺序（`gtk/gtkrc.c:514-550`）

1. `GTK2_RC_FILES` 环境变量 —— **整表替换**，注意是 `GTK2_RC_FILES`，不是 GTK3 的 `GTK_RC_FILES`
2. 否则 `/usr/local/share/gtk-2.0/gtkrc`（烤死前缀，**不读环境变量**）
3. `g_get_system_config_dirs()` + `/gtk-2.0/gtkrc` → 即 `/etc/gtk-2.0/gtkrc`（受 `XDG_CONFIG_DIRS` 影响）
4. `/usr/local/etc/gtk-2.0/gtkrc`
5. `$HOME/.gtkrc-2.0`

#### 4) 软链接能调试，但有更轻的三档，优先序如下

| 手段 | 代价 | 说明 |
|---|---|---|
| `GTK_DATA_PREFIX=/usr` | 零重编、零拷贝 | 只改主题根 → `/usr/share/themes`。**最省事的验证手段**，但只影响主题根，不影响第 3 节第 2 项 fallback gtkrc |
| `GTK2_RC_FILES=/usr/share/themes/<name>/gtk-2.0/gtkrc` | 零重编 | 直接喂 rc 文件，**完全绕过主题名查找**，可单独验证某个主题文件本身对不对 |
| `~/.gtkrc-2.0` 里 `include ".../gtkrc"` | 零重编 | 用户级，搜索顺序最后一位但一定会被查 |
| 软链接 `ln -s /usr/share/themes /usr/local/share/themes` | 改文件系统 | 能用，但 `/usr/local/share` 里还有 `locale`、awesome 自己的主题，整目录挂会有覆盖风险；逐个主题建软链接更安全 |

#### 5) 要真正可用，得动四层

1. **数据层**：得装真实 GTK2 主题（含 `gtk-2.0/gtkrc`）。openbox 那 9 个主题不行 —— 目录里只有 `openbox-3/`，没有 `gtk-2.0/gtkrc`，GTK 应用认不出来。
2. **查找层**（三选一）：`GTK_DATA_PREFIX=/usr` → 软链接 → 重编 GTK2 加 `--prefix=/usr`（代价最大，牵动所有已构建 GTK2 组件，且和 `/usr/local/static/<comp>` 隔离模型冲突）。
3. **名称层**：让 `gtk-theme-name` 拿到你装的主题名。候选位置：`GTK2_RC_FILES`、`~/.gtkrc-2.0`、`/etc/gtk-2.0/gtkrc`。**订正：原写的是 `/etc/gtk-2.0/settings.ini`、`~/.config/gtk-2.0/settings.ini`，实测两个都不生效 —— GTK 2.24 根本不读 `settings.ini`，见 4.2(a)**。
4. **引擎层（隐藏坑）**：主题 gtkrc 里如果有 `-engine " Clearlooks "` 这类指令，引擎是 `<prefix>/lib/gtk-2.0/<version>/engines/*.so`（`gtk_rc.c:402/404`），**又是一次 dlopen**，静态构建下同 gdk-pixbuf loader 的毛病。所以选主题时要挑 **gtkrc 里不带 `-engine` 指令的**。另外 `u-gtk/build.sh:108` 带的是 `--disable-modules`，这个对引擎加载的影响未实测。

#### 6) 一个容易搞混的点

lxtask 自己的 `--prefix=$TARGETPATH`（`/usr/local/static/lxde`，`Dockerfile:265`）**跟主题查找无关**，那只决定 lxtask 二进制装到哪。烤死的是 **GTK2 库自己的 prefix**（`/usr/local`）。两者不是一个东西。

### 3. musl 下编译的 lxtask 在 ubt22 环境下能用 gtk2 主题吗

**问**：

> 主题那块，musl下编译的lxtask在ubt22环境下能用gtk2主题吗

**答**：

能跑，但结论分两半：**主题「认得到」，但「出得了效果」的只有纯 rc 主题**。而且 musl/glibc 这层跟问题完全无关。

#### 1) musl 这层不参与

lxtask 是全静态（`ldd` → Not a valid dynamic program），musl 打包在二进制里，主机 libc 不参与任何符号解析；X11 协议 ABI 稳定。所以 musl 静态二进制的 lxtask 在 ubt22 上照跑。真正决定主题的只有**两件主机相关的事：路径、dlopen**。

#### 2) 路径：还是烤死前缀那套，跟发行版无关

- 烤死 `/usr/local` → 查 `/usr/local/share/themes`
- 实测 ubt22：**`/usr/local/share` 存在，`themes` 子目录不存在**
- 加 `GTK_DATA_PREFIX=/usr` 或写 `~/.gtkrc-2.0` → 就能找到。这条在 ubt22 上通

#### 3) ubt22 实际有什么主题

（`docker-hdmi-desktop-desktop-1`，Ubuntu 22.04.5）

- `/usr/share/themes` 26 个目录，**只有 4 个带 `gtk-2.0/gtkrc`**：Raleigh / Greybird / Greybird-dark / MurrinaChrome
- openbox 那批（Artwiz-boxed、Bear2、Clearlooks、Natura、Onyx、Orang…）**没有 `gtk-2.0/gtkrc`**，GTK 认不出
- 无 `/etc/gtk-2.0/settings.ini`、无 `~/.config/gtk-2.0/settings.ini` → `gtk-theme-name` 停在编译默认 **"Raleigh"**

#### 4) 出不出效果：分档

| 主题 | `engine` 指令数 | 静态构建下的实际效果 |
|---|---|---|
| Raleigh | **0**（gtkrc 只有注释） | 找到即「生效」，但等于内置默认灰色 → **视觉零变化** |
| Greybird / Greybird-dark | 30 | murrine 加载失败，**优雅降级**：gtkrc 里 947 行非 engine 的 style/widget 规则照吃 → 颜色/字号/边框宽度生效，圆角/渐变/阴影不生效 |
| MurrinaChrome | 6 | 同上，降级 |

两个事实叠起来：

- murrine 引擎走 `<prefix>/lib/gtk-2.0/<ver>/engines/*.so` dlopen（`gtk_rc.c:402/404`），静态二进制无 `-rdynamic` → 加载失败
- **这台 ubt22 引擎目录里只有 `libpixmap.so`，murrine 根本没装** —— 就算用动态 GTK2 的应用，在这台机器上也加载不了 murrine。所以这不是 musl 的锅，是环境本来就缺引擎

#### 5) 图标这层，ubt22 也救不了

有意思的对比：ubt22 的 PNG/JPEG **是编进 `libgdk-pixbuf` 的**（`ldd` 显示直接链接 `libpng16.so.16`、`libjpeg.so.8`；loaders 目录里只有 ani/bmp/gif/icns/ico/pnm/qtif/svg/xpm，**没有 png.so / jpeg.so**）。

但那是**主机的 glibc 版库**，帮不上我们二进制里自带的那份 —— 我们的 PNG/JPEG 是独立的 `libstaticpixbufloader-*.a`，没链进 lxtask。所以图标在 ubt22 上照样不显示，跟主机有无 loader 无关。

#### 6) 要真拿到主题视觉，三条路

1. **带一个纯 rc 主题**（gtkrc 里不含任何 `engine` 指令，只用 `style` / `font_name` / `border` / `bg` 等纯 rc 属性，Emacs 风格）→ 零依赖，静态下 100% 生效。**最推荐**
2. **解决引擎 dlopen**：链接加 `-Wl,--export-dynamic` 导出动态符号表 + 把 murrine engine .so 装到 `/usr/local/lib/gtk-2.0/2.10.0/engines/`。代价：重编 lxtask，且 glibc 版引擎 .so 要跟静态 musl 二进制的导出符号对上，风险不小
3. **放弃全静态**，动态链 GTK2 —— 那就不叫静态构建了

---

**一句话**：musl → ubt22 跑没问题；主题加个 `GTK_DATA_PREFIX=/usr` 就「认得到」，但真正能出效果的只有纯 rc 主题，Greybird 类会降级成半成品，murrine 这台机子压根没装；图标是另一条独立的死路。

### 4. greybird主题呢

**问**：

> greybird主题呢

**答**：

真跑了。Greybird 在静态 musl GTK2 下：**能识别、能部分生效、但视觉降级**。

#### 1) 实验

在 builder-obox 编了一个 36M 静态 GTK2 测试程序（`ldd` = not a dynamic executable，`-rwxr-xr-x`），`docker cp` 进 `docker-hdmi-desktop-desktop-1`（Ubuntu 22.04.5，带 Xvfb + scrot），跑了三种配置截图对比。

编译要点：LIBS0 整体包在 `-Wl,--start-group ... -Wl,--end-group` 里，**且 `-lXinerama -lXfixes -lXrandr` 必须在 group 内**（放外面会剩 21 个 `XFixes*` / `XRR*` undefined）。lxtask 脚本能链过是因为它源码直接引用 `gdk_*`。

#### 2) 关键发现

**(a) `settings.ini` 完全无效 —— GTK2 根本不读它（订正 2.5 第 3 条）**

`HOME=/tmp/hB` 里写了 `~/.config/gtk-2.0/settings.ini`（`[Settings]` + `gtk-theme-name = "Greybird"`），程序回读仍是 **`gtk-theme-name=Raleigh`**。

原因：`grep -rln settings.ini /tmp/gtk/gtk /tmp/gtk/gdk` → **空**。GTK 2.24 源码里压根没有 `settings.ini` 这个字符串，`GTK_PATH_SETTINGS` 也不存在。**settings.ini 是 GTK3 的机制**，GTK2 只读 gtkrc。

能用的注入方式是 `GTK2_RC_FILES=/tmp/myrc`（内容 `gtk-theme-name = "Greybird"`）→ 回读 **`gtk-theme-name=Greybird`** ✓

**(b) 补上了本张末尾挂着的待实测项 (a) —— dlopen 失败的真实报错**

```
GModule-CRITICAL: g_module_symbol: assertion 'module != NULL' failed
GModule-CRITICAL: g_module_close: assertion 'module != NULL' failed
```

**这就是 lxappearance 当年死掉的那个 gmodule 错误**，同一根因：静态二进制无动态符号表 → `g_module_open` 失败。lxappearance 的挂掉和 lxtask 的 loader 失效是同一条根。

**(c) Greybird 的 30 条 engine 指令全挂**

| 项 | 数据 |
|---|---|
| gtkrc 里 `engine "murrine"` | 27 处 |
| gtkrc 里 `engine "pixmap"` | 3 处 |
| `^style ` 块 | 49 个 |
| 非 engine 有效行 | 947 行 |
| gtkrc 里位图引用 | **0 个**（不碰 gdk-pixbuf） |
| 运行时报 | `Unable to locate theme engine in module_path: "murrine"` ×34、`"pixmap"` ×4 |

#### 3) 截图对比

`default` 12477B / `Greybird` 12253B，md5 不同 —— **有真实变化，但只有半条**：

- Greybird 的 `bg_color:#CECECE` 等**非 engine 属性生效**了：窗口底色变浅暖灰、菜单栏变无边框扁平
- 按钮**丢失全部 bevel / 渐变 / 浮雕**（那些是 murrine 画的）—— 退化成扁灰矩形

#### 4) 还有两件环境侧的事

- 这台 ubt22 的引擎目录里**只有 `libpixmap.so`，murrine 根本没装** → 就算动态 GTK2 应用，在这台机上也加载不了 Greybird
- 该 ubt22 的 `libgdk-pixbuf` 把 PNG/JPEG **编进库内**（`ldd` 直链 `libpng16.so.16` / `libjpeg.so.8`；loaders 目录无 png/jpeg.so）—— 跟 Alpine 静态构建「PNG/JPEG 是独立 `libstaticpixbufloader-*.a`」机制相反

#### 5) 结论

Greybird 这种 murrine 系主题在静态构建下 = **配色能用、造型没了**。想要完整主题视觉，要么挑**纯 rc 主题**（无 `engine` 指令，Greybird 的 947 行证明了普通 `style` / `widget` 属性照常工作），要么走 `-Wl,--export-dynamic` + 补 murrine .so（未实测）。
