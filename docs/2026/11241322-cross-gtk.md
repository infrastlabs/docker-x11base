### 1、xdpyprobe 交叉缺 X11：修复+依赖清单（2026-11-25 19:01）

方案二（xx-cross）首次全平台 CI 实跑（`--platform linux/amd64,linux/arm64,linux/arm`），`tiger` stage 的 xdpyprobe 在 arm/v7 挂。native amd64 通过——典型的"交叉 sysroot 缺依赖，native 靠镜像烘焙才过"。

#### 1.1、现象：armv7 交叉缺 X11 头（2026-11-25 19:01）

失败点 `Dockerfile:63` 的 RUN（xdpyprobe 编译+校验+upx）。对比 native 与 arm/v7：

| 平台 | buildx step | 编译/链接 | 结果 |
|---|---|---|---|
| `linux/amd64`（native） | `#77 [linux/amd64 tiger 3/3]` | `xx-clang … -c -o xdpyprobe.o` → `xx-clang -static … -lX11 -lxcb -lXau -lXdmcp -o xdpyprobe` | ✅ `1016040 → 603692 59.42% linux/amd64`，`Packed 1 file` |
| `linux/amd64->arm/v7`（cross） | `#139 [linux/amd64->arm/v7 tiger 3/3]` | `xx-clang … -c -o xdpyprobe.o xdpyprobe.c` | ❌ `xdpyprobe.c:23:10: fatal error: 'X11/Xlib.h' file not found` → `make Error 1` → upx `FileNotFoundException` exit 1 |

arm64 同样会挂（其 xdpyprobe `#161` 被 arm/v7 失败 cancel，没跑到，但 sysroot 同样只有 musl/gcc）。

#### 1.2、根因：sysroot 未装 X11（2026-11-25 19:01）

`base` stage 的初始化只给交叉 sysroot 装了 musl/gcc，没装 X11：

```dockerfile
# base stage（第 10-11 行）
RUN apk update; apk add gawk git; \
  xx-apk add musl-dev gcc
```

- `xx-apk` 经 `xx-info env` 感知 `TARGETPLATFORM`，把包装进对应 sysroot（`/armv7-alpine-linux-musleabihf/`、`/aarch64-alpine-linux-musl/`）。
- native amd64 之所以过：`alpine-builder-gtk224-2` 镜像**烘焙了 X11**（dev+static 都在 `/usr/include/X11`、`/usr/lib/*.a`），`xx-clang` native 直接找到。
- arm/v7 的 sysroot 是 xx-cross 新建的空 sysroot，只有 musl/gcc → `Xlib.h` 找不到。

而 xdpyprobe 的 Makefile 链接 `-lX11 -lxcb -lXau -lXdmcp`，编译要 `X11/Xlib.h`——两样 sysroot 都没有。Dockerfile 里本有补 X11 的两行，但**早被注释掉**（60-61 行）：

```dockerfile
# RUN apk --no-cache add make clang
# RUN xx-apk --no-cache add gcc musl-dev libx11-dev libx11-static libxcb-static
```

#### 1.3、qemu 能跑因原生、交叉缺依赖（2026-11-25 19:01）

`buildx.sh` 的 `compile="alpine-compile"` 上方注释 `#2=qemu-former; 3=xx-cross`——已从 qemu 模式换到 xx-cross 模式，xdpyprobe 没跟着适配：

| | qemu 模式（旧，`alpine-compile-2`） | xx-cross 模式（现在，`alpine-compile-3`） |
|---|---|---|
| stage 跑在哪 | **真 arm/v7 容器**（qemu 模拟） | **amd64** 上 `xx-clang` 交叉 |
| 编译器 include 路径 | 容器**原生** `/usr/include/X11`（镜像烘焙，全有） | **sysroot** `/armv7-.../usr/include`（只有显式 `xx-apk` 装的） |
| sysroot 内容 | 不适用（无 sysroot 概念） | 只有 `xx-apk add musl-dev gcc` 装的 musl/gcc |
| `make` 找 `Xlib.h` | 原生自带 → 过 | sysroot 无 → 挂 |

- **qemu 下**：arm/v7 容器自带 X11（dev+static），`make` 直接找到 → 所以"关掉也能跑"。
- **xx-cross 下**：sysroot 靠显式 `xx-apk` 填充；那两行注释掉的 `xx-apk` 在 qemu 时代可有可无，换模式后变成**必需**——注释掉就成了坑。

#### 1.4、修复：补装 X11 dev+static（2026-11-25 19:01）

make 前补装 X11 dev+static 到当前平台 sysroot；同时把 `'; '` 改 `&&`（原 make 失败被 upx 掩盖，错误归因错到 upx，难定位）：

```dockerfile
COPY src/xdpyprobe /tmp/xdpyprobe
RUN xx-apk add --no-cache libx11-dev libx11-static libxcb-dev libxau-dev libxdmcp-dev && \
  CC=xx-clang make -C /tmp/xdpyprobe && \
  xx-verify --static /tmp/xdpyprobe/xdpyprobe && \
  upx /tmp/xdpyprobe/xdpyprobe
```

**`xx-apk` 包清单依据**（builder-g224 内一个正常 armv7 sysroot 实测已装包）：

| 包 | 提供物 |
|---|---|
| `libx11-dev` | `X11/Xlib.h` 等头 |
| `libx11-static` | `libX11.a`（libx11 的 `.a` 单独在 `-static` 包） |
| `libxcb-dev` | `libxcb.a`（xcb/xau/xdmcp 的 `.a` 在各自 `-dev`，无 `-static` 变体） |
| `libxau-dev` | `libXau.a` |
| `libxdmcp-dev` | `libXdmcp.a` |

`xorgproto` 作依赖自动拉。native amd64 已装全套 → `xx-apk add` 幂等零影响（三平台都安全）。

#### 1.5、排查坑：长跑容器复现不出（2026-11-25 19:01）

本机 `builder-g224`（`alpine-builder-gtkmm224-2`）是 **Up 4 天的长跑容器**，其 armv7 sysroot 早被手动补过 X11（实测已装 `libx11-dev/libx11-static/libxcb-dev/libxau-dev/libxdmcp-dev`），`make` 在本地**能过** → **本地复现不出 CI 失败**，只有 CI 的干净 sysroot 才暴露。

- 教训：排查交叉编译问题**别信长跑容器**（sysroot 被污染），要以 CI 干净 sysroot 为准。
- 本地验证 `xx-apk` 拉包还受沙箱网络限制（armv7 APKINDEX fetch `rc=7`），无法端到端复现 CI；但包名已由本地 sysroot 已装列表确认。
- 顺带确认 `xx-apk` 包装器：`xx-info env` 取 `TARGETOS/TARGETARCH`，cross 装进 sysroot、native 装进 `/`（已装即幂等）。

#### 1.6、问答：开关/qemu/烤镜像辨析（2026-11-25 19:24）

**问 1**：是不是 `buildx.sh` 那边开关关掉了，相关依赖没装，构建脚本又有，然后就错了？但奇怪的是之前的 qemu 模式也可以呀，关掉也能跑。

**答 1**：不是开关关掉导致的，而且"之前 qemu 能跑"正好对上根因。

第一，**不是开关**。xdpyprobe 那段 RUN 不受任何 `COMPILE_*` 开关控制，无条件执行。`tiger` stage 里 xdpyprobe 前面那段（`x-tigervnc/build.sh cache`）才受 `COMPILE_TIGER` 控制，日志显示它走的是 `doMake` 分支（开关是 yes），跑完了；失败的是后面 xdpyprobe 那条**独立的、无开关的 RUN**。

第二，**qemu 为何能跑**。`buildx.sh` 的 `compile="alpine-compile"` 上方注释 `#2=qemu-former; 3=xx-cross`——已从 qemu 模式换到 xx-cross 模式，xdpyprobe 没跟着适配：

| | qemu 模式（旧，`alpine-compile-2`） | xx-cross 模式（现在，`alpine-compile-3`） |
|---|---|---|
| stage 跑在哪 | **真 arm/v7 容器**（qemu 模拟） | **amd64** 上 `xx-clang` 交叉 |
| 编译器 include 路径 | 容器**原生** `/usr/include/X11`（镜像烘焙，全有） | **sysroot** `/armv7-.../usr/include`（只有显式 `xx-apk` 装的） |
| sysroot 内容 | 不适用（无 sysroot 概念） | 只有 `xx-apk add musl-dev gcc` 装的 musl/gcc |
| `make` 找 `Xlib.h` | 原生自带 → 过 | sysroot 无 → 挂 |

qemu 下 arm/v7 容器自带 X11（dev+static），`make` 直接找到 → 所以"关掉也能跑"。xx-cross 下 sysroot 靠显式 `xx-apk` 填充；那两行注释掉的 `xx-apk`（Dockerfile 60-61）在 qemu 时代可有可无，换模式后变成**必需**——注释掉就成了坑。

**问 2**：意思就是交叉编译模式，直接在那个基础镜像里面做依赖库安装还不行，得构建的时候动态安装是吧？

**答 2**：不是"不行"，是**有代价**。

**为什么不能简单烤进基础镜像（amd64 那个）**：xx-cross 下 `base` 镜像是 amd64 的（`FROM --platform=$BUILDPLATFORM`），里面没有 armv7/arm64 的库。交叉要的 armv7 X11 头/`.a` 平时不在 amd64 镜像里，是构建时 `xx-apk` 现拉进 sysroot 的。所以"烤进基础镜像"对 native 那份 X11 有效（native 本来就有），对**交叉 sysroot 无效**——sysroot 是构建期才生出来的，基础镜像里没这东西。

**那能不能把 sysroot 烤进基础镜像？能，但有代价**（可在构建 builder 镜像时预建 armv7/arm64 sysroot 并装满常用静态库）：

| | 烤进镜像 | 动态装（现状） |
|---|---|---|
| 编译期网络 | 零（已烤） | 每平台拉一次（有层缓存，可接受） |
| 基础镜像体积 | **膨胀**（每 sysroot 几十 MB `.a`+头，×多架构） | 瘦 |
| 依赖更新 | **重烤整个 builder 镜像** | 改 build.sh 一行 |
| 耦合 | 依赖绑死在某个 gtk224 镜像版本 | 依赖跟着组件走 |
| 多余依赖 | 装一堆用不到的 | 每组件只装自己的 |

**推荐做法**（不是二选一）：保持动态装，但**下沉到 build.sh + 收敛成共享预设**，而不是每组件在 Dockerfile 散写。仓库现状已是这路子——`common.sh` 有 `xx_cross_init/xx_la_fix/xx_meson_crossfix`，各 build.sh 用 `xx-apk` 声明自己的 sysroot 依赖（`x-xrdp`/`x-xbindkeys`/`xcompmgr`/`suckless` 等已如此）。

xdpyprobe 之所以漏，因为它是**唯一不走 build.sh 的裸 `make`**（全 Dockerfile 就它一个），没接上这套机制。三个选项：

1. 给 xdpyprobe 包一个 `build.sh`（走 `xx_cross_init` + `xx-apk`），Dockerfile 退化成 `sh /src/x-xdpyprobe/build.sh`，与其它组件一致。
2. 最小改动：就在它那条 RUN 里补 `xx-apk`（能用，但属于"写在 Dockerfile 里"）。
3. 把 X11 静态包清单提成 `common.sh` 里一个变量（如 `XX_X11_PKGS`），各 X11 组件引用，免得 6+ 处重复。

**拍板（2026-11-25 19:51 用户）**：选 **2 + 3**。xdpyprobe 特殊，留在 Dockerfile（不包 build.sh）；同时把 X11 静态包清单提成 `common.sh` 的 `XX_X11_PKGS` 共享变量，供各 X11 组件引用。

#### 1.7、落地：依赖清单+通盘检查（2026-11-25 19:51）

##### 1.7.1、落地的两处改动

**① `common.sh`——新增共享清单 `XX_X11_PKGS`**（`xx_cross_init` 前）：

```sh
export XX_X11_PKGS="libx11-dev libx11-static libxcb-dev libxcb-static libxau-dev libxdmcp-dev"
```

X11 静态库/头的**公共最小集**。用法 `xx-apk add $XX_X11_PKGS [<本组件额外包>]`；native 已装 → 幂等零影响。`.a` 归属：libx11 在 `libx11-static`；xcb/xau/xdmcp 在各自 `-dev`（无 `-static` 变体）；xorgproto 作依赖自动拉。

**② `Dockerfile`——xdpyprobe 复用共享清单**（tiger stage，仍留 Dockerfile，不包 build.sh）：

```dockerfile
RUN . /src/common.sh && \
  xx-apk add --no-cache $XX_X11_PKGS && \
  CC=xx-clang make -C /tmp/xdpyprobe && \
  xx-verify --static /tmp/xdpyprobe/xdpyprobe && \
  upx /tmp/xdpyprobe/xdpyprobe
```

`source /src/common.sh` 与全部 build.sh 写法一致（`x-dbus`/`u-gtk`/`w-tint2` 等均 `source /src/common.sh`），无新副作用；把原先内联的字面清单换成 `$XX_X11_PKGS`，避免共享变量成死代码。

**commit**：`common.sh` → `fd211acb`；`Dockerfile` → `a2a753a9`（文档 1.6 经并行代理 `c3700c33` 带入）。

##### 1.7.2、通盘依赖检查结论

扫全 Dockerfile stage：**只有 xdpyprobe 一处是裸 `make -C`**（不经 build.sh、不走 `xx_cross_init`），其余组件全部 `sh /src/<comp>/build.sh <target>` → 经 `common.sh` 接上交叉机制。所以 xdpyprobe 是孤例，非系统性问题。

仓库**已有**的交叉依赖通用机制（在 `common.sh` / 各 build.sh，不在 Dockerfile）：

| 机制 | 作用 |
|---|---|
| `xx_cross_init()` | is-cross 时生成 meson cross-file + 导出 `XX_SYSROOT/XX_CROSS_FILE/XX_TRIPLE/XX_MARCH` |
| `xx_la_fix()` | 交叉 `.la` libdir 改 sysroot 相对（libtool 原生 `.a` 路径根因） |
| `xx_meson_crossfix()` | meson 交叉 native 依赖头泄漏修复 |
| build.sh 内 `xx-apk add` | 各组件声明自己的 sysroot 依赖（`x-xrdp`/`x-xbindkeys`/`xcompmgr`/`suckless`/`fluxbox`/`x-xrandr`/`x-x11vnc` 等已用） |

依赖三条来源（按优先级）：① `xx-apk add`（有预编译目标包，最快）② `b_deps` 源码交叉建进 sysroot（无 apk 包的，如 imlib2/fontconfig/librsvg）③ **烘焙在 builder 镜像**（仅 native 有效，交叉视为"不可用"，别依赖）。

##### 1.7.3、通用组装思路（供后续组件遵循）

1. **别在 Dockerfile 散写依赖**：所有编译走 `build.sh`，Dockerfile 退化为 `sh /src/<comp>/build.sh <target>`。裸 `make`（如 xdpyprobe）是历史孤例，新组件别仿。
2. **sysroot 依赖在 build.sh 内 `xx-apk add` 声明**：X11 类用 `$XX_X11_PKGS` 打底 + 本组件额外包（`libxext-dev`/`libxrender-dev`/`libxcomposite-dev`/`libxfixes-dev`/`libxrandr-dev`/`libxdamage-dev`…），把原先 6+ 处重复的 `.a` 归属清单收敛到 `common.sh` 一处。
3. **无 apk 包的依赖**走 `b_deps` + `xx_cross_init` 源码交叉建进 sysroot，装完对相关 `.la` 跑 `xx_la_fix`。
4. **native 幂等**：所有 `xx-apk`/交叉分支守 `[ -n "$XX_CROSS_FILE" ]` 或依赖 `xx-apk` 自身的 cross 感知，native 已装=零影响。

### 2、GTK2 应用交叉失败：烤基础镜像方案（2026-11-25 21:49）

xdpyprobe 修好后 CI 复跑，整体仍 `exit 1`——挂在 **pcmanfm arm/v7**（`Dockerfile:406`）。本轮失败的是**一批 GTK2 应用**（`v-lxde`/`v-gpicview`/`v-geany`/`v-engrampa`/`v-pcmanfm`），**arm/v7 + arm64 双双挂**。与 xdpyprobe 不同，这不是单点 bug，而是这批组件的交叉适配尚未收口。

#### 2.1、失败三分类与总根因（2026-11-25 21:49）

失败模式**不止一种**，分三类：

| 类 | 组件 | 报错 | 根因 |
|---|---|---|---|
| **A. 缺头/缺工具** | lxappearance（v-lxde） | `libintl.h not found` + glib `static_assert(sizeof(unsigned long long)==sizeof(unsigned long))` | 编译用了 **native `/usr/include/glib-2.0`** 而非 sysroot（报错路径可证）；且缺 gettext/libintl |
| | engrampa（v-engrampa） | `glib-compile-schemas not found` | 交叉下缺该宿主工具 |
| **B. pkg-config "not met"** | lxtask（v-lxde） | `glib-2.0 >= 2.14.0 not met` | build.sh 设了 `PKG_CONFIG_LIBDIR`，但**本地能找到、CI 找不到** → CI 干净 sysroot 的 gtk2 栈与本地长跑容器不一致 |
| | gpicview（v-gpicview） | `gtk+-2.0 >= 2.12.0 not met` | 同上 |
| | geany（v-geany） | `gtk+-2.0/glib-2.0/gio-2.0 not met` | 同上 |
| | pcmanfm（v-pcmanfm，libfm） | `gio-unix/glib/gtk+-2.0/pango/cairo not met` | 同上 |
| **C. 连锁失败** | geany | + `make: No rule to make target 'libctags.la'` | configure 失败后 make 找不到中间产物 |
| | pcmanfm | + `C compiler cannot create executables` | libfm 没产出 `.a`/`.pc` → pcmanfm configure 探测编译器失败 |

**总根因（已定位，2026-11-25 21:54）**：**u-gtk 没为交叉 sysroot 跑** → sysroot 缺整条 gtk2 栈 → 这些 GTK2 应用 configure 找不到 gtk/glib。qemu 旧模式 vs 交叉新模式的关键差异：

| | qemu 旧模式 | 交叉新模式 |
|---|---|---|
| 构建发生在哪 | **arm 镜像/容器内**（qemu 模拟，原生 for-arm） | **amd64 上**（`FROM --platform=$BUILDPLATFORM`），`xx-clang` 交叉 |
| gtk2 栈在哪 | 镜像**原生路径** `/usr/lib`（u-gtk 在镜像里跑，烤进 arm 镜像） | 须**交叉建进 sysroot** `/armv7-.../usr/lib`（动态） |
| configure 找 gtk | 原生 `/usr/lib` 有 → 过 | sysroot **没有**（u-gtk 没为交叉跑）→ `not met` |

- `u-gtk/build.sh` **有交叉支持**（16 处 `xx_cross_init`/`XX_SYSROOT`）——它**能**交叉建 gtk2 进 sysroot。
- 但 Dockerfile 里 pcmanfm/lxde 这些 stage 是 `FROM base`，**没跑 u-gtk**；`base` stage 只 `xx-apk add musl-dev gcc` → sysroot 起步只有 musl/gcc，**无 gtk2**。
- 本地 builder-g224 sysroot 有 gtk2（之前 u-gtk 交叉跑过/手动填过）→ **本地复现不出，CI 干净 sysroot 才暴露**。

**关键判断**：

- 本地 builder-g224（长跑容器）的 armv7/arm64 sysroot **有完整 gtk2 栈**（实测 libgtk-x11.a=ARM EABI5、libglib-2.0.a=ARM EABI5、pkg-config 交叉 LIBDIR 下能找到 glib 2.70.5/gtk+-2.0）→ **本地复现不出，CI 干净 sysroot 才暴露**（与 xdpyprobe 同一坑：别信长跑容器）。
- 这 6 个都是 **GTK2 应用**，依赖整条 gtk2 栈（glib/gtk/pango/cairo/atk/gdk-pixbuf）。要交叉过，**前提是 gtk2 栈先交叉建进 sysroot**——属方案一/二的大头，非单点 bug。
- 这 5 个 build.sh 各有 `PKG_CONFIG_LIBDIR`（设成 sysroot，与能过的写法一致）+ `XX_CROSS_FILE` 守卫，但**都没用 `xx_cross_init`**（能过的 openbox 用了）——交叉环境建立方式不统一，是排查难点之一。

**待定方向（工作量不小，优先级待拍板）**：

- **① 逐个适配**（方案一路线）：每个 build.sh 补交叉（像 openbox/fluxbox），工作量大、各有细节（libintl/glib-compile-schemas/libctags/编译器探测）。
- **② 先禁用这些组件的交叉**：CI 里 arm64/armv7 的 `COMPILE_LXDE/PCMANFM/GEANY/ENGRAMPA/GPICVIEW=no`，让 CI 先绿，交叉适配后续啃。
- **③ 只修 pcmanfm**（挂它导致整局 `exit 1`），其余先容忍。
- **④ B 类根因已定位 = u-gtk 没为交叉跑**：修法是让 u-gtk 先交叉建 gtk2 进 sysroot（一次建好、所有 GTK2 应用共享，同 openbox/fluxbox 消费方式），通了能一次性解 B 类 4 个组件（lxtask/gpicview/geany/pcmanfm-libfm）；A 类（libintl/glib-compile-schemas）待 gtk2 栈起来后复验是否连带就解。

#### 2.2、烤镜像体积估算（2026-11-25 22:04）

背景：整体倾向**提前把 gtk2/gtkmm 交叉编译进那两个基础镜像**（`gtk224`/`gtkmm224`）。担心点——gtk/gtkmm 当初独立成基础镜像就因库太大、依赖层多、编译久，若在现有基础镜像里做交叉，**镜像体积会不会翻三倍**。

##### 2.2.1、纯 `.a` 静态库层实测（builder-g224 / builder-mm224，每架构）

| 架构 | gtk2 `.a` | gtkmm `.a` | 小计 |
|---|---|---|---|
| amd64（native `/usr`） | 54 MB | 14 MB | 68 MB |
| arm64（aarch64 sysroot） | 69 MB | 15 MB | 84 MB |
| armv7（EABI5 sysroot） | 45 MB | 10 MB | 55 MB |
| **三架构合计** | **168 MB** | **39 MB** | **≈207 MB** |

- gtk2 清单（~22 个 `.a`）：libgtk-x11/gdk-x11/glib/gobject/gio/gmodule/gthread/pango/pangocairo/pangoft2/cairo/atk/gdk_pixbuf/harfbuzz/freetype/fontconfig/pixman/libpng16/X11/xcb/Xrender/Xext。
- gtkmm 清单（8 个 `.a`）：libgtkmm-2.4/gdkmm-2.4/glibmm-2.4/giomm-2.4/pangomm-1.4/atkmm-1.6/cairomm-1.0/sigc-2.0。
- **源码包不计**（已有独立 tarsrc 缓存层）。

##### 2.2.2、结论：会不会翻三倍

| 方案 | 体积落点 | 基础镜像是否膨胀 |
|---|---|---|
| **动态（方案二现状）** | 交叉 gtk2 建进 **sysroot**（compile stage `alpine-compile-3` 构建期临时生成，按平台各自建、有缓存/可 GC） | **不会**。基础镜像仍 amd64 + 原生 gtk2，交叉产物在 compile stage 临时层，不回灌 |
| **烤进基础镜像** | arm64+armv7 的 gtk2/gtkmm sysroot 预建好烤进 `gtk224`/`gtkmm224` | **会显著涨**：基础镜像已有 amd64 原生栈，再叠 arm64+armv7 两份 `.a` → 接近 3 份，奔 2~3 倍 |

**回答**：按**现在的动态方案**，交叉 gtk2 落在 compile stage 的临时 sysroot，**不回灌基础镜像 → 不会翻三倍**。会翻三倍的是"烤进基础镜像"那条路。若整体倾向提前编译进基础镜像，则要接受在现有基础上**叠加约 207 MB**（三架构纯 `.a`；若同时清掉中间产物 `.o`/`.lo`/源码树，净增量会小于此数，因中间产物通常是 `.a` 的好几倍）。

**待补精确值**：现有 `gtk224`/`gtkmm224` 镜像当前体积 + 其中中间产物占比未量；"清中间产物 + 加三架构 `.a`"后的净体积需再测（已向用户提出可量）。

**sysroot 除 `.a` 外必留的文件**：

| 文件 | 必留 | 原因 |
|---|---|---|
| `.a` | ✅ | 静态链接本体 |

##### 2.4.3、xx-clear.sh 设计（参数化子命令）

```sh
#!/bin/sh
# xx-clear.sh — 交叉基础镜像专用清理（给 gtk224.xx/gtkmm224.xx Dockerfile 调）
# 用法:
#   xx-clear.sh intermediate <prefix>            # 清中间产物，保留 .a/.pc/include/.la
#   xx-clear.sh staticlib <sysroot> [libname...] # 清旧静态库（防串架构污染），无 libname=清全部 lib*.a
set -e
cmd=${1:-}; shift || true
case "$cmd" in
  intermediate)
    prefix=${1:?need prefix}
    find "$prefix" -name "*.o"  -delete 2>/dev/null || true
    find "$prefix" -name "*.lo" -delete 2>/dev/null || true
    find "$prefix" -name ".libs" -type d -exec rm -rf {} + 2>/dev/null || true
    find "$prefix" -name ".deps" -type d -exec rm -rf {} + 2>/dev/null || true
    # 保留: *.a  *.pc  include/  *.la(已 xx_la_fix)
    log "xx-clear: intermediate cleaned ($prefix)"
    ;;
  staticlib)
    sysroot=${1:?need sysroot}; shift || true
    if [ -n "$1" ]; then for l in "$@"; do rm -f "$sysroot"/usr/lib/"$l"; done
    else rm -f "$sysroot"/usr/lib/lib*.a; fi
    log "xx-clear: staticlib cleaned ($sysroot)"
    ;;
  *) echo "usage: $0 {intermediate|staticlib} ..."; exit 1;;
esac
```

##### 2.4.8、基础镜像预烤候选（排除 alpine-builder 已有，2026-11-26 00:01）

###### 2.4.8.1、交叉 linker ld64（机制已定位）

- `xx-clang` 首次交叉编译会 `download_ld64()`（`/usr/bin/xx-clang` L197）拉 `ld64-signed-<os>-<arch>.tar.gz`（从 `LD_MIRRORS`），解出 `/usr/bin/ld64.signed`，软链 `/usr/bin/<target>-ld`。
- **fresh alpine-builder 实测没有** `ld64.signed` / `aarch64-...-ld` / `armv7-...-ld`；builder-g224 有是方案二跑出来的。
- aarch64 + armv7 各一份 → 烤进 `gtk224-3` 后，`gtkmm224-3 FROM gtk224-3` 也继承，一次烤两镜像受益。

###### 2.4.8.2、预烤候选

| # | 项 | 为何通用/值得烤 | 落点 |
|---|---|---|---|
| **1** | **交叉 linker `ld64.signed`**（aarch64 + armv7 各一） | xx-clang 首次交叉必拉；所有交叉编译共用；不变动；每 stage 省重下 | `/usr/bin/ld64.signed` + `/usr/bin/<target>-ld` 软链 |
| **2** | **交叉 sysroot 的 musl 基座**（arm64 + armv7 的 musl libc.a + 头） | 每个交叉 sysroot 起步都要 musl；`xx-apk add musl-dev` 每 stage 重装 | `/arm64-.../`、`/armv7-.../` 的 musl |

###### 2.4.8.3、不值得预烤的（避免过度）

- **XX_X11_PKGS（X11 静态库）**：已在 gtk2 栈构建（b_deps 的 apkdeps）时装进 sysroot → **已随 gtk224-3 烤好**，应用无需再 xx-apk。
- **各应用特有依赖**（openssl/fuse/imlib2/ibus 等）：per-app，非"多处复用不变动"，留在各 build.sh。
- **alpine-builder 已有的**（xx-clang/xx-info/download_ld64 函数/原生工具链）：按范围排除。

###### 2.4.8.4、净结论

除 gtk2/gtkmm 栈本体，**真正值得预烤的是 #1 交叉 linker ld64**——通用、不变动、每 stage 省重下，体积小（aarch64+armv7 各一份）。#2 musl 交叉基座可选（看体积权衡）。ld64 具体体积待 arm64 e2e 时顺带量（备份/alpine-builder 均未含）。

##### 2.4.9、Dockerfile.builder.gtk224.xx：amd64 纳入循环 + 三架构并行/存放分析（2026-11-26 02:47，本轮）

gtk224-3（`FROM alpine-builder`）实测**缺 amd64 静态 gtk2**：base 只有 apk 装的 amd64 gtk2 `.so`（`gtk+-2.0.pc` 日期 2020-12-27），**无自建静态 `.a`**；原 amd64 静态 gtk2 只在旧 `gtk224-2`（`u-gtk full` native 建）。所以 `.xx` 镜像**必须纳入 amd64**，否则 amd64 静态应用链不动。

###### 2.4.9.1、amd64 纳入循环（1d）

- 循环加 `amd64`：`for arch in amd64 arm64 arm/v7`。
- amd64 时 `TARGETPLATFORM=linux/amd64` → `xx_cross_init` 不设 `XX_SYSROOT`（native）→ **两个 xx-clear 加 `[ -n "$XX_SYSROOT" ]` 门**（否则 `xx-clear staticlib ""` 炸）。
- amd64 b_deps native 跑 → 装 `/usr`，与 base apk `.so` 共存（= 原 gtk224-2 行为，已知可用）。

```dockerfile
RUN set -e; \
  for arch in amd64 arm64 arm/v7; do \
    export TARGETPLATFORM=linux/$arch; \
    . /src/common.sh; \
    [ -n "$XX_SYSROOT" ] && sh /src/u-gtk/xx-clear.sh staticlib "$XX_SYSROOT"; \
    sh /src/u-gtk/build.sh b_deps; \
    [ -n "$XX_SYSROOT" ] && sh /src/u-gtk/xx-clear.sh intermediate "$XX_SYSROOT"; \
  done; \
  unset TARGETPLATFORM
```

###### 2.4.9.2、三架构并行 + 独立日志 + 检查点（2d）

- 并行结构（单 RUN 内 `&` + `wait`）：`wait` 只返回最后子进程状态，`set -e` 对 `wait` 不可靠 → **逐 arch 写 rc 文件**再统一判，最后加**产库检查点**。
- 日志：每 arch 一个 `/tmp/gtk-$arch.log`（b_deps 内部 doExec 已落日志，此处再包一层）；失败时 `grep -c "undefined reference\|attempted static link"` 兜底（=0）。
- **资源红线**：b_deps 每架构编译整条 gtk2 栈（峰值内存高）；本机 1.9Gi → 3 路并行大概率 OOM（AGENTS「禁止并行跑多个重构建」）。**本机串行，CI/大内存才并行**。

###### 2.4.9.3、amd64 `.a` 存放：Option B（native `/usr`）推荐（3d）

**Option B（推荐）— amd64 静态 gtk2 装 native `/usr`（原路径）**
- amd64 应用：**Dockerfile 不用改**（继续 native `/usr` pkg-config，原路成熟）。
- 交叉应用：走 sysroot（已在计划内）。
- 优点：零 amd64 应用改动、向后兼容、u-gtk/build.sh native 路径不动（合「少动原 build.sh」）、apk 依赖与自建库同处 `/usr` 无割裂。
- 缺点：两条代码路径（native `/usr` vs sysroot）；base 含 amd64 gtk2（可接受）。

**Option A（统一 sysroot）— amd64 进 `/x86_64-alpine-linux-musl/usr/lib`**
- amd64 应用需 `PKG_CONFIG_LIBDIR`+`PKG_CONFIG_SYSROOT_DIR` 指向 amd64 sysroot → **Dockerfile 必改**。
- 代价：u-gtk native 路径用 `DESTDIR` 装前缀（**改 u-gtk/build.sh native 路径**，违「少动」）；native apk 依赖留 `/usr`，pkg-config 要**同时搜 sysroot + `/usr`**（割裂）；`xx_la_fix` gate 在 `XX_CROSS_FILE`（amd64 不设）→ 需放宽 gate。
- 结论：架构更纯但工作量/风险显著更高；**除非强求统一，否则不推**。

**净结论**：`Dockerfile.builder.gtk224.xx` 改 `for arch in amd64 arm64 arm/v7` + 双 xx-clear 加 `[ -n "$XX_SYSROOT" ]` 门（Option B）；本机串行、CI 才并行；amd64 应用 Dockerfile 无需改。

4. **pangomm 头文件缺失（未解，新卡点）**：pangomm `attrlist.cc:5:10: fatal error: 'pango/pango-markup.h' file not found`；gtkmm configure `Package requirements (giomm-2.4 >= 2.27.93 pangomm-1.4 >= 2.27.1 gtk+-2.0 >= 2.24.0) were not met`——pango 头/PKG_CONFIG 路径在交叉 sysroot 未对齐（`pango/pango-markup.h` 在 `$XX_SYSROOT/usr/include/pango-1.0/pango/`，pangomm 编译未带 `-I$XX_SYSROOT/usr/include/pango-1.0`，或 pango.pc 没被 pangomm configure 找到）。**待查**：pangomm 编译 CPPFLAGS 是否含 pango-1.0 include、`pango.pc` 是否在 sysroot、pkg-config 是否指向 sysroot。

##### 2.6.1、实测结论：ld64 已随重建自动预烤，无需再动手（2026-11-26 13:45，本轮）

**① 编译器 vs 链接器定位**

| | 组件 | 作用 | 是否需预烤 |
|---|---|---|---|
| **编译器** | `xx-clang`（clang） | `.c`→`.o` | 否——alpine-builder 已有 |
| **链接器** | `ld64`（`ld64.signed`/`linux-<arch>-ld`） | 交叉**链接**成最终 ELF | 是——首次交叉时才下载 |

**② 实测：两镜像均已含 ld64**（`docker run --rm` 实测，非推断）

- `alpine-builder-gtk224-3`：`/usr/bin/linux-arm64-ld` **3.5M** + `/usr/bin/linux-armv7-ld` **2.0M**；软链 `aarch64-alpine-linux-musl-ld -> linux-arm64-ld`、`armv7-alpine-linux-musleabihf-ld -> linux-armv7-ld` 齐备；`ld64.signed` 已由 `<target>-ld` 软链方案取代（无需保留）。
- `alpine-builder-gtkmm224-3`：**与 gtk224-3 一致**（`FROM gtk224-3` 继承）。

**③ 为何「自动达成」**

- `gtk224-3` 构建时跑 `u-gtk` 交叉（arm64/armv7）→ `xx-clang` 首调 `download_ld64()`（`/usr/bin/xx-clang` L197，从 `LD_MIRRORS` 拉 `ld64-signed-<os>-<arch>.tar.gz`）→ 解进 `/usr/bin/` 并建 `<target>-ld` 软链 → **该层固化进镜像**。
- `gtkmm224-3 FROM gtk224-3` → 继承，一次构建两镜像受益。
- **镜像里存在 = 下载成功 = `LD_MIRRORS` 本机/CI 可达**（重建时实证，无外网挂死风险）。

**④ 结论**

1. 2.4.8 预烤候选 #1 **已由重建自动达成，无需再动手**；体积成本仅 5.6MB（可忽略）。
2. 每份 `gtk224-3` 自建时仍需下载一次 ld64（不可避免），但**下游所有应用 stage** 消费该镜像时**零下载**——正是「预烤」收益。

##### 2.6.2、预烤候选 #2（musl 交叉基座）细化 + 实测已预烤（2026-11-26 13:59，本轮）

**是什么**：每个交叉目标架构的 **musl 静态基座** = `libc.a`（musl 静态库本体）+ `usr/include`（musl 头）+ `/usr/lib/crt*.o`（启动对象），装进**交叉 sysroot**：

#### 3.1、根因三 bug+缺陷D 与 $WS 修复（2026-11-26 14:46）

##### 3.1.1、根因 A/B/C + 缺陷 D

- **根因 A——路径斜杠（直接致命，CI 铁证）**：`Dockerfile.builder.gtk224.xx:31-34` 循环变量 `arch` 取值含 `arm/v7`，`> /tmp/gtk-$arch.log` 展开成 `> /tmp/gtk-arm/v7.log`，父目录 `/tmp/gtk-arm` 不存在 → 重定向失败，**armv7 分支压根没启动**（`sh build.sh b_deps` 从未运行）。gtkmm224.xx 同病（`/tmp/gtkmm-$arch.log`）。
- **根因 B——`rm -f /tmp/*.log` 误删日志/rc（放大器）**：`u-gtk/xx-clear.sh:51` 的 `rm -f /tmp/*.log /tmp/*.out` 在并行下会删掉**其它分支**正要写/已写的 `/tmp/gtk-<arch>.log`/`.rc`（三路并行共用 `/tmp`）。结果 `cat .rc` 报 No such file，且失败时日志已丢、无法定位。
- **根因 C——并行共享源码树（潜伏污染，必须一并修）**：三棵**绝对路径硬编码**源码树无 per-arch 隔离——`u-gtk/build.sh:195` `/tmp/gtk-cross`、`u-gtk/build.sh:323` `/tmp/murrine-cross`、`u-gtkmm/build.sh`（L32/34/99-177/**L223 `rm -rf /tmp/gtkmm-src`**）`/tmp/gtkmm-src`。arm64 与 armv7 并行时会互相 `make clean`/`rm -rf` 对方正在编译的树。**这是 2.5.5 armv7 串架构污染（archcheck 抓到 4 成员 aarch64）的同根**——串行靠 xx-clear 事后清理掩盖，并行无法掩盖。
- **缺陷 D——失败日志不可见**：CI 只打印 `FAIL amd64 (see /tmp/...)`，既没 `tail` 出日志，日志又被 B 删了 → 无法定位。需失败时 dump 日志尾。

##### 3.1.2、修复方案：统一 `$WS` 工作区隔离（per-arch）

核心思路（用户拍板）：**设一个 `$WS` 变量，取值 `/tmp/ws-<链>-<arch安全名>`，该链路的源码树、日志、构建中间产物全部放进 `$WS` 子目录**。各架构并行时增删改各在各的 `$WS` 里，互不影响。`$WS` 由 `common.sh` 的 `xx_cross_init` 统一派生并 export，各脚本从 `$WS` 取子路径。

##### 3.1.5、doExec/oneBuild 独立日志的并行冲突评估（2026-11-26 15:04，本轮）

用户要求评估 `doExec`/`oneBuild` 的独立日志机制在并行下是否冲突。结论：**冲突，且 `doExec_check` 串味是真正确性 bug**（会把别的架构的失败记到本架构头上，误杀健康分支）。根因是 `LOGS` 派生自 `TARGETPATH`，而三并行分支的 `TARGETPATH` 相同 → `LOGS` 完全相同、共用一棵 doExec 日志树。

- **冲突点清单**（`common.sh` 的 `doExec`/`doExec_mark`/`doExec_check`/`oneBuild`）：

| # | 共享路径 | 写法 | 并行后果 | 严重度 |
|---|---|---|---|---|
| 1 | `$LOGS/doExec/<caller>/_exec_result.txt` | `echo "rc|cmd" >>` 追加 | 三架构 rc 记录混进同一文件 | 高 |
| 2 | 同上文件的 `# MARK` 边界 | `doExec_mark >>` 追加 | 三架构的组边界交错 | 高 |
| 3 | `doExec_check` 只读「最后一个 `# MARK` 之后」 | 读共享 `_exec_result.txt` | **串味**：读到别的架构 Concurrent 组的 rc → 误判本架构 FAIL（`|| exit 1` 杀死健康分支）或掩盖本架构真失败 | **致命** |
| 4 | `$LOGS/doExec/<caller>/<命令清洗名>.log` | `tee -a` 追加 | 同一命令（如 `build.sh pango`）三架构同名 → 输出交错进一个文件，失败无法按架构定位 | 中 |
| 5 | `oneBuild-$1.log`（`logfile`） | 仅 `oneBuild` 失败 tail 的 fallback | 与 #4 同理 | 低 |
| 6 | `LOGS`/`DOEXEC_LOG`/`logfile` 被 `export` | 泄漏进 `( set +e; $cmd )` 子 shell | 子 shell 同分支，benign；但若嵌套脚本重派生不一致会错位 | 低 |

#### 3.3、并行流程优化：fast-fail（2026-11-26 18:09）

##### 3.3.1、fast-fail（任一架构失败立即中断，不等全部完成）

###### 3.3.1.1、方案

**背景**：当前 `Dockerfile.builder.gtk224.xx` / `gtkmm224.xx` 的 `PARALLEL_BUILD=1` 分支用 `( ... ) &` 起三架构（amd64/arm64/arm-v7）后台子 shell，`wait` **等全部完成**后才逐 arch 校验 `.rc`。任一架构（如 amd64）早早失败，其余架构（arm64/armv7 可能各几十分钟）仍会跑完才报错——浪费时间。

**能否任一失败就直接报错？** 能。shell 无原生「等所有后台 job、任一失败即中断」，但用**进程组自杀 + 失败标记文件**可实现：

- 每个并行子 shell：① 启动时把自身 PID 记到 `$WS/logs/pids`；② `b_deps` 失败 → `kill 0`（杀整个进程组，sibling 全停）→ 写 `FAIL_ARCH=$tag` → `exit 1`。
- 父进程 `wait` 后：有 `FAIL_ARCH` → 直接报该架构失败 + `tail -60` dump 它的日志 → `exit 1`；无 → 才走原逐 arch `.rc` 校验（全成功路径不变）。

**效果**：任一架构失败 → 秒级中断全部（`kill 0` 杀进程组），不等慢的架构（可省几十分钟）；失败时 dump 该架构日志尾便于定位；**串行分支（`PARALLEL_BUILD=0`）、全成功路径完全不变**。

**两个注意点**：
1. `kill 0` 杀整个进程组（本 RUN 的 sh + 全部子 shell）——失败即整体放弃，正是目的。busybox ash 用 `|| { ...; }` 显式捕获失败比依赖 `set -e` 的 trap ERR 更稳。
2. 失败时 sibling 的 `.rc` 可能没写（被 kill）——但父进程优先看 `FAIL_ARCH`，不依赖 rc，不受影响。

**改动点（两个 builder Dockerfile 的 `PARALLEL_BUILD=1` 分支）**：
- 子 shell：登记 PID 到 `$WS/logs/pids`；`b_deps ... || { echo $tag > $WS/logs/FAIL_ARCH; kill 0 2>/dev/null; exit 1; }`。
- 父进程：`wait` 后先 `FA=$(cat $WS/logs/FAIL_ARCH 2>/dev/null)`，非空则报 `FAIL $FA (fast-fail)` + `tail -60` + `exit 1`；空才走原 rc 校验。

**待办**：gtk224.xx + gtkmm224.xx 都改（本轮开工）。

###### 3.3.1.2、实际落地代码（2026-11-26 18:15）

3.3.1 方案已落到 `Dockerfile.builder.gtk224.xx`（commit `d6ebd8c1`）与 `Dockerfile.builder.gtkmm224.xx`。两处改动**完全同构**，仅 `<链>`（gtk224/gtkmm224）与 `build.sh` 目标（`b_deps`/`full`）不同。以下为**实际加的代码**（以 gtk224 为例，`PARALLEL_BUILD=1` 分支）：

**① 子 shell 内——登记 PID + intermediate 失败也置 RC=1 + 失败写 FAIL_ARCH 并 kill 进程组**：
```sh
export WS=/tmp/ws-gtk224-$tag; \
mkdir -p $WS/logs; \
echo $$ >> $WS/logs/pids; \                    # 【新增】登记本分支 PID（供 kill 0 兜底/排查）
( unset XX_SYSROOT XX_CROSS_FILE XX_TRIPLE XX_MARCH; export TARGETPLATFORM=linux/$arch; export WS_LOCK=1; . /src/common.sh; xx_cross_init; \
  [ -n "$XX_SYSROOT" ] && sh /src/u-gtk/xx-clear.sh staticlib "$XX_SYSROOT"; \
  sh /src/u-gtk/build.sh b_deps > $WS/logs/$tag.log 2>&1; RC=$?; \
  [ -n "$XX_SYSROOT" ] && sh /src/u-gtk/xx-clear.sh intermediate "$XX_SYSROOT" || RC=1; \   # 【改】intermediate 失败也置 RC=1（原不管）
  echo $RC > $WS/logs/$tag.rc; \
  [ "$RC" = 0 ] || { echo "tag=$tag" > $WS/logs/FAIL_ARCH; kill 0 2>/dev/null; exit 1; } ) & \  # 【新增】失败→写标记+杀进程组
done; wait; \
```

**② 父进程——wait 后先查 FAIL_ARCH，有则秒报失败（不等/不看逐 arch rc）**：
```sh
FA=$(cat /tmp/ws-gtk224-*/logs/FAIL_ARCH 2>/dev/null); \       # 【新增】glob cat 避多文件 [ -s ] 误判
if [ -n "$FA" ]; then eval "$FA"; \                            # 【新增】从文件取回失败的 tag（子 shell 局部变量传不回父）
  echo "FAIL $tag (fast-fail):"; tail -60 /tmp/ws-gtk224-$tag/logs/$tag.log; exit 1; \
fi; \
for arch in amd64 arm64 arm/v7; do \                            # 【不变】无失败才走原逐 arch rc 校验
  ... [ "$(cat .../$tag.rc)" = "0" ] || { echo "FAIL $arch:"; tail -60 $LOG; exit 1; }; \
done; \
```

**关键设计点**：
- **`kill 0`**：杀整个进程组（本 RUN 的 sh + 全部子 shell），任一失败即整体中断，不等慢的架构。
- **`FAIL_ARCH` 文件传 tag**：子 shell 是 `( ... ) &` 后台，其局部 `tag` 传不回父进程；故失败时 `echo "tag=$tag" > FAIL_ARCH`，父进程 `eval "$FA"` 取回。
- **`cat glob` + `[ -n ]` 而非 `[ -s glob ]`**：多架构同时失败会产生多个 `FAIL_ARCH` 文件，`[ -s glob ]` 展开成多参数会"参数过多"误判漏报；`cat` 拼接 + `[ -n "$FA" ]` 稳。
- **`intermediate ... || RC=1`**：原来 `xx-clear intermediate` 失败不影响 RC（b_deps 成功就算过）；现失败也置 `RC=1`，触发 fast-fail（清理失败同样该中断）。
- **串行分支、全成功路径完全不变**：`FAIL_ARCH` 只在并行分支写；无失败时父进程走原 rc 校验。

**commit**：gtk224.xx=`d6ebd8c1`、gtkmm224.xx=本轮同批。两个 RUN 命令提取后 `bash -n` 语法通过；并行实际中断行为待 CI 三跑确认。

##### 3.3.2、apk 并行锁冲突与 flock 修复（2026-11-26 18:20，本轮）

###### 3.3.2.1、问题诊断与方案对比（前面的内容）

**现象**（CI 三架构并行实跑，`Dockerfile.builder.gtk224.xx:34`）：
```
1416.6 apkdeps, start building..
>>> Installing required Alpine packages...
ERROR: Unable to lock database: temporary error (try again later)
ERROR: Failed to open apk database: temporary error (try again later)   ×3
== doExec FAIL: bash /src/openbox/build.sh apkdeps (rc=99) ==
```

**根因**：`openbox/build.sh` 的 `apkdeps()`（u-gtk `b_deps` L427 `doExec .../openbox/build.sh apkdeps` 调用）里**第一条就是 native `apk --no-cache add`**（L385，装 curl/build-base/clang/meson/pkgconfig/glib-dev/intltool 等构建工具）。三架构并行时**每条分支都跑这条 native apk**，抢同一个 `/lib/apk/db/lock` → `rc=99 ELOCKED "temporary error (try again later)"`。
- **2.4.9.2「apk 并行无冲突」判断有误**：当时只分析了 cross `xx-apk` 自带的 `/var/lock/xx-apk` flock（arm64/armv7 互串）+ native/cross 不同 `--root`，**漏了 `apkdeps()` L385 这条 native apk**——它不走 xx-apk 的 flock，三分支抢同一 native lock。

**方案对比**：

| 方案 | 做法 | 缺点 |
|---|---|---|
| A. 重试退避 | rc=99 时退避重试 12 次（总容忍 ~5 分钟） | 不消除竞争只绕；最坏空等 ~5 分钟；非确定性（靠重试时机） |
| **B. flock 串行化（采用）** | 包装器先抢全局锁 `/tmp/apk-parallel.lock`，拿到才跑 apk，跑完释放 | 几乎无。3 次 native apk add 串行 ≈ 几秒~十几秒（apk add 本身快），**确定性、零重试浪费** |
| C. 装一次（最理想，改动大） | 公共 native 构建工具提到并行 fan-out 之前装一次，各分支 apkdeps 只留 cross xx-apk | 要重构 apkdeps/b_deps 拆 native/cross，改动大 |

**采用 B（flock）**：native apk add 本身快，3 分支排队能接受；确定性拿锁、无重试空等。`flock` 是 busybox/util-linux 标准工具，容器内有。

**修复实现**：`common.sh` 定义 `apk()` 包装器覆盖 native apk——**并行（`WS_LOCK=1`）时先 `flock /tmp/apk-parallel.lock` 再跑真 apk**（串行无 `WS_LOCK` 零开销直通）。`openbox/build.sh` 等 23 个 apk add 点均 source common.sh → 自动走包装器，**调用点零改动**；`xx-apk`（cross）自带 flock 不动。

###### 3.3.2.2、修复实现（common.sh `apk()` 包装器 flock，2026-11-26 18:32，本轮）

B 方案落地代码，全部在 `compile/src/common.sh`（commit `649db870`）。**仅新增一块 `apk()` 包装器 + 一行 `REAL_APK` 预解析**，23 个 apk add 调用点零改动（openbox/build.sh 等 source common.sh 后 `apk` 自动变包装器）：

```sh
# 真 apk 二进制在定义 apk() 前解析(此刻无同名函数不递归; 容器实测 = /sbin/apk)
REAL_APK=$(command -v apk 2>/dev/null)
function apk {
  if [ -z "$WS_LOCK" ]; then "$REAL_APK" "$@"; return $?; fi   # 串行(无 WS_LOCK)零开销直通
  flock /tmp/apk-parallel.lock "$REAL_APK" "$@"                # 并行: 全局锁串行化, 无竞争
}
```

**四个要点**：

1. **`REAL_APK=$(command -v apk)` 在定义 `apk()` 之前**——此刻 `apk` 还不是函数，`command -v` 解析到 PATH 里的真二进制（容器实测 `=/sbin/apk`）；若在函数内解析会拿到函数自身 → 递归。
2. **不能用 `/proc/$$/exe` 同目录推导真 apk**——容器 bash 在 `/bin/bash`，但 apk 在 `/sbin/apk`（不同目录），实测 `/bin/apk: No such file` 踩过。故用 `command -v` 预解析存 `REAL_APK`。
3. **`WS_LOCK` 门控**：并行子 shell 设 `WS_LOCK=1` → 走 `flock` 串行化；串行（`PARALLEL_BUILD=0`，无 `WS_LOCK`）直通真 apk，**零开销、行为不变**。
4. **只包 native apk**——冲突源是各分支 `apkdeps()` L385 的 native `apk add` 抢 `/lib/apk/db/lock`；cross `xx-apk` 自带 `/var/lock/xx-apk` flock 串行化不冲突，不动。

**验证**：`bash -n common.sh` 通过；容器内实测 `REAL_APK=/sbin/apk`、`flock ... apk --version` 正常、3 路并发 flock 拿锁 OK。并行实际去冲突效果待 CI 三跑确认。

##### 3.4.2、方案A：出错也 exit 0，镜像一定建成（只动首尾两处，2026-11-26 21:35）

**痛点**：当前 RUN 用 `set -e`，中途命令失败即整体 exit 1、镜像建不成；且 b_deps 输出 `> $WS/logs/$tag.log` 重定向进容器、RUN 退出即丢，错误日志拿不到（armv7 实测：b_deps 失败后 `kill 0` 在 dump 真错前杀掉父 shell，零错误输出）。

**方案（只动首尾两处，中间 fast-fail/archcheck/apkc 全不改）**：

把整个构建逻辑包进一个子 shell `( ... )`，子 shell 里 `set -e` 照旧（fast-fail 该杀杀、archcheck 该验验、失败该 exit 1 就 exit 1）——但这些只决定子 shell 的退出码。子 shell 结束后，外层最后一句 `exit 0` 兜底，RUN 永远 exit 0 → 镜像一定建成。

改前（L37 + L82）：
```dockerfile
  RUN set -e; \
    ARCHS=$(...); \
    if ... fi; \
    for ... done; \
    unset TARGETPLATFORM; \
    sh /src/u-gtk/apkc clean
```
改后：
```dockerfile
  RUN ( set -e; \
    ARCHS=$(...); \
    if ... fi; \
    for ... done; \
    unset TARGETPLATFORM; \
    sh /src/u-gtk/apkc clean \
  ); exit 0
```

就两处字符改动：
- L37：`RUN set -e;` → `RUN ( set -e;`
- L82：`apkc clean` → `apkc clean` + 换行 `); exit 0`

**为什么必须包一层（不能光尾部加 exit 0）**：`set -e` 在最前面，中途命令一失败（比如 archcheck/apkc 静默失败）当场就退出、走不到末尾的 `exit 0`。包进 `( ... )` 后，`set -e` 只管子 shell 内部（失败让子 shell exit 1），外层不看子 shell 退出码、直接执行 `exit 0`——这样才保证镜像一定建成。

**关键点**：
- fast-fail（失败杀全家）逻辑一字不改——它在子 shell 内部照旧工作（`kill 0` 杀并行兄弟、写 FAIL_ARCH、子 shell exit 1）。
- 子 shell 退出码被外层 `exit 0` 无视 → 无论内部成败，镜像一定建成。
- 事后判断：看镜像里产物 `.a` + `.logs/doExec|oneBuild` 明细（本地 `docker run`、CI pull 后都能取）；失败时 fast-fail 的 `tail -60` 也会进 build log。

**适用边界**：`kill 0` 杀同一进程组。单架构调试（armv7/arm64 单跑，只 1 个后台子 shell）它只杀自己（无兄弟），外层存活 → exit 0 → 镜像建成；三架构并行时先失败分支的 `kill 0` 会连外层一起带走 → 镜像建不成（这与「fail-fast 杀全家不能改」同一件事，保留的行为）。

**待拍板**：(a) 纯无条件 exit 0（建议，最符合「即使中途失败也 exit 0」）；(b) 末尾加「产物 `.a` 全缺才 exit 1」兜底。范围：gtk224.xx + gtkmm224.xx 是否一起改。

##### 3.5.1、找错误文件 / 错误定位 / 错误分析：armv7 实录（2026-11-27 00:35，本轮，已复现）

**① 找错误文件：四层信号，由外向内**

| 层 | 位置 | 内容 | 作用 |
|---|---|---|---|
| ① 报告 | `/report/u-gtk-<tag>.txt` | `FAIL_MODULE` + `FAIL_LOG` 绝对路径 + `CONCLUSION` | 入口：直接告诉你**哪个模块**、**日志在哪** |
| ② 退出码 | `$WS/logs/<tag>.rc` | 单个 rc | 粗判成败（`intermediate cleaned` **不等于**成功，见 3.1） |
| ③ 步骤账本 | `/usr/local/static/.logs/<arch>/doExec/<caller>/_exec_result.txt` | 逐行 `rc\|cmd`，`# MARK` 组边界 | **真凶定位**：找 `rc!=0` 的那一行 |
| ④ 步骤日志 | 同目录下 `<cmd 文件名化>.log` | 该步全量输出 | 看**死在哪一刻**（字节数是关键线索） |

- ③④ 按 `<arch>` 隔离（`armv7l`/`aarch64`/`native`，3.1.5 加的），三架构不串味。
- 失败现场可**烘焙进镜像**（本例 `-bk0` 镜像 1.51GB 就带着 `.logs`）→ `docker run --rm <img> cat <path>` 直接读，不用复现。

**② 错误定位：三条判定规则**

1. **`_exec_result.txt` 里只有一行 `rc!=0`，同组其余全 `0|`** → 那行就是元凶，**不是连带受害者**（并行的 `kill 0` 连带会让多行一起非 0）。
2. **FAIL_LOG 字节数极小**（本例 220B）→ 死在 **source 脚本 / 前置阶段**，连 Download 都没到——别去猜编译错、别猜 OOM。
3. **rc 语义先解码再分析**：`1` = `set -e` 打断的前置错 / `141` = SIGPIPE（128+13）/ `137` = OOM(SIGKILL) / `143` = SIGTERM(`kill 0` 灭口) / `99` = apk `ELOCKED`。141 曾误导成"被 kill"，实为管线写端被断。

**③ 为什么「干净隔离重跑成功」会误导**

隔离重跑 armv7 b_deps 曾 **BUILD_RC=0 全过** → 一度误判"armv7 无病、是 CI 环境问题"。教训：**隔离重跑排除了并行维度，也就排除了并行类根因**。竞态类 bug 必须**并发复现**（见下方 8 并发实验），顺序跑必然查不出。

**④ 具体错误问题分析：`xx-clang-wrapper` 安装竞态**

**真错一行**（`FAIL_LOG` 里）：

```
cp: can't open '/usr/bin/xx-clang-wrapper': File exists
```

**元凶**：`compile/src/openbox/build.sh:30`（脚本**顶部，source 即执行**）：

```sh
[ -f "$SCRIPT_DIR/xx-clang-wrapper" ] && { \cp -a "$SCRIPT_DIR"/xx-clang-wrapper /usr/bin/; chmod +x /usr/bin/xx-clang-wrapper; }
```

**为何只有 libxrandr 挂**：group1 里 `openbox/build.sh pango` 与 `openbox/build.sh libxrandr` **两条并行分支 source 同一脚本** → 同时 `cp -a ... /usr/bin/` 抢建 `/usr/bin/xx-clang-wrapper`，后到者撞 EEXIST → `set -e` 下该 step 退出 rc=1。`_exec_result.txt` 铁证：仅 `1|bash /src/openbox/build.sh libxrandr`，同组 pango/Xdamage/libcroco 全 `0|`。

**`:29` 注释「两个并行进程各自兜底，无竞态」是错的**——顺序 `cp -a` 两次都是 rc=0，**顺序测试查不出**，必须并发。

**8 并发复现实验**（`-bk0` 镜像，约 1 秒）：

| 方式 | 结果 |
|---|---|
| 删掉 wrapper 后 8 条并发 `cp -a src /usr/bin/` | **1/8 失败** rc=1，错误串与 FAIL_LOG **一字不差** |
| 8 条并发 `cp tmp + mv -f` | **全 8 个 rc=0**，零报错 |

**修法（已拍板落地，`46f20a06` + `763dab49`）**：采用**存在性判断**（内容一致 → 跳过即安全），加 `|| true` 吞掉极窄 TOCTOU 窗口里输掉的那次 cp（否则 `set -e` 直接退出，正是本例死法），`2>/dev/null` 免刷屏。8 并发实测 8/8 rc=0、`cmp` 内容一致。

```sh
if [ ! -x /usr/bin/xx-clang-wrapper ] && [ -f "$SCRIPT_DIR/xx-clang-wrapper" ]; then
  \cp -a "$SCRIPT_DIR"/xx-clang-wrapper /usr/bin/ 2>/dev/null || true
  chmod +x /usr/bin/xx-clang-wrapper 2>/dev/null || true
fi
```

另一候选（未采用）：原子 tmp + `mv -f`（`rename(2)` 替换不 EEXIST）——完全 race-free，但为这点窗口不值得加复杂度；存在性判断已把窗口压到两个分支**同时**都读到「不存在」的量级。

**连带潜伏点（未爆，建议日志/并行侧一并处理）**：`xx_cross_init`（`common.sh:359`）对**同一个** `$WS/xx-cross-<march>.ini` 做 `cat >`；group1 四分支同 arch 同 march → 4 路并发写同一 cross-file，理论可撕裂。本例死在更早的 wrapper cp，未波及。
